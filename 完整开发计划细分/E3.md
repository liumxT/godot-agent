# 1. 阶段概述

## 1.1 阶段定位

E3 的主要任务是建立 Godot Editor Plugin 与 Local Backend 之间的完整连接体系。

E0 建立了 Godot 插件工程骨架。

E1 建立了 Backend Core。

E2 建立了 API、认证、Session 和权限服务。

E3 将这些基础能力连接起来，使 Godot 插件真正成为 Backend 的本地客户端。

本阶段完成后，系统应该具备：

- Godot 插件可以正常安装、启用和关闭。
- 插件可以自动发现或连接本地 Backend。
- 插件和 Backend 可以安全认证。
- 插件可以建立和维护 Editor Session。
- Backend 能够识别当前 Godot Editor 和项目。
- 插件可以持续发送心跳。
- Backend 能够感知 Editor 在线状态。
- 连接中断后能够重新连接和恢复状态。
- 多 Editor、多项目能够相互隔离。
- Backend 能够获得必要的 Godot Editor 状态信息。
- Godot Runtime 可以通过独立通道与 Backend 通信。

**本阶段的核心不是让 AI 自动修改游戏，而是先建立 AI 能够可靠、安全地连接和感知 Godot 的基础。**

## 1.2 阶段目标

| 编号 | 目标 | 完成标准 |
|---|---|---|
| E3-G01 | Plugin 生命周期 | 插件启用、关闭和资源释放正常 |
| E3-G02 | Backend Discovery | 能够发现并连接本地 Backend |
| E3-G03 | Editor Bridge | 建立 Godot Editor 与 Backend 双向通信 |
| E3-G04 | 身份认证 | 复用 E2 认证机制 |
| E3-G05 | Editor Session | 建立独立 Editor Session |
| E3-G06 | Heartbeat | 持续检测连接和 Session 状态 |
| E3-G07 | Session Lease | 防止过期 Editor 会话继续执行操作 |
| E3-G08 | Event Sync | 支持事件同步和事件确认 |
| E3-G09 | Snapshot Recovery | 断线后通过 Snapshot + Event 恢复 |
| E3-G10 | Multi-Editor | 支持多个 Godot Editor 同时连接 |
| E3-G11 | Project Isolation | 不同项目之间保持隔离 |
| E3-G12 | Editor State | 获取必要的编辑器状态 |
| E3-G13 | Runtime Bridge | 建立游戏运行时独立通信通道 |
| E3-G14 | Integration Testing | 完成真实 Godot Editor 集成测试 |

## 1.3 本阶段不包含

- 自动创建完整游戏场景。
- 自动编辑 Inspector 属性的完整工具集。
- 自动操作 TileMap 的完整工具集。
- 自动修改脚本的完整工作流。
- AI Agent 的自主执行循环。
- 多 Agent 协作。
- 资源生成管线。

这些功能会在 E5–E8 等阶段逐步实现。

E3 只负责提供可靠的通信、状态感知和操作授权基础。

## 2.2 三个核心组成部分

### A. Godot Editor Plugin

负责：

- 插件生命周期。
- Backend 连接。
- 身份认证。
- Editor Session。
- 心跳。
- 编辑器状态采集。
- 接收 Backend 命令。
- 执行经过授权的编辑器操作。
- 发送执行结果。

### B. Backend Editor Bridge

负责：

- 接收 Editor 连接。
- 验证身份。
- 创建 Editor Session。
- 管理 Session Lease。
- 接收心跳。
- 管理连接状态。
- 分发事件。
- 维护状态快照。
- 恢复断线连接。

### C. Runtime Bridge

负责：

- 接收游戏运行时主动连接。
- 独立验证 Runtime 身份。
- 识别对应的 Editor Session 和 Project。
- 接收运行状态。
- 传递调试和运行事件。
- 断开后安全清理。

Runtime Bridge 不得直接继承 Editor 的写入权限。

## E3-T04：Editor Bridge Protocol

**优先级：** P0  
**依赖：** E2、E3-T03

### 开发目标

建立 Editor Plugin 与 Backend 之间的专用通信协议。

### 通信原则

- 使用本机 WebSocket。
- 协议使用统一 Envelope。
- 每个消息具有唯一 ID。
- 每个消息具有协议版本。
- 请求与响应可关联。
- 事件具有唯一事件 ID。
- 重要事件需要确认。
- 未知消息类型必须安全拒绝。

### Envelope 格式

```json
{
  "protocol_version": "1.0",
  "message_id": "message-id",
  "message_type": "REQUEST",
  "action": "editor.get_state",
  "timestamp": "2026-11-17T10:00:00Z",
  "session_id": "session-id",
  "project_id": "project-id",
  "correlation_id": "correlation-id",
  "payload": {}
}
```

### 消息类型

| 类型 | 用途 |
|---|---|
| HELLO | 连接初始化 |
| AUTH_CHALLENGE | 认证挑战 |
| AUTH_RESPONSE | 认证响应 |
| SESSION_CREATED | Session 创建 |
| HEARTBEAT | 心跳 |
| REQUEST | 请求 |
| RESPONSE | 响应 |
| EVENT | 事件 |
| EVENT_ACK | 事件确认 |
| SNAPSHOT_REQUEST | 请求快照 |
| SNAPSHOT_RESPONSE | 返回快照 |
| ERROR | 错误 |

### 实施步骤

1. 定义 Envelope。
2. 定义 Message Type。
3. 定义 Action Registry。
4. 定义 Payload Schema。
5. 定义响应关联机制。
6. 定义消息超时。
7. 定义未知消息处理。
8. 实现协议版本校验。

### 验收标准

Backend 和 Godot Plugin 对同一消息能够正确解析，且非法消息无法触发未经授权的操作。

**依赖：** E3-T07

```text

```

### Lease 状态

```text

   |
   v

   |
   ├──> ACTIVE
   |
   └──> EXPIRED
```

### 实施步骤

1. 创建 Lease Model。
2. 创建 Lease Manager。
3. 实现 Lease 发放。
4. 实现 Lease 续期。
5. 实现 Lease 过期。
6. 实现 Lease 撤销。
7. 实现 Fencing Token。
8. 实现失效 Lease 拒绝。
9. 实现 Lease 审计。

### Fencing Token 原则

每次产生新的有效租约时，应产生可比较的新版本令牌。

涉及受保护操作时，Backend 必须验证操作所携带的 Fencing Token 是否仍然有效。

旧连接恢复时不能覆盖新连接已经获得的有效租约。

### 验收标准

过期租约无法执行需要有效 Editor Session 的操作。

## E3-T12：Reconnection & Recovery

**优先级：** P0  
**依赖：** E3-T08、E3-T09、E3-T11

### 开发目标

实现网络中断后的自动重连和状态恢复。

### 恢复流程

```text
连接中断
   |
   v
标记连接失效
   |
   v
停止新的受保护操作
   |
   v
执行重连策略
   |
   v
重新认证
   |
   v
验证 Session 和 Lease
   |
   v
请求 Snapshot
   |
   v
获取缺失事件
   |
   v
校验事件顺序
   |
   v
状态恢复成功？
  ├── 否：进入人工处理或完整重新同步
  └── 是：恢复正常连接
```

### 实施步骤

1. 检测连接断开。
2. 暂停受保护操作。
3. 实现重连等待策略。
4. 重新建立 WebSocket。
5. 重新认证。
6. 验证原 Session 状态。
7. 获取有效 Lease。
8. 请求 Snapshot。
9. 补齐缺失事件。
10. 验证恢复结果。
11. 恢复正常服务。
12. 记录恢复过程。

### 安全原则

- 断线不等于操作成功。
- 未知操作结果不能盲目重试。
- 已经过期的 Fencing Token 不得继续使用。
- 无法确认状态时必须标记 UNKNOWN。
- 不允许把不确定状态自动转换为成功。

## E3-T14：Project Identity & Isolation

**优先级：** P0  
**依赖：** E3-T13

### 开发目标

让 Backend 能够准确识别每个 Godot 项目。

### Project Identity

建议使用：

```text
project_id
project_root
project_fingerprint
project_config_path
godot_version
project_name
```

其中：

- project_id：Backend 内部项目标识。
- project_root：项目根目录。
- project_fingerprint：用于识别项目的稳定指纹。
- project_config_path：项目配置文件路径。

### 识别原则

不能只依靠项目名称识别项目。

不能只依靠客户端传入的路径认定项目身份。

需要综合检查：

- 项目路径。
- 项目配置文件。
- 项目标识信息。
- 文件系统访问权限。
- Backend 已注册项目记录。

### 实施步骤

1. 获取当前项目根目录。
2. 定位 `project.godot`。
3. 计算项目指纹。
4. 与 Backend 项目记录比对。
5. 创建或查询项目关联。
6. 建立 Session 与 Project 关系。
7. 实现路径变化检测。
8. 实现项目切换处理。

### 重要规则

如果同一个 Editor 切换项目：

1. 暂停原项目受保护操作。
2. 更新当前项目身份。
3. 重新验证 Project Access。
4. 创建或更新相应 Session Scope。
5. 完成状态同步后才允许继续执行。

### 权限要求

Runtime 不得自动继承 Editor 的写入权限。
