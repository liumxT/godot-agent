# 1. 阶段概述

## 1.1 阶段定位

E1 是 Backend 正式进入功能开发的第一个阶段。

E0 建立了工程骨架、开发规范、技术选型和基础协议。

E1 则需要将这些基础设施真正实现为可以运行、测试、维护的 Backend Core。

Backend Core 是整个系统的基础运行层，后续所有业务模块都需要依赖它。

本阶段不开发具体 AI Agent 业务，也不实现完整 Godot 编辑器操作，而是建立后续模块共同使用的核心服务。

## 1.2 阶段目标

| 编号 | 目标 | 完成标准 |
|---|---|---|
| E1-G01 | Backend 生命周期 | 能够启动、运行、优雅关闭 |
| E1-G02 | 配置服务 | 支持配置加载、验证和分层 |
| E1-G03 | 数据库服务 | SQLite 正常运行，支持事务和迁移 |
| E1-G04 | Repository 基础 | 建立模块隔离的数据访问机制 |
| E1-G05 | 日志服务 | 结构化日志、关联 ID、日志轮转 |
| E1-G06 | 事件基础设施 | 建立事件发布、订阅和持久化基础 |
| E1-G07 | 异常处理 | 统一异常分类和错误响应 |
| E1-G08 | 备份与恢复 | 支持数据库备份、完整性检查和恢复 |
| E1-G09 | 健康检查 | 能够识别 Backend 核心服务状态 |
| E1-G10 | 可观测性 | 能够定位启动、数据库和基础设施故障 |

## 1.3 本阶段不包含

以下内容由后续阶段负责：

- Task、Workflow 的完整业务实现。
- Agent Runtime。
- Model Gateway。
- Tool Registry 和 Tool Execution。
- Godot Editor Bridge。
- Runtime Bridge。
- 多 Agent Orchestration。
- Asset Pipeline。
- Verification 业务系统。

E1 可以提供这些模块未来需要的基础接口，但不能提前把它们的业务状态管理放入 Backend Core。

# 2. 总体架构

## 2.1 Backend Core 组成

本阶段将 Backend Core 划分为以下模块：

| 模块 | 职责 |
|---|---|
| Application Lifecycle | 应用启动、关闭和生命周期管理 |
| Configuration Service | 配置加载、合并和验证 |
| Database Service | SQLite 连接、事务和连接管理 |
| Migration Service | 数据库结构版本管理 |
| Repository Infrastructure | 数据访问基础设施 |
| Logging Service | 统一日志记录 |
| Event Infrastructure | 事件基础设施 |
| Error Handling | 异常分类和统一错误处理 |
| Backup Service | 数据库备份和恢复 |
| Health Service | 健康检查 |
| Observability | 基础运行状态和诊断信息 |

## 2.2 模块关系

```text
                 Backend Application
                          |
                 Application Lifecycle
                          |
       ┌──────────────────┼──────────────────┐
       |                  |                  |
 Configuration       Core Services       Observability
       |                  |                  |
       |          ┌───────┼────────┐         |
       |          |       |        |         |
       |       Database  Logging  Event    Health
       |          |       |        |
       |       Migration  Error   Outbox
       |          |
       |       Repository Infrastructure
       |          |
       └──────────┴──────────────────────────┘
                          |
                    Future Modules
```

## 2.3 核心架构原则

1. Backend Core 不拥有具体业务模块的业务状态。
2. 业务模块通过公开接口使用 Core 服务。
3. Repository 只能访问所属模块的数据。
4. Core 不允许反向依赖业务模块。
5. 数据库是持久化数据的唯一 Primary Store。
6. 重要事件需要具备持久化和幂等基础。
7. 服务关闭必须考虑未完成事务和正在执行的任务。
8. Core 服务失败时不得伪装成正常运行。
9. 所有关键操作必须具备可追踪的日志。
10. 关键数据恢复必须经过验证。

# 4. 详细开发实施

## E1-T01：Backend 生命周期管理

**优先级：** P0  
**依赖：** E0 工程骨架  
**负责人：** Backend 工程师

### 4.1.1 开发目标

建立 Backend 应用统一的启动、运行和关闭管理机制。

不允许每个业务模块自行启动后台线程或独立管理整个 Backend 的生命周期。

### 4.1.2 建议目录

```text
apps/backend/src/
├── app/
│   ├── application.py
│   ├── lifecycle.py
│   └── service_registry.py
│
├── bootstrap/
│   ├── bootstrap.py
│   ├── startup.py
│   └── shutdown.py
│
└── core/
    └── lifecycle/
        ├── interfaces.py
        ├── manager.py
        └── states.py
```

具体文件扩展名按 E0 最终选定的语言和框架调整。

### 4.1.3 生命周期状态

```text
CREATED
   |
   v
INITIALIZING
   |
   v
STARTING
   |
   v
RUNNING
   |
   v
STOPPING
   |
   v
STOPPED
```

异常状态：

```text
INITIALIZING / STARTING / RUNNING
                  |
                  v
                FAILED
```

### 4.1.4 实施步骤

1. 创建 Application 主对象。
2. 创建 Lifecycle Manager。
3. 定义应用生命周期状态。
4. 实现启动依赖注册。
5. 实现服务初始化顺序。
6. 实现启动失败处理。
7. 实现优雅关闭。
8. 实现关闭超时。
9. 实现系统信号处理。
10. 实现启动和关闭日志。

### 4.1.5 启动顺序

建议：

```text
读取配置
   ↓
初始化日志
   ↓
初始化错误处理
   ↓
初始化数据库
   ↓
执行 Migration
   ↓
初始化基础服务
   ↓
启动健康检查
   ↓
Backend RUNNING
```

### 4.1.6 关闭顺序

```text
停止接收新请求
   ↓
通知服务进入 STOPPING
   ↓
停止后台调度
   ↓
等待正在执行的操作
   ↓
提交或回滚事务
   ↓
关闭事件处理器
   ↓
关闭数据库连接
   ↓
刷新日志
   ↓
Backend STOPPED
```

### 4.1.7 异常处理要求

如果数据库初始化失败：

- Backend 不得进入 RUNNING。
- 必须记录具体失败原因。
- 必须清理已初始化的资源。
- 必须返回明确启动失败结果。

### 4.1.8 测试

- E1-T01-UT-001：正常启动。
- E1-T01-UT-002：正常关闭。
- E1-T01-UT-003：重复关闭。
- E1-T01-UT-004：启动过程中失败。
- E1-T01-UT-005：关闭超时。
- E1-T01-IT-001：完整生命周期运行。

### 4.1.9 验收标准

Backend 能够稳定启动和关闭；启动失败不会留下无法清理的半初始化状态。

## E1-T02：配置服务实现

**优先级：** P0  
**依赖：** E1-T01

### 4.2.1 开发目标

实现真正可用的配置管理服务。

### 4.2.2 配置来源

4. 本地用户配置。

```text

  ↓

```

Secrets 不应直接参与普通配置文件的明文合并。

### 4.2.3 配置分组

```text
application
database
logging
network
security
storage
runtime
backup
```

### 4.2.4 实施步骤

1. 创建 Configuration Provider 接口。
2. 实现默认配置加载。

8. 实现必填项验证。
9. 实现配置快照。

### 4.2.5 动态配置原则

## E1-T03：SQLite 数据库服务

**优先级：** P0  
**依赖：** E1-T01、E1-T02

### 4.3.1 开发目标

实现统一数据库访问基础设施。

### 4.3.2 数据库原则

- SQLite 是唯一 Primary Database。
- WAL 模式。
- 事务尽量短。
- 数据库连接生命周期由 Backend 管理。
- Repository 不自行创建全局数据库连接。
- 数据库异常必须明确分类。
- 不允许业务模块直接操作其他模块的数据表。

### 4.3.3 建议目录

```text
apps/backend/src/infrastructure/database/
├── connection.py
├── database_manager.py
├── transaction.py
├── health.py
├── errors.py
└── interfaces.py
```

### 4.3.4 实施步骤

1. 创建 Database Manager。
2. 创建数据库连接接口。
3. 实现 SQLite 连接初始化。
4. 配置 WAL。
5. 配置合理的忙等待和锁处理策略。
6. 配置外键约束。
7. 实现数据库连接关闭。
8. 实现数据库完整性检查。
9. 实现数据库状态检测。
10. 实现数据库故障日志。

### 4.3.5 并发要求

SQLite 存在写入并发限制。

必须：

- 控制事务时间。
- 避免长时间持有写锁。
- 避免在事务中调用外部 AI 服务。
- 避免在事务中等待用户审批。
- 为写入冲突定义明确的处理策略。

### 4.3.6 测试

- E1-T03-UT-001：数据库初始化。
- E1-T03-UT-002：WAL 模式验证。
- E1-T03-UT-003：外键约束验证。
- E1-T03-UT-004：数据库关闭。
- E1-T03-IT-001：多连接访问。
- E1-T03-IT-002：写入冲突。
- E1-T03-IT-003：数据库文件不可写。

### 4.3.7 验收标准

数据库能够正常创建、连接、读写、关闭，异常状态能够被识别。

## E1-T06：事务管理服务

**优先级：** P0  
**依赖：** E1-T03

### 4.6.1 开发目标

建立统一事务边界管理。

### 4.6.2 事务能力

- Begin。
- Commit。
- Rollback。
- Transaction Scope。
- Nested Transaction 处理策略。
- Timeout。
- Transaction Error。

### 4.6.3 关键规则

2. 不允许在事务内等待外部模型响应。

4. 不允许长时间持有数据库写锁。
5. 失败时必须回滚。
6. 不允许在事务结束后继续使用失效会话。

### 4.6.4 测试

- E1-T06-UT-003：事务超时。

### 4.9.1 开发目标

建立系统内部事件基础设施。

后续 Task、Workflow、Agent、Asset、Verification 等模块都需要通过事件进行解耦通信。

### 4.9.2 事件模型

```json
{
  "event_id": "unique-event-id",
  "event_type": "example.event",
  "event_version": 1,
  "occurred_at": "2026-11-17T10:00:00Z",
  "producer": "example-module",
  "correlation_id": "correlation-id",
  "payload": {}
}
```

### 4.9.3 事件分类

- Domain Event。
- Integration Event。
- Infrastructure Event。

### 4.9.4 实施步骤

1. 创建 Event Interface。
2. 创建 Event Registry。
3. 创建 Publisher。
4. 创建 Subscriber。
5. 创建事件处理器注册机制。
6. 创建事件版本字段。
7. 创建事件处理结果记录。
8. 实现重复事件检测基础。
9. 实现处理异常记录。

### 4.9.5 关键原则

- 事件不能替代业务状态的唯一所有权。
- 发布事件不意味着业务操作必然成功。
- 事件处理器必须考虑重复投递。
- 事件必须可追踪。
- 事件处理失败不能静默丢弃。

### 4.9.6 测试

- E1-T09-UT-001：事件发布。
- E1-T09-UT-002：事件订阅。
- E1-T09-UT-003：重复事件。
- E1-T09-UT-004：事件版本。
- E1-T09-IT-001：多订阅者处理。

## E1-T10：Outbox / Inbox 基础机制

**优先级：** P1  
**依赖：** E1-T09、E1-T06

### 4.10.1 开发目标

解决数据库事务提交与事件发送之间的一致性问题。

### 4.10.2 Outbox

业务数据与待发布事件必须在同一数据库事务中提交。

建议流程：

```text
开始事务
   ↓
写入业务数据
   ↓
写入 Outbox
   ↓
提交事务
   ↓
后台扫描 Outbox
   ↓
发布事件
   ↓
标记已发布
```

### 4.10.3 Inbox

接收方需要记录已处理事件。

建议流程：

```text
接收事件
   ↓
检查 Event ID
   ↓
是否已处理？
  ├─ 是：返回已处理结果
  └─ 否：执行业务处理
           ↓
       记录 Inbox
           ↓
          提交
```

业务处理和 Inbox 记录应尽可能处于同一个本地事务中。

### 4.10.4 建议数据字段

Outbox：

```text
event_id
event_type
payload
created_at
published_at
status
retry_count
last_error
```

Inbox：

```text
event_id
consumer_id
received_at
processed_at
status
```

### 4.10.5 测试

- E1-T10-UT-001：Outbox 写入。
- E1-T10-UT-002：事件成功发布。
- E1-T10-UT-003：发布失败重试。
- E1-T10-UT-004：Inbox 重复事件拒绝。
- E1-T10-IT-001：业务事务和事件持久化一致性。
- E1-T10-IT-002：进程中断恢复。

## E1-T11：数据库备份与恢复

**优先级：** P1  
**依赖：** E1-T03、E1-T04

### 4.11.1 开发目标

确保 Backend 在数据库损坏、升级失败或用户误操作后具备基础恢复能力。

### 4.11.2 备份类型

- 手动备份。
- 自动备份。
- 升级前备份。
- 重大操作前备份。

### 4.11.3 实施步骤

1. 创建 Backup Service。
2. 实现数据库一致性备份。
3. 实现备份元数据。
4. 实现备份文件完整性校验。
5. 实现备份保留策略。
6. 实现恢复前检查。
7. 实现恢复操作。
8. 实现恢复后数据库完整性验证。
9. 实现恢复审计日志。

### 4.11.4 恢复流程

```text
选择备份
   ↓
检查备份完整性
   ↓
停止数据库写入
   ↓
创建当前数据保护副本
   ↓
恢复备份
   ↓
执行完整性检查
   ↓
验证 Migration 版本
   ↓
恢复服务
   ↓
记录恢复结果
```

恢复失败时不得直接删除当前数据。

## E1-T12：Health Check 健康检查

**优先级：** P1  
**依赖：** E1-T02、E1-T03、E1-T07

### 4.12.1 开发目标

建立 Backend 核心服务状态检查机制。

### 4.12.2 检查内容

- Application 状态。
- Database 状态。
- Migration 状态。
- Configuration 状态。
- Logging 状态。
- Event Infrastructure 状态。
- Backup Service 状态。

### 4.12.3 健康状态

```text
HEALTHY
DEGRADED
UNHEALTHY
STARTING
STOPPING
```

### 4.12.4 检查原则

健康检查应区分：

- Liveness：进程是否存活。
- Readiness：是否能够正常接受工作。
- Dependency Health：关键依赖是否可用。

健康检查不应触发危险的写入操作。

### 4.12.5 测试

# 9. E1 风险管理

| 风险编号 | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| E1-R01 | SQLite 写入锁竞争 | 并发性能下降 | 短事务、限制写入并发 |
| E1-R02 | 事务范围不清晰 | 数据不一致 | 统一 Transaction Scope |
| E1-R03 | 事件重复投递 | 重复业务操作 | Event ID 和 Inbox 幂等 |
| E1-R04 | Migration 失败 | Backend 无法启动 | 升级前备份、失败检测 |
| E1-R05 | 日志泄露敏感数据 | 安全风险 | 字段脱敏和安全测试 |
| E1-R06 | 备份不可恢复 | 数据丢失 | 定期恢复演练 |
| E1-R07 | Core 过度耦合业务 | 后续扩展困难 | 严格模块依赖约束 |
| E1-R08 | 过早引入复杂机制 | 开发成本上升 | 只实现后续阶段确实需要的基础能力 |

# 10. E1 阶段结束后的下一阶段准入条件

E1 验收完成后，进入 E2 Backend Services。

E2 将在 E1 基础上实现对外服务和业务基础接口，主要包括：

- Backend API Server。
- API 路由和版本管理。
- 请求认证。
- Session 管理基础服务。
- 权限检查接口。
- Request/Response 中间件。
- API 限流和请求大小限制。
- 基础审计接口。
- 服务端错误响应。
- API 契约测试。

E2 不应重新实现 E1 已完成的数据库、日志、配置和事务基础设施。
