# 1. 阶段概述

## 1.1 阶段定位

E0 是整个 Godot AI Agent 项目的工程基础阶段。

本阶段不开发完整的 AI Agent 功能，也不开发复杂的 Godot 编辑器自动化功能。

本阶段的主要任务是建立后续所有开发工作共同使用的工程基础，确保未来 Backend、Godot Plugin、Agent Runtime、Tool System、Asset Pipeline、Verification 等模块能够按照统一规范开发和集成。

E0 完成后，团队应当拥有：

- 可以正常运行的项目开发仓库。
- 清晰且可扩展的代码目录结构。
- 统一的开发环境和运行方式。
- 统一的模块划分和依赖规范。
- 统一的 API、事件和错误编码规范。
- 基础 CI 检查流程。
- 数据库迁移和版本管理基础。
- 日志、配置、环境变量管理规范。
- 开发、测试、构建的基本工作流程。
- 可以供 E1 直接使用的工程骨架。

## 1.2 阶段目标

| 目标编号 | 目标 | 完成标准 |
|---|---|---|
| E0-G01 | 建立项目仓库 | 所有核心工程拥有明确归属 |
| E0-G02 | 建立代码目录 | 模块边界清晰，目录结构可扩展 |
| E0-G03 | 建立开发环境 | 新开发人员能够按照文档启动项目 |
| E0-G04 | 建立编码规范 | 命名、格式、异常处理有统一标准 |
| E0-G05 | 建立接口规范 | API、事件、错误响应具有统一格式 |
| E0-G06 | 建立基础 CI | 提交代码时自动执行基础检查 |
| E0-G07 | 建立配置体系 | 开发配置、生产配置和 Secrets 分离 |
| E0-G08 | 建立工程文档体系 | 后续开发有统一的设计、实施和测试文档模板 |

## 1.3 本阶段不包含的内容

以下内容不属于 E0 的正式开发范围：

- 完整 Backend 服务。
- Agent 执行引擎。
- AI 模型调用。
- 多 Agent 协作。
- Godot Editor Bridge。
- Godot Runtime Bridge。
- 完整任务管理系统。
- 资源生成和导入管线。
- 完整游戏开发能力。

这些内容分别在后续阶段实施。

# 2. 整体工程结构设计

## 2.1 系统组成

整个产品由三个主要工程组成：

1. Godot Editor Plugin：负责 Godot 编辑器内的交互和操作。
2. Local Backend：负责业务逻辑、Agent、工具、项目管理和数据管理。
3. Shared Contracts：负责跨模块和跨进程的数据协议。

建议初始仓库采用 Monorepo（单仓库多工程）结构。

## E0-T02：技术栈和运行环境确定

**优先级：** P0  
**依赖：** E0-T01  
**负责角色：** 技术负责人、Backend 负责人、Godot 负责人

### 开发目标

明确 Backend、Godot Plugin、数据库、测试工具的技术选型。

### 需要评审的技术领域

| 领域 | 需要确定的内容 |
|---|---|
| Backend | 编程语言、运行时、服务框架 |
| Godot Plugin | Godot 版本、GDScript 使用范围 |
| 通信 | 本地 HTTP、WebSocket 等通信基础 |
| Database | SQLite 驱动和迁移工具 |
| Testing | 单元测试和集成测试框架 |
| CI | 自动化构建和测试平台 |
| Packaging | Backend 本地安装和运行方式 |
| Logging | 日志框架和日志格式 |

### 技术选型原则

1. 优先本地运行。
2. 优先跨平台。
3. 避免 Backend 与 Godot 版本强绑定。
4. 避免插件直接依赖 Backend 内部代码。
5. 优先使用成熟、可维护的工具。
6. 不引入没有实际使用需求的复杂基础设施。
7. 不把用户 API Key 和密码写入普通配置文件。

### 需要形成的技术决策记录

每项重要选型形成 ADR（Architecture Decision Record）：

```text
docs/06-decisions/

ADR-001-backend-language.md
ADR-002-backend-framework.md
ADR-003-godot-version.md
ADR-004-database.md
ADR-005-local-communication.md
ADR-006-testing-framework.md
```

每份 ADR 应包含：

- 问题背景。
- 备选方案。
- 比较标准。
- 选定方案。
- 选择理由。
- 影响范围。
- 后续可能调整的条件。

### 交付物

- 技术栈清单。
- 开发环境版本清单。
- ADR 文档。
- 开发环境安装说明。

### 验收标准

所有核心技术选择均有记录，开发人员能够在统一环境中运行基础工程。

## E0-T05：Shared Contracts 协议基础

**优先级：** P0  
**依赖：** E0-T02  
**负责角色：** 系统架构师、Backend 工程师、Godot 工程师

### 开发目标

建立 Backend 和 Godot Plugin 之间共同遵守的数据协议。

### 设计原则

1. 跨模块通信必须使用公开接口。
2. 不直接暴露内部 Repository。
3. 不通过隐式共享对象传递业务状态。
4. 协议需要版本号。
5. 协议需要统一错误格式。
6. 关键操作需要 Request ID 或 Correlation ID。
7. 事件必须具有唯一事件标识。

### 基础协议目录

```text
packages/contracts/
│
├── api/
├── events/
├── schemas/
├── errors/
├── common/
└── README.md
```

### 统一请求格式

```json
{
  "protocol_version": "1.0",
  "request_id": "request-unique-id",
  "timestamp": "2026-11-17T10:00:00Z",
  "session_id": "session-id",
  "action": "example.action",
  "payload": {}
}
```

### 统一响应格式

```json
{
  "protocol_version": "1.0",
  "request_id": "request-unique-id",
  "success": true,
  "data": {},
  "error": null
}
```

### 统一错误格式

```json
{
  "code": "ERROR_CODE",
  "message": "Human readable message",
  "details": {},
  "retryable": false,
  "correlation_id": "correlation-id"
}
```

### 本阶段需要定义的公共类型

- Request。
- Response。
- Error。
- Event。
- Event ID。
- Request ID。
- Correlation ID。
- Protocol Version。
- Timestamp。
- Session ID。
- Project ID。

这些是协议基础类型，不代表 E0 已经实现 Session 或 Project 业务系统。

### 交付物

- Contracts 目录。
- 基础 Schema。
- 请求和响应协议。
- 错误编码规范。
- 事件格式规范。

### 验收标准

Backend 和 Godot Plugin 能够分别读取、验证相同的协议样例。

## E0-T06：数据库和数据管理规范

**优先级：** P0  
**依赖：** E0-T02、E0-T03  
**负责角色：** Backend 工程师、数据工程师

### 开发目标

确定后续系统使用的数据存储基础规范。

### 已确定的基础原则

- SQLite 作为单一 Primary Database。
- WAL 模式。
- 短事务。
- Repository 按模块隔离。
- 数据库变更使用 Migration。
- 重要写入需要事务。
- 跨模块事件使用 Outbox/Inbox 机制。
- 消息投递采用 At-least-once，并通过幂等处理重复消息。

### 本阶段需要完成

1. 选择 SQLite 驱动。
2. 确定数据库文件存放规则。
3. 确定 Migration 目录结构。
4. 确定 Migration 命名规则。
5. 确定数据库备份策略。
6. 确定开发和测试数据库隔离方式。
7. 确定 Repository 编写规范。
8. 确定数据库升级失败的处理方式。

### Migration 规范

建议格式：

```text
000001_initial_schema
000002_add_xxx_table
000003_add_xxx_index
```

每个 Migration 应当：

- 有唯一版本。
- 可以记录执行状态。
- 能够检测重复执行。
- 能够检测升级失败。
- 有相应测试。
- 不允许无记录地手动修改生产数据库结构。

### 本阶段不做

不提前建立完整 Task、Workflow、Agent、Asset 等业务表。

这些数据模型由对应阶段负责。

### 交付物

- 数据库技术规范。
- Migration 机制设计。
- 数据备份和恢复规范。
- Repository 规范。

### 验收标准

工程具备执行数据库 Migration 的基础能力，并能在测试环境验证升级与失败处理。

## E0-T07：配置和 Secrets 管理体系

**优先级：** P0  
**依赖：** E0-T03  
**负责角色：** Backend 工程师、安全负责人

### 开发目标

建立统一配置管理体系，避免后续 API Key、密码和 Token 被写入数据库或代码。

### 配置分类

| 配置类型 | 示例 |
|---|---|
| 应用配置 | 服务名称、运行模式 |
| 网络配置 | 本地服务端口、通信地址 |
| 数据配置 | 数据库路径 |
| 日志配置 | 日志级别、日志目录 |
| 模型配置 | Provider 选择 |
| 安全配置 | Token、密钥、凭证 |

### 基础要求

1. 提供 `.env.example`。
2. 禁止提交真实 `.env`。
3. 禁止在代码中硬编码凭证。
4. 配置需要进行类型和范围验证。
5. 缺少必要配置时明确报错。
6. Secrets 与普通配置分离。
7. 优先使用操作系统 Credential Store。
8. 数据库不得保存明文凭证。

### 交付物

- 配置管理规范。
- Secrets 管理规范。
- 示例配置。
- 配置校验规范。

### 验收标准

代码仓库中不存在真实凭证，配置缺失和格式错误均能够被检测。

## E0-T08：统一日志和异常规范

**优先级：** P1  
**依赖：** E0-T03、E0-T04、E0-T05  
**负责角色：** Backend 工程师、Godot 工程师

### 开发目标

确保后续系统出现故障时能够定位问题。

### 日志字段

建议统一包含：

- Timestamp。
- Level。
- Component。
- Event。
- Request ID。
- Correlation ID。
- Session ID（可用时）。
- Project ID（可用时）。
- Error Code。
- Message。

### 日志级别

- DEBUG：调试信息。
- INFO：正常业务事件。
- WARNING：非致命异常。
- ERROR：操作失败。
- CRITICAL：系统关键故障。

### 异常处理原则

1. 业务异常和系统异常分开。
2. 不允许静默吞掉异常。
3. 对外错误信息不得泄露 Secrets。
4. 异常应保留关联 ID。
5. 重要操作需要记录执行结果。
6. 日志不得保存模型隐藏推理或不必要的敏感信息。

### 交付物

- 日志规范。
- 错误码规范。
- 异常处理规范。
- 日志脱敏规范。

### 验收标准

Backend 和 Godot Plugin 均具备统一的基础日志输出和错误记录能力。

## E0-T09：CI 与自动化工程检查

**优先级：** P1  
**依赖：** E0-T03、E0-T04、E0-T05  
**负责角色：** DevOps、Backend 工程师、Godot 工程师

### 开发目标

建立提交代码后的自动检查机制。

### CI 基础流程

```text
代码提交
   ↓
仓库结构检查
   ↓
代码格式检查
   ↓
静态检查
   ↓
Backend 基础测试
   ↓
Godot Plugin 基础检查
   ↓
Contracts Schema 检查
   ↓
生成检查报告
```

### 本阶段 CI 要求

- 检查代码格式。
- 检查基础语法。
- 执行 Backend 基础测试。
- 执行 Godot 项目基础检查。
- 检查协议 Schema。
- 检查敏感文件是否被提交。
- 保存测试结果。

### 后续扩展

E1–E12 逐步增加：

- 数据库测试。
- API 契约测试。
- Editor Bridge 测试。
- Agent Runtime 测试。
- 多 Agent 集成测试。
- 资源导入测试。
- 游戏 E2E 测试。
- 导出和发布测试。

### 交付物

- CI 配置。
- 自动化检查脚本。
- 测试报告。
- CI 使用说明。

### 验收标准

一次正常代码提交能够触发完整的 E0 自动检查流程，检查失败能够阻止不合格代码合并。

# 5. E0 测试实施计划

## 5.1 单元测试

| 测试编号 | 测试内容 | 预期结果 |
|---|---|---|
| E0-UT-001 | Backend 工程启动 | 正常启动 |
| E0-UT-002 | 配置加载 | 正确读取配置 |
| E0-UT-003 | 配置缺失 | 明确报错 |
| E0-UT-004 | 日志输出 | 格式符合规范 |
| E0-UT-005 | 错误格式 | 返回统一错误结构 |
| E0-UT-006 | Contracts Schema | 合法数据通过验证 |
| E0-UT-007 | 非法协议数据 | 验证失败 |
| E0-UT-008 | Migration 执行 | 成功创建版本记录 |
| E0-UT-009 | Migration 重复执行 | 不重复破坏数据 |
| E0-UT-010 | Secrets 检查 | 不允许明文凭证进入代码仓库 |

## 5.2 集成测试

| 测试编号 | 测试内容 | 预期结果 |
|---|---|---|
| E0-IT-001 | Backend 工程整体启动 | 正常运行 |
| E0-IT-002 | Godot Plugin 安装 | 安装成功 |
| E0-IT-003 | Godot Plugin 启用 | 正常启用 |
| E0-IT-004 | Godot Plugin 关闭 | 正常释放资源 |
| E0-IT-005 | Backend 与 Plugin 协议样例验证 | 双方解析一致 |
| E0-IT-006 | CI 流程 | 自动检查成功 |
| E0-IT-007 | Migration 升级失败模拟 | 能够发现并报告失败 |
| E0-IT-008 | 日志敏感信息检查 | 不输出真实 Secrets |

## 5.3 故障注入测试

必须至少验证：

1. 配置文件不存在。
2. 配置格式错误。
3. 数据库文件无法创建。
4. 数据库文件不可写。
5. Migration 执行失败。
6. CI 某项检查失败。
7. Godot 插件重复启用。
8. Godot 插件初始化过程中出现异常。

测试目标是验证错误能够被发现、记录和安全处理，而不是要求所有异常都自动恢复。

# 8. E0 风险与注意事项

| 风险编号 | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| E0-R01 | 技术栈选型不合理 | 后续返工 | E0 进行技术评审 |
| E0-R02 | 模块边界不清 | 形成循环依赖 | 提前冻结模块依赖规则 |
| E0-R03 | Backend 与 Plugin 协议不统一 | 集成困难 | 先建立 Shared Contracts |
| E0-R04 | 配置和凭证管理混乱 | 安全风险 | 从 E0 建立 Secrets 规范 |
| E0-R05 | 工程结构过度复杂 | 增加开发成本 | 先建立最小可运行结构 |
| E0-R06 | 缺少自动化检查 | 问题积累 | E0 建立 CI 基础门禁 |

# 9. E0 阶段结束后的下一阶段条件

E0 验收通过后，允许进入 E1。

E1 将在 E0 的工程骨架上正式实现 Backend Core，包括：

- Backend 生命周期管理。
- 应用启动和关闭。
- 配置服务。
- 数据库服务。
- Migration 执行器。
- 日志服务。
- 事件基础设施。
- 异常处理机制。
- 基础健康检查。
- 数据库备份基础能力。

**E0 的最终目标不是做出一个功能丰富的产品，而是建立一套不会阻碍后续开发、能够长期扩展和维护的工程基础。**
