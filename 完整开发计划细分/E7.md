# 1. 阶段概述

## 1.1 阶段目标

E7 的目标是在 E6 单 Agent Runtime 的基础上，建立完整的多 Agent 协作系统，并实现第一批真正面向 Godot 游戏开发的专业 Agent。

E6 解决的是：

> 一个 Agent 如何可靠地执行任务？

E7 解决的是：

> 多个不同专业的 Agent 如何围绕同一个游戏项目分工、协作、交接、并行工作，并最终交付一致的游戏开发结果？

完成 E7 后，系统应当具备：

1. Multi-Agent Orchestrator。
2. Agent Capability Registry。
3. Agent Assignment。
4. Agent Team Management。
5. Agent Handoff。
6. Agent Collaboration。
7. Lead Agent。
8. Specialized Agent Definitions。
9. Agent Parallel Execution。
10. Inter-Agent Communication。
11. Shared Task Context。
12. Agent Conflict Detection。
13. Resource Coordination。
14. Agent Result Integration。
15. Agent Team Observability。
16. 基础游戏设计 Agent。
17. 基础游戏程序开发 Agent。
18. 基础 Godot Scene、Node、Inspector、TileMap 专业 Agent。
19. 基础 QA Agent。
20. Platformer Demo 所需的第一批专业 Agent。

## 1.2 本阶段最终目标

系统能够接受一个具有多个子目标的游戏开发任务，例如：

“创建一个 2D 平台跳跃游戏，包含玩家移动、跳跃、敌人、关卡、生命系统和 HUD。”

Orchestrator 能够：

1. 分析任务目标。
2. 识别所需专业能力。
3. 选择合适的 Agent。
4. 创建 Agent Team。
5. 分配子任务。
6. 管理依赖关系。
7. 允许无依赖任务并行执行。
8. 管理 Agent Handoff。
9. 协调共享资源。
10. 汇总各专业 Agent 的结果。
11. 处理不同 Agent 之间的冲突。
12. 将集成结果提交 Verification System。
13. 根据验证结果决定返工或完成。
14. 向用户提供可追踪的开发进度。

## 1.3 本阶段明确不实现

E7 不负责：

- 完整 Asset Generation Pipeline。
- 图片、音频、视频生成服务的完整管理。
- 完整 QA 自动化平台。
- 完整 Build、Export、Release。
- 云端 Agent 集群调度。
- 不受控制的自主 Agent 网络。
- Agent 自行创建 Agent。
- Agent 之间绕过 Orchestrator 直接委派。
- 38 个专业 Agent 的全部高级能力。

E7 建立专业 Agent 的基础定义和可用能力。E8 以后逐步补齐资产、QA 和交付能力。

## 2.2 架构冻结规则

### G01：Orchestrator 是唯一 Agent 分配入口

所有 Agent Assignment 必须由 Multi-Agent Orchestrator 发起。

禁止：

- Agent 自行选择其他 Agent 并创建实例。
- Agent 直接向另一个 Agent 发送任务。
- Agent 绕过 Orchestrator 修改 Assignment。
- Lead Agent 绕过 Orchestrator 创建新的专业 Agent。

Agent 可以提出 Handoff Request，但必须由 Orchestrator 审核和执行。

### G02：Agent 不拥有 Task 状态

Task System 仍然是 Task 状态唯一权威。

Orchestrator 管理的是：

- Agent Team。
- Assignment。
- Handoff。
- Collaboration。
- Integration Status。

Agent Runtime 管理 Agent Instance 和 Execution。

Workflow Engine 管理 Workflow、Phase 和 Node。

Verification System 管理验证结果。

### G03：权限与能力必须分开

Capability 表示 Agent 能做什么。

Permission 表示 Agent 被允许做什么。

具备某项能力不代表自动获得对应权限。

### G04：Lead Agent 不自动拥有写权限

Lead Agent 负责：

- 需求协调。
- 子任务分解。
- 结果整合。
- 冲突协调。
- 验收材料整理。

Lead Agent 不因为拥有 Lead 角色而获得额外项目写权限。

所有写入仍然通过 Tool System、Permission System 和 Approval System。

### G05：多 Agent 共享 Context，但不共享可变执行状态

Agent 可以共享：

- 项目事实。
- 需求。
- 接口定义。
- 设计决策。
- 任务依赖。
- 已批准的变更记录。

Agent 不得直接共享：

- 内部可变执行状态。
- 未提交的私有计划。
- 未授权的临时数据。
- 其他 Agent 的权限。
- 其他 Agent 的隐藏推理。

### G06：Resource Lock 和 Fencing Token

并行 Agent 访问同一项目资源时必须有资源协调机制。

资源锁必须具备：

- Owner。
- Resource ID。
- Lease。
- Fencing Token。
- Expiration。
- Recovery State。

旧 Agent 即使恢复运行，也不能使用已经过期的 Fencing Token 修改资源。

### Godot 专业能力

- resource_management
- editor_automation

### 美术与内容

- 2d_art_creation
- 2d_technical_art

- vfx_creation
- asset_pipeline_management

### 质量与交付

- qa_testing
- test_automation
- project_planning
- build_release

## Capability Metadata

每项能力应描述：

- 能力目标。
- 输入格式。
- 输出格式。
- 依赖能力。
- 所需 Tool。
- 所需 Model Capability。
- 风险级别。
- 验证方法。
- 版本。

## 能力匹配规则

Agent 候选筛选分为两阶段：

第一阶段：硬性过滤。

- Agent 是否启用。
- 是否拥有所需 Capability。
- 是否拥有所需权限。
- Tool 是否可用。
- Model 是否满足要求。
- Project 是否可访问。
- Budget 是否足够。

第二阶段：软性排序。

- Capability 匹配度。
- 专业方向。
- 历史任务成功率。
- 当前负载。
- 模型能力。
- 预计成本。
- 预计完成时间。

软性评分不能覆盖硬性权限限制。

## 测试

- 能力不存在。
- Agent 已停用。
- Tool 不可用。
- Model 能力未知。
- 权限不足。
- 多个候选 Agent 排序。
- 高负载 Agent 被合理降权。

# 7. E7-T03 Multi-Agent Orchestrator Core

**优先级：P0**  
**依赖：E7-T01、E7-T02、E6**

## 目标

建立多 Agent 的唯一调度和协调入口。

## Orchestrator 职责

1. 接收 Task System 授权。
2. 获取 Task 和 Acceptance Criteria。
3. 分析任务复杂度。
4. 判断是否需要多 Agent。
5. 分解子任务。
6. 查询 Capability Registry。
7. 选择专业 Agent。
8. 创建 Agent Team。
9. 创建 Assignments。
10. 管理依赖。
11. 启动 Agent Runtime。
12. 监控 Assignment。
13. 接收 Handoff Request。
14. 处理执行冲突。
15. 汇总结果。
16. 组织 Lead Agent Integration。
17. 提交 Verification。

## Orchestrator 工作流程

```text
Task System Authorization
          |
          v
Task Analysis
          |
          v
Complexity Assessment
          |
          v
Task Decomposition
          |
          v
Capability Matching
          |
          v
Permission Filtering
          |
          v
Agent Team Creation
          |
          v
Assignment Creation
          |
          v
Dependency Planning
          |
          v
Agent Runtime Execution
          |
          v
Progress Monitoring
          |
          v
Handoff / Replanning
          |
          v
Lead Integration
          |
          v
Verification
          |
          v
Task System
```

## 单 Agent 与多 Agent 决策

Orchestrator 不应把所有任务都拆分成多个 Agent。

以下情况优先使用单 Agent：

- 简单问题。
- 单文件修改。
- 单一技术分析。
- 无明显专业分工。
- 并行没有收益。
- 多 Agent 成本高于预期收益。

以下情况适合多 Agent：

- 多专业工作。
- 多个互相独立的子目标。
- 需要独立验证。
- 需要设计、程序、美术等不同角色。
- 任务可以安全并行。

## 关键规则

Orchestrator 只能创建由 Task System 授权范围内的 Assignment。

拆分任务不得改变原始 Task 的目标和验收标准。

如果需要改变目标，必须回到 Task System 和用户确认流程。

# 9. E7-T05 Agent Task Decomposition

**优先级：P0**  
**依赖：E7-T03、E4**

## 目标

把复杂游戏开发任务拆分为可执行的子任务。

## 分解结果

每个 Assignment 必须具有：

- Objective。
- Scope。
- Input。
- Output。
- Acceptance Criteria。
- Required Capability。
- Required Tools。
- Dependencies。
- Permission Requirements。
- Budget。
- Estimated Duration。
- Risk Level。

## 分解示例

原始任务：

“创建一个 2D 平台跳跃游戏。”

Orchestrator 可以拆分为：

```text
A. 游戏整体设计
       |
       +----> B. 核心玩法设计
       |
       +----> C. 玩家控制系统
       |
       +----> D. 关卡结构设计
       |
       +----> E. UI/HUD 设计
       |
       +----> F. 敌人行为设计
       |
       v
G. 技术架构整合
       |
       v
H. 场景与资源整合
       |
       v
I. QA 验证
```

## 依赖关系

例如：

- 玩家控制系统依赖核心玩法设计。
- 关卡结构依赖 TileMap 方案。
- HUD 依赖游戏状态和生命系统接口。
- QA 依赖可运行的集成版本。

## 验收标准

- 子任务目标清晰。
- 子任务有可验证结果。
- 依赖关系无循环。
- 子任务范围不冲突。
- 子任务覆盖原始 Acceptance Criteria。

# 10. E7-T06 Agent Assignment Manager

**优先级：P0**  
**依赖：E7-T02、E7-T05**

## 目标

管理 Agent 与子任务之间的分配关系。

## Assignment 状态

- CREATED
- READY
- ASSIGNED
- STARTING
- RUNNING
- WAITING
- HANDOFF_PENDING
- INTEGRATING
- COMPLETED
- FAILED
- CANCELLED
- BLOCKED
- UNKNOWN

## Assignment 规则

1. 一个 Assignment 只允许一个当前执行负责人。
2. 同一个 Assignment 不得被两个 Agent 同时独立写入。
3. 需要重新分配时，必须先处理原 Assignment。
4. 原 Agent 尚有未完成 Tool Execution 时，不允许直接替换。
5. Assignment 必须绑定 Task 和 Attempt。
6. Assignment 不能改变 Task 状态。
7. Assignment 的成功需要符合自身 Acceptance Criteria。

## 失败处理

Agent 失败时：

1. 记录失败。
2. 保留已有结果。
3. 判断是否可重试。
4. 判断是否需要新 Agent。
5. 由 Orchestrator 决定是否重新分配。
6. 保留旧 Assignment 历史。

不能通过删除失败 Assignment 来隐藏失败记录。

# 11. E7-T07 Agent Handoff Manager

**优先级：P0**  
**依赖：E7-T03、E7-T06、E6**

## 目标

建立受控的 Agent 工作交接机制。

## Handoff 类型

- ROLE_HANDOFF：不同专业角色之间交接。
- TASK_HANDOFF：子任务负责人更换。
- REVIEW_HANDOFF：交给其他 Agent 审查。
- INTEGRATION_HANDOFF：交给 Lead Agent 集成。
- FAILURE_HANDOFF：失败后交给其他 Agent 处理。

## Handoff Payload

必须包括：

- 原始目标。
- 当前工作范围。
- 已完成工作。
- 未完成工作。
- 关键发现。
- 项目文件引用。
- ChangeSet 引用。
- 设计决策。
- 已知风险。
- 失败原因。
- 下一步建议。
- 验收标准。
- Context Snapshot Reference。

不得直接传递隐藏推理。

## Handoff 流程

```text
Source Agent
     |
     v
Handoff Request
     |
     v
Orchestrator Validation
     |
     v
Validate Target Capability
     |
     v
Validate Permission
     |
     v
Validate Context
     |
     v
Create Target Assignment
     |
     v
Create New Agent Instance
     |
     v
Transfer Approved Context
     |
     v
Target Agent Acknowledgement
     |
     v

```

## 关键规则

- Agent 只能提出 Handoff Request。
- Orchestrator 才能执行 Handoff。
- 目标 Agent 必须重新进行权限校验。
- 原 Agent 权限不能自动转移。
- 原 Agent 的未完成 Tool Execution 必须先处理。
- Handoff 必须记录完整审计事件。

# 14. E7-T10 Parallel Execution Manager

**优先级：P1**  
**依赖：E7-T03、E7-T06、E7-T09**

## 目标

支持多个 Agent 并行执行互不冲突的任务。

## 并行条件

满足以下条件才允许并行：

1. Assignment 依赖已经满足。
2. 项目资源访问范围明确。
3. 资源锁允许并行。
4. Tool Permission 有效。
5. Team Budget 足够。
6. 不存在不可接受的写入冲突。
7. Task/Attempt 仍然有效。

## 并行执行模型

```text
               Orchestrator
                    |
          +---------+---------+
          |         |         |
          v         v         v
       Agent A   Agent B   Agent C
          |         |         |
          v         v         v
       Output A  Output B  Output C
          |         |         |
          +---------+---------+
                    |
                    v
              Lead Agent
                    |
                    v
                Integration
```

## 并行策略

支持：

- Read Parallelism。
- Independent Write Parallelism。
- Sequential Dependency。
- Bounded Concurrency。

禁止：

- 未经资源协调的共享文件写入。
- 两个 Agent 同时修改同一 Scene。
- 两个 Agent 同时修改同一 Script。
- 两个 Agent 同时修改相互关联的 Project Settings。

## 失败隔离

一个 Agent 失败时：

- 不应自动终止所有无关 Agent。
- 需要判断失败是否影响其他 Assignment。
- 对依赖失败结果的 Assignment 标记 BLOCKED。
- 由 Orchestrator 决定是否重新规划。

# 15. E7-T11 Resource Coordination & Conflict Resolution

**优先级：P0**  
**依赖：E4、E6、E7-T10**

## 目标

解决多个 Agent 同时访问项目资源时产生的冲突。

## 资源类型

- Project File。
- Scene。
- Script。
- Resource。
- Project Settings。
- Input Map。
- Asset。
- TileSet。
- Animation。
- Shared Interface。
- Database Resource。

## 冲突类型

- WRITE_WRITE。
- READ_WRITE。
- STALE_CONTEXT。
- SCHEMA_CONFLICT。
- INTERFACE_CONFLICT。
- CHANGESET_CONFLICT。
- RESOURCE_LOCK_CONFLICT。

## 资源协调规则

### 文件级协调

多个 Agent 修改不同文件时，允许在其他条件满足时并行。

### Scene 级协调

同一个 Scene 默认只允许一个活动写入者。

### Project Settings 协调

Project Settings 采用受控写入，避免多个 Agent 同时修改。

### 接口协调

共享接口变更必须经过 Integration Manager。

### ChangeSet 协调

多个 ChangeSet 修改相同资源时，必须进行冲突检测。

## 冲突处理流程

```text
Conflict Detected
       |
       v
Freeze Conflicting Assignment
       |
       v
Collect Current Resource State
       |
       v
Compare ChangeSets
       |
       v
Classify Conflict
       |
       v
Choose Resolution Strategy
       |
       +----> Sequential Execution
       |
       +----> Rebase
       |
       +----> Merge Proposal
       |
       +----> Reassign
       |
       +----> User Decision
```

## 安全要求

- 不允许 Agent 直接覆盖其他 Agent 的变更。
- 不允许通过强制写入绕过 Resource Lock。
- 旧 Fencing Token 必须拒绝。
- 冲突未解决前不能继续相关写入。

# 21. E7-T17 Agent Conflict Resolution

**优先级：P1**  
**依赖：E7-T11、E7-T15**

## 目标

处理专业 Agent 之间的设计和实现冲突。

## 冲突示例

- 游戏设计要求与技术限制冲突。
- 玩家控制接口与动画接口冲突。
- UI 设计与现有 Scene 结构冲突。
- TileMap 结构与碰撞方案冲突。
- 两个 Agent 修改同一个 Script。
- 不同 Agent 提交互相不兼容的 ChangeSet。

## 解决流程

1. 发现冲突。
2. 创建 Conflict Record。
3. 暂停相关 Assignment 的冲突操作。
4. 收集双方输入和证据。
5. 判断冲突类型。
6. 根据规则选择技术协调方案。
7. 必要时请求 Lead Agent 协调。
8. 必要时请求用户决定。
9. 更新相关 Context。
10. 重新验证。

## 重要规则

- Lead Agent 不得擅自改变用户确认的需求。
- 设计冲突如果影响用户目标，必须请求用户确认。
- 技术冲突必须保留决策记录。
- 不能简单采用最后写入者获胜。

# 28. 安全与权限测试

必须验证：

1. Agent 无法绕过 Orchestrator 创建 Assignment。
2. Agent 无法自行创建其他 Agent Instance。
3. Lead Agent 无法自动获得写权限。
4. Agent 不能把自己的权限转交给另一个 Agent。
5. Handoff 后目标 Agent 必须重新授权。
6. Agent 不能访问其他 Project。
7. Agent 不能修改其他 Assignment 的状态。
8. Agent 不能绕过 Resource Lock。
9. 旧 Fencing Token 无法执行写入。
10. Agent Message 不能直接触发越权工具调用。
11. 未授权 Agent 无法获取 Team Context。
12. Team Budget 不得突破 Task Budget。
13. Assignment 不能改变原 Task 的验收标准。
14. Lead Agent 不能自动批准 ChangeSet。
15. 未验证结果不能被标记为已验收。

# 33. 主要风险与处理策略

| 风险 | 后果 | 处理 |
|---|---|---|
| Agent 自行委派 | 权限和任务失控 | Orchestrator 唯一分配入口 |
| Assignment 范围不清 | 重复工作 | 明确 Objective 和 Acceptance Criteria |
| 多 Agent 并行写入 | 项目损坏 | Resource Lock + Fencing Token |
| Context 不一致 | 结果冲突 | Shared Context Version |
| Lead Agent 权限过大 | 越权修改 | Lead 角色不自动授予写权限 |
| Handoff 信息缺失 | 重复分析和执行 | 标准 Handoff Payload |
| Agent 互相传递错误事实 | 错误传播 | FACT/INFERENCE 分离和来源记录 |
| Team Budget 超限 | 成本失控 | Task Budget 硬限制 |
| Agent 失败影响全队 | 不必要的整体失败 | Assignment 隔离 |
| Agent 结果无法集成 | 返工 | Integration Contract |
| 专业 Agent 能力虚假声明 | 错误调度 | Capability Evidence 和验收测试 |

# 36. 最终阶段目标

E7 的真正完成标志不是系统能够同时启动多个 Agent，而是：

**多个具有明确专业能力、独立权限、明确任务边界和可验证交付标准的 Agent，能够由 Orchestrator 统一协调，在共享项目 Context 的基础上安全分工、并行执行、交接、处理冲突，并由 Lead Agent 整合为一致的游戏开发结果。**

当这一能力通过真实 Godot Platformer Demo 验证后，系统才真正具备从单 Agent 工具执行系统向多专业 Agent 游戏开发团队演进的基础。
