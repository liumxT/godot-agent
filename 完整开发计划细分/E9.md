# 1. 阶段概述

## 1.1 阶段目标

E9 的目标是建立独立于 Agent 执行系统的完整质量验证体系。

E0–E8 已经建立：

- Backend 基础设施。
- API 和权限。
- Godot Editor Integration。
- Project 和 Workflow。
- AI Model Gateway。
- Tool System。
- Agent Runtime。
- Multi-Agent 协作。
- Asset Pipeline。

但这些系统能够执行任务，并不代表执行结果一定正确。

例如：

- Agent 声称玩家已经可以跳跃，但实际运行时跳跃失效。
- Agent 声称敌人已经完成巡逻，但敌人实际上卡在墙边。
- Agent 声称 UI 已经完成，但分辨率变化后 UI 错位。
- Agent 声称资源已经导入，但 Godot 实际导入失败。
- Agent 声称没有错误，但 Debugger 中存在运行时异常。
- Agent 声称测试通过，但测试实际上没有执行。
- Agent 修改了场景，却破坏了原有信号连接。
- Agent 修复了一个 Bug，却导致其他功能回归失败。

E9 必须建立一套独立的验证机制，确保：

1. 需求有明确验收标准。
2. 每项需求都有对应验证方法。
3. 验证过程真实执行。
4. 验证结果有证据。
5. 失败结果能够生成缺陷。
6. 缺陷修复后必须重新验证。
7. 变更必须执行影响分析。
8. Agent 不能自行宣布任务成功。
9. Verification System 不能直接修改 Task 状态。
10. Phase Review 必须经过用户验收。

## 1.2 核心设计原则

**Verification 是独立的质量判定系统，不是 Agent 的自我评价模块。**

以下规则必须冻结：

- Agent 可以提交验证请求。
- Agent 可以提供验证计划。
- Agent 可以提交自测结果。
- Agent 不拥有最终 Verification Result。
- Verification System 拥有验证结果状态。
- Task System 拥有 Task 状态。
- Workflow Engine 拥有 Workflow、Phase、Node 状态。
- Approval System 拥有审批状态。
- ChangeSet Manager 拥有变更状态。
- Verification System 不直接修改 Task 状态。
- Agent 不能自行宣布 Task 成功。
- 用户验收与机器测试通过是两个不同条件。

## 1.3 E9 完成后的能力

用户可以提出：

“完成 Platformer Demo 的玩家移动、跳跃和攻击系统。”

系统应当：

1. 从需求中提取验收标准。
2. 建立需求与测试之间的追踪关系。
3. 分析涉及的 Scene、Node、Script 和 Resource。
4. 制定静态检查、结构检查、运行测试和交互测试计划。
5. 执行 Godot 项目检查。
6. 启动游戏并执行测试。
7. 收集 Debugger 日志。
8. 检查游戏运行结果。
9. 记录截图、日志和测试报告。
10. 判断是否满足验收标准。
11. 失败时创建 Defect。
12. 将缺陷交给对应 Agent 修复。
13. 修复后重新执行相关测试。
14. 完成 Regression Test。
15. 生成 Phase Review Report。
16. 等待用户验收。

# 5. 详细开发任务

# E9-T01 Verification Domain & Contract

**优先级：P0**

## 5.1 目标

建立独立的 Verification 领域模型。

Verification 不应只是 Task 上的一个布尔字段。

例如：

```text
verified = true
```

这种设计无法表达：

- 哪些需求通过。
- 哪些测试执行过。
- 哪些测试没有执行。
- 哪些结果不确定。
- 哪些证据失效。
- 哪些缺陷尚未修复。
- 哪些验证需要重新执行。

- 结果能够追踪到需求。
- 结果能够追踪到证据。
- UNKNOWN 与 FAILED 分离。

# E9-T02 Requirement Traceability

**优先级：P0**

## 6.1 目标

建立需求到实现、测试和验收证据的追踪关系。

## 6.2 追踪链

```text
Requirement
    |
    v

    |
    v

    |
    v

    |
    v
ChangeSet
    |
    v
Implementation
    |
    v
Test Case
    |
    v
Verification Run
    |
    v
Evidence
    |
    v
Verification Result
```

## 6.3 需求来源

支持：

- 用户需求。
- Game Design。
- Gameplay Design。
- Technical Design。
- Bug Fix Requirement。
- Performance Requirement。
- UI/UX Requirement。
- Asset Requirement。
- Security Requirement。

## 6.4 追踪规则

每项正式需求必须具有：

- Requirement ID。
- 描述。
- 来源。
- 优先级。
- 验收标准。
- 关联 Workflow。
- 关联 Task。
- 关联 ChangeSet。
- 关联 Test Case。
- 最终验证结果。

## 6.5 覆盖率指标

需求测试覆盖率：

\[
Coverage =
\frac{Requirements\ with\ Valid\ Tests}
{Total\ Testable\ Requirements}
\times 100\%
\]

验证通过率：

\[
PassRate =
\frac{Passed\ Executed\ Tests}
{All\ Executed\ Tests}
\times 100\%
\]

未执行测试不能被计入通过。

## 6.6 关键规则

需求被修改后：

1. 创建新的需求版本。
2. 计算受影响的验收标准。
3. 识别受影响的测试。
4. 使旧验证结果进入待复核状态。
5. 必要时重新执行测试。

不能让旧测试结果自动覆盖新的需求版本。

## 6.7 验收标准

- 所有正式需求有 ID。
- 可查询需求覆盖情况。
- 可以追踪到测试和证据。
- 需求修改能够触发影响分析。

# E9-T03 Acceptance Criteria Registry

**优先级：P0**

## 7.1 目标

将自然语言需求转换为可判定的验收标准。

## 7.2 验收标准类型

### Functional Criteria

例如：

- 玩家可以移动。
- 玩家可以跳跃。
- 玩家受到伤害后生命值减少。
- 玩家死亡后能够重生。

### Structural Criteria

例如：

- Player 场景包含 CharacterBody2D。
- 玩家具有 CollisionShape2D。
- 攻击系统具有对应状态。
- UI 使用独立场景。

### Runtime Criteria

例如：

- 游戏可以正常启动。
- 玩家可以在运行时移动。
- 敌人能够巡逻。
- 游戏暂停后物理模拟停止。

### Visual Criteria

例如：

- 角色动画显示正确。
- HUD 不超出屏幕。
- UI 在指定分辨率下布局正常。

### Performance Criteria

例如：

- 在指定测试环境中保持目标帧率。
- 场景切换时间低于设定阈值。
- 内存使用量不超过项目预算。

### Security Criteria

例如：

- 未授权工具调用被拒绝。
- 跨项目资源访问被拒绝。
- 未审批的项目写入被阻止。

## 7.3 验收标准 Contract

```text
AcceptanceCriterion
- id
- requirement_id
- version
- criterion_type
- description
- verification_method
- expected_value
- tolerance
- severity
- mandatory
- automation_level
- evidence_requirements
```

## 7.4 可验证性

每条标准必须明确：

- 验证方法。
- 预期结果。
- 允许误差。
- 所需证据。
- 失败等级。

无法自动验证的标准必须明确标记为人工验收。

## 7.5 验收标准

- 每项需求至少有一条验收标准。
- 每条标准有验证方法。
- 每条标准有预期结果。
- 不可自动验证的内容必须标记。
- 验收标准变更可以追踪版本。

# E9-T04 Verification Plan Engine

**优先级：P0**

## 8.1 目标

根据需求、变更范围和风险自动生成验证计划。

## 8.2 输入

- Requirement。
- Acceptance Criteria。
- Task。
- ChangeSet。
- Scene Dependency。
- Asset Dependency。
- Historical Defects。
- Test Environment。
- Project Configuration。

## 8.3 计划生成步骤

1. 读取需求。
2. 获取验收标准。
3. 读取 ChangeSet。
4. 分析文件和资源变化。
5. 查询依赖图。
6. 识别风险。
7. 选择验证层级。
8. 选择测试用例。
9. 确定环境。
10. 确定证据要求。
11. 生成 Verification Plan。

## 8.4 风险分级

```text
LOW
MEDIUM
HIGH
CRITICAL
```

示例：

| 变更 | 风险 |
|---|---|
| 修改普通 UI 文本 | LOW |
| 修改 HUD 布局 | MEDIUM |
| 修改玩家移动逻辑 | HIGH |
| 修改存档系统 | HIGH |
| 修改核心场景加载机制 | CRITICAL |
| 修改权限和文件写入安全 | CRITICAL |

## 8.5 验证范围策略

- LOW：针对性测试。
- MEDIUM：针对性测试 + 依赖测试。
- HIGH：完整相关功能测试 + 回归测试。
- CRITICAL：完整回归测试 + 安全或专项审查。

## 8.6 验收标准

- 每个 ChangeSet 可以生成验证计划。
- 计划包含风险分析。
- 测试范围可追踪。
- 测试环境明确。
- 验证计划支持人工调整。
- 计划版本不可被静默覆盖。

# E9-T05 Verification Orchestrator

**优先级：P0**

## 9.1 目标

统一协调所有验证执行。

## 9.2 模块职责

- 创建 Campaign。
- 加载 Plan。
- 分配 Test Run。
- 管理执行队列。
- 选择执行器。
- 管理超时。
- 收集结果。
- 收集证据。
- 处理失败。
- 处理 UNKNOWN。
- 汇总 Verification Result。

## 9.3 执行器类型

```text
STATIC_ANALYZER
SCENE_VALIDATOR
RESOURCE_VALIDATOR
RUNTIME_TEST_RUNNER
FUNCTIONAL_TEST_RUNNER
VISUAL_TEST_RUNNER
PERFORMANCE_TEST_RUNNER
SECURITY_TEST_RUNNER
MANUAL_REVIEWER
```

## 9.4 状态

```text
CREATED
  |
  v
PLANNED
  |
  v
READY
  |
  v
RUNNING
  |
  +----> PASSED
  |
  +----> FAILED
  |
  +----> PARTIAL
  |
  +----> BLOCKED
  |
  +----> UNKNOWN
  |
  +----> CANCELLED
```

## 9.5 并发控制

允许无依赖关系的测试并行执行。

以下情况需要串行：

- 共用同一 Godot Editor Session。
- 共用同一 Runtime Instance。
- 修改相同项目文件。
- 使用相同的可变测试数据。
- 依赖同一个临时资源。

必须通过 Resource Lock 和测试环境隔离避免互相干扰。

## 9.6 验收标准

- 多测试并发调度。
- 支持串行依赖。
- 支持超时。
- 支持取消。
- 支持断线恢复。
- 支持 UNKNOWN。
- 测试结果不可由 Agent 直接覆盖。

# E9-T06 Static Analysis

**优先级：P0**

## 10.1 目标

建立 Godot 项目的静态分析能力。

## 10.2 检查范围

### GDScript

- 语法错误。
- 类型错误。
- 未定义变量。
- 未定义函数。
- 无效引用。
- 不合理的信号连接。
- 可疑的空引用。
- 不可达代码。
- 资源路径错误。
- 危险文件操作。
- 项目编码规范。

### Project Configuration

- project.godot 配置。
- Main Scene。
- Autoload。
- Input Map。
- Rendering 设置。
- Physics 设置。
- Feature Tags。

### Scene 和 Resource

- 场景文件是否可以解析。
- Resource Path 是否存在。
- External Resource 是否有效。
- SubResource 引用是否完整。
- UID 引用是否有效。

## 10.3 检查方式

优先使用 Godot 自身能够提供的解析、编辑器检查和命令行检查能力。

静态分析器可以提供额外规则，但不能取代 Godot 实际解析。

## 10.4 输出

```text
StaticAnalysisResult
- project_id
- analyzed_revision
- godot_version
- analyzer_version
- diagnostics
- severity
- file_path
- line_number
- rule_id
- evidence_id
```

## 10.5 验收标准

- 能发现 GDScript 语法错误。
- 能发现无效资源路径。
- 能检查项目配置。
- 能生成结构化诊断。
- 结果可追踪到项目版本。
- 不会因为旧诊断自动判定新版本失败。

# E9-T07 Scene & Resource Validation

**优先级：P0**

## 11.1 目标

验证 Godot 场景、节点、资源和引用关系。

## 11.2 Scene Validation

检查：

- Scene 是否存在。
- Root Node 类型。
- Node 层级。
- Node Name。
- Node Path。
- Script Attachment。
- Signal Connection。
- Group。
- Collision。
- Animation Player。
- SpriteFrames。
- TileSet。
- TileMapLayer。
- Resource Reference。

## 11.3 Resource Validation

检查：

- 资源文件存在。
- Godot UID 有效。
- Resource Type 正确。
- Import Status 正常。
- 引用关系完整。
- 资源未损坏。
- 资源版本符合预期。

## 11.4 Editor State

必须区分：

- Disk State。
- Editor State。
- Runtime State。

当 Editor 有未保存修改时，验证器必须明确当前验证基于哪一个状态。

不能把磁盘上的旧版本误认为当前 Editor 中的最新状态。

## 11.5 未保存修改处理

如果验证需要依赖未保存的 Editor State：

1. 查询 Editor 状态。
2. 获取相关 Scene 和 Resource 状态。
3. 标记验证快照。
4. 对可能存在冲突的操作进行限制。
5. 必要时请求用户保存或确认。

## 11.6 验收标准

- 能验证 Scene 结构。
- 能检查资源引用。
- 能识别 UID 问题。
- 能检查 Signal。
- 能识别未保存修改。
- 结果关联实际验证快照。

- 所有强制验收标准通过。

## 20.5 验收标准

- 门禁失败阻止后续流程。
- 豁免有独立审批。

```text
             Recovery
```

## 23.4 Agent Budget

验证也必须受预算控制：

- Test Run Budget。
- Runtime Time Budget。
- Screenshot Budget。
- Video Capture Budget。
- Retry Budget。
- Regression Budget。

禁止 Agent 无限重复测试。

## 23.5 验收标准

- Agent 能发起验证。
- Agent 能读取结果。
- 结果由 Verification System 管理。
- 缺陷通过 Orchestrator 分配。
- 修复后重新验证。
- Agent 不能控制最终质量判定。

- 证据失效必须保留历史。
- 用户敏感数据不应进入无关截图和日志。

# 18. 最终架构冻结规则

E9 实施期间不得破坏以下规则：

1. Verification 独立于 Agent。
2. Verification Result 由 Verification System 唯一管理。
3. Task 状态由 Task System 管理。
4. Workflow 状态由 Workflow Engine 管理。
5. Agent 不能自行宣布成功。
6. 测试通过必须有真实执行记录。
7. 正式通过结果必须有有效证据。
8. UNKNOWN 不等于 PASSED。
9. SKIPPED 不等于 PASSED。
10. 需求变更必须重新评估验证范围。
11. ChangeSet 变更必须触发影响分析。
12. 缺陷修复必须执行回归测试。
13. 质量门禁不能由 Agent 自行绕过。
14. 证据不能被静默删除。
15. 用户验收必须独立进行。
16. Phase ACCEPTED 后才能进入下一阶段。
17. 所有验证执行必须有权限和审计记录。
18. 所有验证结果必须关联项目版本和测试环境。

**E9 的最终目标，是让系统不仅能够开发游戏，还能够用真实、可重复、可审计的证据证明开发结果正确，并且在出现问题时能够定位、修复和重新验证。**
