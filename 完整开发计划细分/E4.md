# 1. 阶段概述

## 1.1 阶段定位

E4 是 AI Agent 系统的业务控制层建设阶段。

E0–E3 已经建立：

- 项目工程基础设施。
- Backend Core。
- Backend API、认证和权限服务。
- Godot Editor Plugin。
- Editor Bridge。
- Editor Session。
- Project Identity。
- Runtime Bridge 基础通信。

但是，目前系统还没有完整的游戏开发任务管理和工作流控制能力。

例如，用户提出：

> 帮我创建一个 2D 横版平台跳跃游戏，包含玩家移动、跳跃、敌人、关卡、生命值和游戏 UI。

系统必须能够把这项需求转化为：

1. 一个可追踪的 Project。
2. 一个明确的 Task。
3. 一组开发需求和验收标准。
4. 一个可执行的 Workflow。
5. 多个有顺序的 Phase。
6. 一组可以审批的 ChangeSet。
7. 一套可追踪的执行记录。
8. 一个由用户最终验收的交付结果。

这就是 E4 的主要职责。

|---|---|

| Domain Layer | Project、Task、Workflow、Approval Domain |
| Infrastructure Layer | Repository、Event、Scheduler、Transaction |
| Integration Layer | Editor Session、Project Identity |
| AI Execution Layer | 本阶段只预留接口 |
| Verification Layer | 本阶段只预留验收结果接口 |

## 2.3 状态所有权原则

这是 E4 最重要的架构要求。

| 状态对象 | 唯一状态权威 |
|---|---|
| Project | Project System |
| Task | Task System |
| Attempt | Task System |
| Workflow | Workflow Engine |
| Workflow Node | Workflow Engine |
| Phase | Workflow Engine |
| ChangeSet | ChangeSet Manager |
| Approval | Approval System |
| Requirement | Requirement Tracking |
| Verification Result | Verification System |

其他模块不得直接修改上述对象的数据库记录。

例如：

- Agent 不能直接把 Task 改成 COMPLETED。
- Workflow Engine 不能直接修改 Approval 状态。
- Approval System 不能直接修改 ChangeSet 内容。
- Verification System 不能直接修改 Task 状态。
- Project System 不能自行推进 Workflow。

所有跨模块状态变化必须通过公开接口或领域事件完成。

# 4. Project System

## E4-T01：Project Domain Model

**优先级：** P0  
**依赖：** E1 数据库基础

### 4.1.1 开发目标

建立整个 AI Agent 系统的 Project 领域模型。

Project 是 AI Agent 开发活动的主要组织单位。

一个 Project 可以包含：

- 多个 Task。
- 多个 Workflow。
- 多个 Requirement。
- 多个 ChangeSet。
- 多个 Approval。
- 多个 Editor Session。
- 多个 Agent Execution。
- 多个开发阶段。
- 多个验证结果。

### 4.1.2 Project 数据模型

```text
Project
- id
- name
- description
- project_root
- project_fingerprint
- godot_version
- project_type
- status
- configuration_id
- created_at
- updated_at
- archived_at
```

建议增加：

```text
ProjectIdentity
- project_id
- fingerprint_algorithm
- fingerprint_value
- project_config_path
- last_verified_at
```

### 4.1.3 Project 类型

初期支持：

- GODOT_2D
- GODOT_3D
- GODOT_HYBRID
- GODOT_UNKNOWN

Project Type 不应限制后续扩展。

### 4.1.4 Project 状态

```text
INITIALIZING
    |
    v
ACTIVE
    |
    ├──> SUSPENDED
    |
    ├──> ARCHIVED
    |
    └──> CLOSED
```

说明：

- ACTIVE：允许正常管理任务。
- SUSPENDED：暂停自动执行和新的受保护操作。
- ARCHIVED：项目进入归档状态。
- CLOSED：项目从当前工作上下文中关闭。

CLOSED 不等于删除项目。

### 4.1.5 验收标准

- Project ID 全局唯一。
- Project Root 与项目指纹可验证。
- Project 状态有明确状态机。
- 项目不能跨用户或跨工作空间非法访问。

## E4-T02：Project Registry

**优先级：** P0  
**依赖：** E4-T01、E3 Project Identity

### 开发目标

### 项目注册流程

```text
Godot Editor 连接
       |
       v
获取 Project Identity
       |
       v
Backend 验证项目路径
       |
       v
检查 Project Registry
       |
       ├── 已存在：加载项目
       |
       └── 不存在：创建注册记录
```

### 实施步骤

1. 实现项目注册。
2. 实现项目查询。
3. 实现项目列表。
4. 实现项目路径验证。
5. 实现项目指纹验证。
6. 实现 Editor Session 关联。
7. 实现项目重复识别。
8. 实现项目移动后的身份核验。

### 重要要求

同一项目可能被不同 Editor 实例打开。

不能简单地将一个项目限制为一个 Editor Session。

但不同 Session 的操作冲突必须通过后续 Resource Lock 和 ChangeSet 机制处理。

## E4-T03：Project Lifecycle

**优先级：** P0  
**依赖：** E4-T02

### 开发目标

管理 Project 从注册到归档的完整生命周期。

### 核心操作

- 创建项目记录。
- 激活项目。
- 暂停项目。
- 恢复项目。
- 关闭项目上下文。
- 归档项目。
- 重新激活归档项目。

### 状态转换约束

不能允许任意状态直接转换。

所有转换必须经过 Project System。

项目归档前必须检查：

- 是否存在运行中的 Task。
- 是否存在运行中的 Workflow。
- 是否存在待处理 Approval。
- 是否存在未完成 ChangeSet。
- 是否存在活动 Editor Session。

如存在未完成操作，必须根据策略要求暂停、完成、取消或确认归档。

### 验收标准

Project Lifecycle 的所有合法和非法转换均有测试。

- 配置变更不能静默改变正在执行的 Task 快照。

# 5. Task System

## E4-T06：Task Domain Model

**优先级：** P0  
**依赖：** E1

### 开发目标

建立统一任务模型。

Task 是用户提出的一项可追踪工作。

示例：

- 创建玩家移动系统。
- 实现敌人巡逻。
- 创建关卡地图。
- 修复玩家碰撞问题。
- 优化资源加载。
- 创建游戏菜单。
- 完成整个 Platformer Demo。

### Task 数据模型

```text
Task
- id
- project_id
- parent_task_id
- title
- description
- task_type
- priority
- status
- created_by
- assigned_to
- workflow_instance_id
- requirement_set_id
- current_attempt_id
- created_at
- updated_at
- completed_at
```

### Task 类型

```text
GAME_DEVELOPMENT
BUG_FIX
REFACTORING
ASSET_CREATION
LEVEL_DESIGN
UI_DEVELOPMENT
TESTING
OPTIMIZATION
RESEARCH
GENERAL
```

### Task 与 Attempt 必须分离

Task 表示用户要求完成的工作。

Attempt 表示这项工作的一次实际执行尝试。

例如：

```text
Task: 实现玩家移动

Attempt 1: 执行失败
Attempt 2: 部分完成
Attempt 3: 执行成功
```

三个 Attempt 属于同一个 Task。

不能通过创建新 Task 的方式代替正常重试。

## E4-T07：Task State Machine

**优先级：** P0  
**依赖：** E4-T06

### Task 状态

```text
CREATED
   |
   v
READY
   |
   v
QUEUED
   |
   v
RUNNING
   |
   ├──> PAUSING
   │       |
   │       v
   │    PAUSED
   │       |
   │       v
   │    RESUMING
   │       |
   │       v
   │    RUNNING
   |
   ├──> WAITING_APPROVAL
   |
   ├──> WAITING_USER
   |
   ├──> BLOCKED
   |
   ├──> FAILED
   |
   ├──> CANCELLED
   |
   └──> REVIEW_PENDING
              |
              v
           COMPLETED
```

还需要支持：

- REJECTED：用户或验收方拒绝结果。
- NEEDS_REVISION：需要修改后重新验收。

### Task 状态转换规则

| 当前状态 | 目标状态 | 条件 |
|---|---|---|
| CREATED | READY | Task 信息和前置条件有效 |
| READY | QUEUED | 已进入调度队列 |
| QUEUED | RUNNING | 获得执行资源 |
| RUNNING | PAUSED | 完成安全暂停 |
| RUNNING | WAITING_APPROVAL | 等待审批 |
| RUNNING | WAITING_USER | 等待用户输入 |
| RUNNING | BLOCKED | 依赖未满足 |
| RUNNING | FAILED | 执行失败 |
| RUNNING | REVIEW_PENDING | 执行阶段结束，等待验证或验收 |
| REVIEW_PENDING | COMPLETED | 满足验收条件并完成用户验收 |
| REVIEW_PENDING | NEEDS_REVISION | 验收发现需要修改 |
| NEEDS_REVISION | READY | 修改计划确认后重新进入队列 |
| 任意可取消状态 | CANCELLED | 用户取消并完成取消处理 |

### 特别规则

Task 的状态只能由 Task System 修改。

Agent 只能提交执行结果和状态建议。

Workflow Engine 只能向 Task System 请求合法状态转换。

Verification System 只能提交验证结果。

用户验收结果必须通过独立接口提交。

## E4-T08：Attempt Manager

**优先级：** P0  
**依赖：** E4-T07

### 开发目标

管理每次 Task 执行尝试。

### Attempt 数据模型

```text
TaskAttempt
- id
- task_id
- attempt_number
- status
- started_at
- ended_at
- agent_instance_id
- workflow_instance_id
- checkpoint_id
- execution_summary
- failure_code
- failure_reason
- resource_usage
```

### Attempt 状态

```text
CREATED
   |
   v
STARTING
   |
   v
RUNNING
   |
   ├──> SUCCEEDED
   ├──> FAILED
   ├──> CANCELLED
   ├──> INTERRUPTED
   └──> UNKNOWN
```

### 实施步骤

1. 创建 Attempt。
2. 分配 Attempt Number。
3. 记录开始时间。
4. 关联 Agent Instance。
5. 关联 Workflow。
6. 记录执行结果。
7. 记录失败原因。
8. 记录资源消耗。
9. 结束 Attempt。
10. 允许 Task 创建新的 Attempt。

### 重试规则

重试必须：

- 创建新 Attempt。
- 保留之前 Attempt。
- 记录重试原因。
- 检查预算。
- 检查前一次执行是否存在未知副作用。
- 必要时执行恢复或人工确认。

不能因为 Attempt 状态为 UNKNOWN 就盲目重新执行。

## E4-T09：Task Dependency

**优先级：** P1  
**依赖：** E4-T07

### 开发目标

支持任务之间的依赖关系。

### 依赖类型

- FINISH_TO_START。
- START_TO_START。
- FINISH_TO_FINISH。
- BLOCKS。
- RELATED。

第一阶段重点支持 FINISH_TO_START 和 BLOCKS。

### 数据模型

```text
TaskDependency
- id
- source_task_id
- target_task_id
- dependency_type
- status
- created_at
```

### 实施步骤

1. 创建依赖模型。
2. 创建依赖关系。
3. 检测循环依赖。
4. 计算任务可执行性。
5. 依赖完成后通知 Task System。
6. 支持依赖解除。
7. 记录依赖变更。

### 验收标准

不能出现无限循环依赖。

被阻塞任务不能错误进入 RUNNING。

### Checkpoint 类型

- PHASE_COMPLETED。
- WAITING_APPROVAL。
- SAFE_PAUSE。
- RECOVERY_POINT。
- EXECUTION_INTERRUPTED。

### 重要原则

模型内部隐藏推理不能作为恢复数据保存。

## E4-T16：Workflow Scheduler

**优先级：** P1  
**依赖：** E4-T14

- Task 状态允许运行。
- 项目未被暂停。

### 调度流程

```text

       |
       v

       |
       v
检查 Workflow 状态
       |
       v
检查 Task 状态
       |
       v
检查 Approval
       |
       v
检查资源锁
       |
       v
提交执行请求
       |
       v
等待 Agent / Tool / Verification 结果
```

E4 阶段可以先实现调度接口和基础串行调度。

复杂并行调度和多 Agent 调度放在 E6、E7。

## E4-T17：Workflow Recovery

**优先级：** P0  
**依赖：** E4-T10、E4-T11

### 开发目标

Backend 重启后能够恢复 Task 和 Workflow。

### 恢复步骤

1. 查询未完成 Task。
2. 查询关联 Attempt。
3. 查询 Workflow Instance。
4. 查询 Workflow Node 状态。
5. 查询最近 Checkpoint。
6. 检查 Outbox 未发送事件。
7. 检查未完成审批。
8. 检查 ChangeSet 状态。
9. 检查运行时操作结果。
10. 根据恢复策略恢复或暂停。

### 恢复策略

| 情况 | 处理 |
|---|---|
| 未开始 Task | 保持 READY |
| 正在执行 Task | 转入恢复检查 |
| 已安全暂停 Task | 保持 PAUSED |
| 正在等待审批 | 保持 WAITING_APPROVAL |
| 操作结果未知 | 标记 UNKNOWN |
| Checkpoint 不完整 | 暂停并请求恢复处理 |
| Session 失效 | 等待 Editor 重新连接 |

### 恢复原则

不能仅因为数据库中的 Task 曾经处于 RUNNING，就在 Backend 重启后直接恢复执行。

必须先确认执行环境、操作状态、权限和资源锁。

# 9. Approval System

## E4-T20：Approval System

**优先级：** P0  
**依赖：** E4-T19、E2 Authorization

### 开发目标

建立统一审批系统。

审批必须是独立业务对象，不能简单地使用 Task 的 WAITING_APPROVAL 状态代替。

### Approval 类型

- REQUIREMENT_APPROVAL。
- DESIGN_APPROVAL。
- CHANGESET_APPROVAL。
- DESTRUCTIVE_OPERATION_APPROVAL。
- RUNTIME_MUTATION_APPROVAL。
- EXTERNAL_DATA_APPROVAL。
- PHASE_ACCEPTANCE。
- RELEASE_APPROVAL。

### Approval 数据模型

```text
Approval
- id
- project_id
- task_id
- attempt_id
- workflow_instance_id
- target_type
- target_id
- target_version
- target_hash
- approval_type
- status
- requested_by
- decided_by
- requested_at
- expires_at
- decided_at
- decision_reason
```

### Approval 状态

```text
PENDING
   |
   ├──> APPROVED
   |
   ├──> REJECTED
   |
   ├──> EXPIRED
   |
   └──> CANCELLED
```

### Approval Decision

```text
ApprovalDecision
- id
- approval_id
- decision
- actor_id
- reason
- target_hash
- created_at
```

### 审批流程

1. 发起审批。
2. 生成审批目标快照。
3. 计算目标内容哈希。
4. 检查审批人权限。
5. 向用户展示变更内容和风险。
6. 用户作出决定。
7. 验证审批仍然有效。
8. 记录决定。
9. 触发对应业务事件。
10. Workflow Engine 根据事件继续执行或暂停。

### 四种权限必须分离

#### 1. Requirement Approval

用户确认要开发什么。

#### 2. ChangeSet Approval

用户确认具体修改哪些内容。

#### 3. Runtime Mutation Authorization

用户授权对运行中的游戏实例执行明确的运行时修改。

#### 4. External Data Authorization

用户授权访问外部数据、外部服务或外部资源。

上述授权不能相互替代。

### 关键安全要求

审批必须绑定：

- 审批目标。
- 目标版本。
- 目标哈希。
- 审批类型。
- 审批人。
- 有效时间。

目标内容改变后必须重新审批。

不能通过更换显示标题或任务描述保留原有审批效力。

- 批准和拒绝操作。

不能只显示一个“是否允许 AI 执行”的简单按钮。

# 15. 性能与可靠性要求

E4 不应仅以功能可用作为完成标准。

必须验证：

1. 大量 Task 列表查询不会阻塞主服务。
2. Task Event Log 查询支持分页。
3. Workflow Node 调度不会产生重复执行。
4. 并发状态修改能够正确检测冲突。
5. Approval 操作具有幂等性。
6. Checkpoint 写入不会无限增长。
7. 归档数据不影响活跃业务查询。
8. Outbox 积压可检测。
9. Backend 重启后恢复任务不会重复创建执行实例。
10. 状态机非法转换能够被拒绝。

具体性能指标应在 E0 的性能基线和实际压力测试中确定，不应在缺少测试数据时虚构吞吐量承诺。

# 18. E4 风险管理

| 编号 | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| E4-R01 | Task 和 Workflow 状态混乱 | 系统不可维护 | 明确唯一状态权威 |
| E4-R02 | Attempt 与 Task 混用 | 重试和审计错误 | 两者独立建模 |
| E4-R03 | Workflow Definition 修改影响运行实例 | 流程不可预测 | Definition Version |
| E4-R04 | Approval 不绑定内容 | 审批失效 | Hash Binding |
| E4-R05 | Agent 越权修改状态 | 业务安全风险 | 唯一状态所有权 |
| E4-R06 | Phase 自动推进 | 用户失去控制 | 强制用户验收 |
| E4-R07 | UNKNOWN 被当作失败重试 | 重复副作用 | UNKNOWN 专项恢复 |
| E4-R08 | ChangeSet 绕过 Tool System | 文件安全风险 | 强制 Tool System 写入 |
| E4-R09 | 并发状态更新 | 数据不一致 | Optimistic Lock |
| E4-R10 | Backend 崩溃导致重复执行 | 重复修改项目 | Checkpoint + Recovery |
