# 1. 阶段概述

## 1.1 阶段目标

E6 的目标是构建完整的单 Agent 运行时系统，使系统第一次具备执行真实游戏开发任务的能力。

完成 E6 后，系统应当能够：

1. 接收 Task System 分配的合法 Task 和 Attempt。
2. 根据 Agent Definition 创建 Agent Instance。
3. 固定 Agent Definition、Prompt、Model Policy、Tool Permission 和 Context Profile 的版本。
4. 获取项目 Context 并构建模型输入。
5. 通过 Model Gateway 调用 AI 模型。
6. 解析模型返回的结构化响应。
7. 制定和执行 Agent Plan。
8. 将具体操作交给 Tool Execution Engine。
9. 对 Tool 执行结果进行检查和验证。
10. 持续记录 Agent Event、Execution、Step 和 Checkpoint。
11. 根据 Task System 的指令暂停、恢复、取消或停止。
12. 在 Backend 重启、模型调用中断、工具执行不确定等情况下安全恢复。
13. 对 Agent 运行过程、预算、工具调用和错误进行追踪。
14. 通过一个 Generic Agent 完成从 Task 到结果的完整执行闭环。

本阶段只实现单 Agent Runtime。

Multi-Agent Orchestrator、专业 Agent 集群、Agent Handoff 和 Agent Collaboration 放在 E7 实现。

## 1.2 E6 的核心交付结果

E6 完成后，应当能够运行以下流程：

```text
用户创建 Task
      |
      v
Task System 创建 Task
      |
      v
Task System 创建 Attempt
      |
      v
Task System 授权 Agent Runtime 启动
      |
      v
Agent Runtime 创建 Agent Instance
      |
      v
加载冻结的 Agent Definition
      |
      v
获取 Project Context
      |
      v
Context Assembly
      |
      v
Prompt Assembly
      |
      v
Model Gateway
      |
      v
解析模型结构化响应
      |
      v
创建 Agent Plan
      |
      v
创建 Agent Step
      |
      v
Tool System 执行工具
      |
      v
结果验证
      |
      v
更新 Step / Event / Checkpoint
      |
      +------> 继续下一 Step
      |
      +------> 等待 Approval
      |
      +------> 等待用户输入
      |
      +------> 请求暂停
      |
      +------> 请求恢复
      |
      v

      |
      v

      |
      v

```

## 1.3 本阶段明确不实现的内容

E6 不负责：

- Multi-Agent Orchestrator。
- Agent-to-Agent Handoff。
- 多 Agent 并行协作。
- 38 个专业 Agent 的完整定义和能力实现。
- Game Designer、Programmer、Artist 等专业 Agent 工作流。
- 自动游戏开发完整工作流。
- Asset Generation Pipeline。
- 完整 QA 和自动化测试系统。
- Build、Export、Release 系统。

这些功能由 E7–E12 逐步实现。

# 2. 架构位置与设计约束

## 2.1 Agent Runtime 在系统中的位置

```text
                    Task System
                         |
                         v
                  Agent Runtime
                         |
           +-------------+-------------+
           |             |             |
           v             v             v
      Context         Model          Tool
     Assembly        Gateway        System
           |             |             |
           v             v             v
     Project Data     AI Provider    Godot Tool
     Knowledge        Adapters       File Tool
     Memory           Model          Editor Bridge
                      Registry       Runtime Bridge
           |
           v
      Agent Runtime
           |
     +-----+------+
     |            |
     v            v
  Checkpoint    Event Log
     |            |
     +------+-----+
            |
            v
     Recovery Coordinator
```

Agent Runtime 只通过模块公开接口与其他模块通信。

禁止直接访问其他模块的 Repository、数据库表或内部实现。

## 2.2 状态所有权冻结规则

| 状态对象 | 唯一状态权威 |
|---|---|
| Task | Task System |
| Attempt | Task System |
| Workflow | Workflow Engine |
| Phase | Workflow Engine |
| Workflow Node | Workflow Engine |
| Agent Definition | Agent Definition Registry |
| Agent Instance | Agent Runtime |
| Agent Execution | Agent Runtime |
| Agent Step | Agent Runtime |
| Tool Execution | Tool System |
| Approval | Approval System |
| ChangeSet | ChangeSet Manager |
| Verification Result | Verification System |
| Resource Lock | Resource Lock Manager |

任何模块不得修改不属于自己的状态。

### 强制规则

1. Agent Runtime 不拥有 Task 状态。
2. Agent Runtime 不拥有 Workflow、Phase、Node 状态。
3. Agent Instance 状态由 Agent Runtime 唯一拥有。
4. Agent 不能自行宣布 Task 成功。
5. Agent 不能绕过 Task System 直接创建或重新分配 Attempt。
6. Agent 不能绕过 Approval System。
7. Agent 不能直接操作项目文件或 Godot Editor。
8. Agent Runtime 不得直接调用任何 AI Provider SDK。
9. 所有模型调用必须经过 Model Gateway。
10. 所有项目操作必须经过 Tool System。
11. Agent Runtime 不保存或暴露模型隐藏推理。
12. Agent 只记录可审计的计划、行动、结果和摘要。

## 2.3 关键设计原则

### 原则 A：Agent Definition 与 Agent Instance 分离

Definition 是可复用的 Agent 配置。

Instance 是一次实际运行中的 Agent 实例。

Definition 更新不影响已经创建的 Instance。

### 原则 B：所有运行配置必须冻结

创建 Instance 时，必须冻结：

- Agent Definition ID。
- Agent Definition Version。
- Model Policy Version。
- Prompt Version。
- Tool Permission Snapshot。
- Context Profile Version。
- Budget Profile。
- Runtime Policy Version。

运行中不得静默替换这些配置。

如果需要升级配置，必须创建新的 Instance 或经过明确授权的版本迁移流程。

### 原则 C：所有操作都必须可追踪

每次模型调用、工具调用、Step 执行、暂停、恢复和错误都必须生成结构化事件。

### 原则 D：不确定状态优先进入 UNKNOWN

模型调用、工具执行、外部操作发生超时或连接中断时，不能直接认定失败并重新执行。

必须先检查原操作的真实状态。

**优先级：P0**  
**依赖：E1、E2、E4、E5**

- 所有实体使用 UUID 或统一 ID 规范。

## 验收标准

- 核心实体全部建立。
- 所有实体有明确状态和关系。
- 数据结构可以序列化。
- 契约有版本。
- 不同模块之间只使用公开 DTO/Contract 通信。

# 6. E6-T02 Agent Definition Registry

**优先级：P0**  
**依赖：E6-T01、E5**

## 目标

建立 Agent Definition 注册、版本管理和查询能力。

## 开发内容

1. 创建 Definition。
2. 更新尚未发布的 Definition。
3. 校验 Definition。
4. 发布新版本。
5. 查询当前版本。
6. 查询历史版本。
7. 停用 Definition。
8. 校验能力声明。
9. 校验 Model Policy 引用。
10. 校验 Prompt 引用。
11. 校验 Context Profile 引用。
12. 校验 Tool 白名单。
13. 校验 Permission Ceiling。
14. 校验 Budget Profile。

## Definition 示例

```yaml
agent:
  id: generic_agent
  name: Generic Agent
  version: 1.0.0

  capabilities:
    - task_analysis
    - planning
    - tool_execution
    - result_summary

  model_policy:
    policy_id: default_agent_policy

  prompt:
    profile_id: generic_agent_prompt
    version: 1.0.0

  context:
    profile_id: project_context_default
    version: 1.0.0

  tools:
    allowed:
      - project_read
      - file_read
      - file_write
      - scene_inspect

  permissions:
    maximum_risk_level: medium

  budgets:
    max_iterations: 30
    max_model_calls: 40
    max_tool_calls: 60
    max_execution_seconds: 1800
```

以上仅为配置示例，实际权限必须经过 Permission System 校验。

## 发布规则

- Definition 发布后不可修改。
- 新版本必须使用新 Version ID。
- 新建 Instance 必须指定已发布版本。
- 禁止通过修改 Definition 影响运行中的 Instance。

## 测试

- 重复发布。
- 非法能力声明。
- 不存在的 Prompt。
- 不存在的 Model Policy。
- 超出权限上限的 Tool。
- Definition 停用后创建 Instance。
- 运行期间发布新版本。

# 7. E6-T03 Agent Instance Manager

**优先级：P0**  
**依赖：E6-T01、E6-T02**

## 目标

负责创建、初始化和管理 Agent Instance。

## 创建流程

```text
收到 Task System 授权
        |
        v
验证 Task
        |
        v
验证 Attempt
        |
        v
验证 Project Access
        |
        v
加载 Definition Version
        |
        v
解析 Model Policy
        |
        v
解析 Prompt Version
        |
        v
解析 Context Profile
        |
        v
生成 Tool Permission Snapshot
        |
        v
生成 Budget Snapshot
        |
        v
保存 Config Snapshot
        |
        v
创建 Agent Instance
```

## 冻结配置内容

Instance 创建后必须保存：

- Agent Definition Version。
- Model Policy Version。
- Model Selection。
- Prompt Version。
- Context Profile Version。
- Tool Permission Snapshot。
- Budget Snapshot。
- Runtime Policy Version。
- Project Identity。
- Session Identity。

## 安全要求

Agent Instance 的有效权限不得高于：

```text
Definition Permission Ceiling
        ∩
Instance Permission
        ∩
Task Authorization
        ∩
Project Access
        ∩
User Permission
```

## 验收标准

- Instance 可以独立创建。
- 配置快照可以恢复。
- Definition 更新不会改变已有 Instance。
- 权限不能被 Instance 自行提高。
- Instance 创建过程具备事务一致性或可靠补偿机制。

# 8. E6-T04 Agent Lifecycle

**优先级：P0**  
**依赖：E6-T03**

## 目标

建立 Agent Instance 完整生命周期状态机。

## 状态定义

| 状态 | 含义 |
|---|---|
| CREATED | 已创建 |
| INITIALIZING | 初始化中 |
| READY | 已准备就绪 |
| RUNNING | 正在运行 |
| WAITING_TOOL | 等待工具执行 |
| WAITING_APPROVAL | 等待审批 |
| WAITING_INPUT | 等待用户输入 |
| PAUSING | 正在暂停 |
| PAUSED | 已暂停 |
| RESUMING | 正在恢复 |
| STOPPING | 正在停止 |
| STOPPED | 已停止 |
| COMPLETED | Agent Execution 已完成 |
| FAILED | 确定性失败 |
| UNKNOWN | 状态无法确认 |

## 状态流转

```text
CREATED
   |
   v
INITIALIZING
   |
   v
READY
   |
   v
RUNNING
   |
   +------> WAITING_TOOL
   |             |
   |             v
   |           RUNNING
   |
   +------> WAITING_APPROVAL
   |             |
   |             v
   |           RUNNING
   |
   +------> WAITING_INPUT
   |             |
   |             v
   |           RUNNING
   |
   +------> PAUSING
   |             |
   |             v
   |           PAUSED
   |             |
   |             v
   |          RESUMING
   |             |
   |             v
   |           RUNNING
   |
   +------> STOPPING
   |             |
   |             v
   |           STOPPED
   |
   +------> COMPLETED
   |
   +------> FAILED
   |
   +------> UNKNOWN
```

实际实现必须定义每个状态允许的前驱、后继和失败转换，不允许任意更新状态字段。

## 状态转换要求

- 所有状态转换必须通过 Lifecycle Manager。
- 每次转换写入 Agent Event。
- 转换需要记录原因。
- 并发转换必须使用乐观锁或版本号。
- UNKNOWN 不能直接转换为 RUNNING，必须先执行恢复检查。

## 特别说明

Agent 的 COMPLETED 只表示 Agent Execution 完成。

它不代表 Task 已完成。

Task System 必须根据 Verification 和任务规则决定 Task 的最终状态。

# 9. E6-T05 Agent Scheduler

**优先级：P0**  
**依赖：E6-T03、E6-T04、E2**

## 目标

实现 Agent Execution 的调度和运行资源管理。

## 功能范围

- Agent Execution Queue。
- 并发限制。
- 项目级并发限制。
- Agent Definition 级并发限制。
- 用户级资源配额。
- 优先级。
- 公平调度。
- 超时处理。
- Worker 健康检查。
- Worker 崩溃检测。

## 调度维度

```text
Global Capacity
    |
    +-- Project Capacity
    |
    +-- User Capacity
    |
    +-- Agent Definition Capacity
    |
    +-- Execution Capacity
```

## 强制规则

1. Scheduler 不直接创建 Task。
2. Scheduler 不直接改变 Task 状态。
3. Scheduler 只能调度 Task System 已授权的 Attempt。
4. 不同 Project 的执行资源必须隔离。
5. 不允许低优先级任务无限饥饿。
6. 不允许同一 Attempt 被多个 Worker 同时执行。
7. Worker 必须使用 Execution Lease 或等效机制避免重复消费。
8. Lease 失效后必须进入 Recovery 流程。

## 测试

- 多 Project 并发。
- 多用户并发。
- Worker 崩溃。
- Queue 积压。
- 重复调度。
- Lease 过期。
- 高优先级任务插队。
- 公平性验证。

# 10. E6-T06 Task Binding & Attempt Binding

**优先级：P0**  
**依赖：E4、E6-T03**

## 目标

建立 Agent Runtime 与 Task System 的正式绑定关系。

## 核心规则

Task 和 Attempt 是两个独立对象。

一次 Attempt 对应一次具体的任务执行尝试。

Attempt 失败后，Task System 根据自身规则创建新的 Attempt。

新 Attempt 不得继承旧 Attempt 的活动执行权。

## 绑定关系

```text
Task
 |
 +-- Attempt 1
 |      |
 |      +-- Agent Instance 1
 |              |
 |              +-- Execution 1
 |
 +-- Attempt 2
        |
        +-- Agent Instance 2
                |
                +-- Execution 2
```

是否允许一个 Attempt 内存在多个 Agent Instance，必须由 Task System 和运行策略明确授权；E6 的默认实现采用一个活动 Agent Instance 对应一个 Attempt。

## 必须实现

- Task Authorization Validation。
- Attempt Authorization Validation。
- Attempt Lease。
- Instance Binding。
- Execution Binding。
- Attempt End Notification。
- Attempt Supersession Detection。

## 防止旧 Attempt 继续执行

当 Attempt 被 Task System 终止或替代时：

1. Agent Runtime 收到状态变更事件。
2. 停止继续派发新 Step。
3. 检查正在执行的 Tool。
4. 对可安全停止的操作执行停止。
5. 对不确定的操作进入 UNKNOWN。
6. 记录终止原因。
7. 释放可释放的资源锁。
8. 将执行结果提交 Task System。

# 11. E6-T07 Agent Execution Loop

**优先级：P0**  
**依赖：E6-T01 至 E6-T06、E5**

这是 E6 最核心的模块。

## 目标

构建可以真正执行任务的 Agent Loop。

## 完整执行流程

### Step 1：接收执行请求

验证：

- Task 是否存在。
- Attempt 是否有效。
- Project 是否有效。
- Session 是否有效。
- Agent Definition 是否有效。
- Agent Runtime 是否有启动权限。

### Step 2：创建 Agent Instance

读取冻结配置并建立运行实例。

### Step 3：加载执行上下文

通过 Context Adapter 获取：

- Task Description。
- Acceptance Criteria。
- Project Information。
- Relevant Project Files。
- Godot Project Structure。
- Previous Attempt Summary（如果允许）。
- Approved Context。
- User Instructions。

### Step 4：组装 Prompt

由 Prompt Assembly Service 构建模型请求。

Prompt 必须明确：

- Agent Role。
- Task Objective。
- Constraints。
- Context。
- Available Tools。
- Tool Restrictions。
- Output Schema。
- Budget。
- Stop Conditions。

### Step 5：调用 Model Gateway

Agent Runtime 只能调用统一 Model Gateway Interface。

不得直接调用：

- OpenAI SDK。
- Anthropic SDK。
- Google AI SDK。
- 其他 Provider SDK。

### Step 6：解析模型响应

响应必须转换为结构化 Agent Action。

支持的 Action 类型：

- ANALYZE
- CREATE_PLAN
- UPDATE_PLAN
- EXECUTE_TOOL
- REQUEST_APPROVAL
- REQUEST_USER_INPUT
- REPORT_PROGRESS
- COMPLETE_EXECUTION
- FAIL_EXECUTION

不允许把任意模型文本直接当成可执行命令。

### Step 7：验证 Action

检查：

- Action Schema。
- 当前 Agent 状态。
- Tool 白名单。
- Permission。
- Budget。
- Approval。
- Project Scope。
- Resource Lock。
- Task/Attempt 状态。

### Step 8：执行 Action

所有工具调用都通过 Tool System。

### Step 9：验证执行结果

工具返回后：

- 检查 Tool Execution Status。
- 检查 Result Schema。
- 检查执行证据。
- 检查目标状态是否满足。
- 判断是否需要重试、重新规划或请求用户。

### Step 10：记录状态

更新：

- Agent Step。
- Agent Execution。
- Agent Event。
- Budget Usage。
- Checkpoint。

### Step 11：决定下一步

根据执行结果决定：

- 继续当前 Plan。
- 创建新 Plan。
- 等待 Approval。
- 等待 User Input。
- 暂停。
- 结束 Agent Execution。
- 报告失败。
- 进入 UNKNOWN。

## Agent Loop 伪代码

```python
async def execute_agent(instance_id):
    instance = await instance_manager.get(instance_id)

    await lifecycle.initialize(instance)

    while True:
        state = await lifecycle.get_status(instance_id)

        if state in TERMINAL_STATES:
            return

        if await task_adapter.is_cancelled(instance.task_id):
            await cancellation_controller.handle(instance_id)
            return

        if await task_adapter.is_pause_requested(instance.task_id):
            await pause_controller.pause(instance_id)
            return

        await budget_manager.check(instance_id)

        context = await context_binding.build(instance_id)

        prompt = await prompt_assembler.assemble(
            instance=instance,
            context=context,
        )

        model_response = await model_gateway_adapter.generate(
            instance=instance,
            prompt=prompt,
        )

        action = await response_parser.parse(model_response)

        await action_validator.validate(
            instance=instance,
            action=action,
        )

        result = await action_dispatcher.dispatch(
            instance=instance,
            action=action,
        )

        await result_verifier.verify(
            instance=instance,
            action=action,
            result=result,
        )

        await event_service.record_action_result(
            instance=instance,
            action=action,
            result=result,
        )

        await checkpoint_service.create(instance)

        if action.type == "COMPLETE_EXECUTION":
            await execution_manager.complete(instance_id)
            return
```

上述伪代码仅表达执行顺序。正式实现必须增加：

- Cancellation Token。
- Execution Lease。
- Transaction Boundary。
- Timeout。
- Idempotency。
- Recovery Check。
- Model Request Tracking。
- Tool Execution Tracking。
- Budget Reservation。
- Event Persistence。
- Checkpoint Consistency。

## 重要要求

模型返回 COMPLETE_EXECUTION 仅表示 Agent 认为自己的工作已经结束。

Agent Runtime 必须检查是否存在未完成的 Step、待处理 Tool、未完成的 Approval 或其他阻塞条件。

之后向 Task System 提交执行结果，由 Task System 决定是否需要 Verification。

# 18. E6-T14 Pause / Resume / Cancel / Stop

**优先级：P0**  
**依赖：E4、E6-T04、E6-T13**

## 目标

建立可控的 Agent 生命周期操作。

## Pause

暂停必须由 Task System 发起或授权。

暂停流程：

1. 接收 Pause Request。
2. 检查当前 Step。
3. 停止派发新 Step。
4. 等待安全原子操作完成，或使用工具提供的安全取消接口。
5. 检查 Tool Execution。
6. 创建 Checkpoint。
7. 更新 Agent Instance 为 PAUSED。
8. 通知 Task System。

不能为了快速暂停而强行中断正在进行的非幂等操作。

## Resume

恢复流程：

1. 接收 Task System 授权。
2. 验证 Task/Attempt 仍有效。
3. 验证 Session。
4. 验证 Project。
5. 验证 Resource Lock。
6. 验证 Approval。
7. 验证 Context Snapshot。
8. 验证 Model Availability。
9. 验证 Tool Version。
10. 验证 Budget。
11. 执行恢复。
12. 写入 RESUMED Event。

任何关键条件不满足时，不允许继续执行。

## Cancel

取消必须由 Task System 发起或授权。

Cancel 不等于 Rollback。

取消之后必须区分：

- 尚未执行的 Step。
- 已完成的 Step。
- 正在执行的 Tool。
- 不确定状态的 Tool。
- 已经产生的项目变更。

Agent Runtime 负责安全停止执行，并向 Task System 提交真实结果。

## Stop

Stop 是 Agent Runtime 内部的停止动作。

不能把 STOPPED 直接映射为 Task CANCELLED。

# 19. E6-T15 Recovery Coordinator Integration

**优先级：P0**  
**依赖：E1、E5、E6-T13、E6-T14**

## 目标

使 Agent Runtime 可以处理进程重启、连接断开和未知执行状态。

## 恢复场景

- Backend 崩溃。
- Worker 崩溃。
- 模型请求超时。
- 模型响应丢失。
- Tool 执行超时。
- Godot Editor 断开。
- Session Lease 过期。
- Resource Lock 失效。
- Approval 状态变化。
- SQLite 写入失败。
- Checkpoint 创建失败。

## 恢复流程

```text
Backend Startup
      |
      v
Recovery Coordinator
      |
      v
Find Non-terminal Agent Instances
      |
      v
Load Last Checkpoint
      |
      v
Replay Agent Events
      |
      v
Validate Task / Attempt
      |
      v
Check Session / Project
      |
      v
Check Model Requests
      |
      v
Check Tool Executions
      |
      v
Check Approval / Resource Lock
      |
      v
Determine Recovery State
      |
      +----> Resume
      |
      +----> Pause
      |
      +----> Wait for User
      |
      +----> UNKNOWN
```

## UNKNOWN 原则

以下情况必须进入 UNKNOWN 或恢复等待状态：

- Tool 执行结果不确定。
- Model Request 状态不确定。
- 关键 Event 丢失。
- Checkpoint 与 Event 不一致。
- Project 当前状态与执行记录冲突。
- Session 身份无法确认。

禁止在 UNKNOWN 状态下自动重复执行可能产生副作用的操作。

## 恢复验收

- Backend 重启后能够找到未完成 Instance。
- 能够定位最后一个可靠 Checkpoint。
- 能够查询原 Model Request。
- 能够查询原 Tool Execution。
- 能够恢复确定完成的 Step。
- 不会重复执行已经完成的非幂等操作。

**依赖：E6-T16、E6-T17、E3**

## 目标

在 Godot Plugin 中提供 Agent 运行监控界面。

## UI 页面

### Agent Overview

显示：

- Agent Name。
- Definition Version。
- Instance Status。
- Task。
- Attempt。
- Project。
- Start Time。
- Execution Duration。

### Execution Monitor

显示：

- 当前 Plan。
- 当前 Step。
- 已完成 Step。
- 待执行 Step。
- 模型调用状态。
- 工具执行状态。
- 最近事件。
- 当前错误。

### Budget Monitor

显示：

- Token Budget。
- Model Call Budget。
- Tool Call Budget。
- Iteration Budget。
- Time Budget。
- Cost Budget。

### Approval Waiting

显示：

- 等待审批的操作。
- 操作目标。
- 风险级别。
- 变更摘要。
- Approval 状态。

审批按钮必须调用 Approval System，不能直接修改 Agent 状态。

### Recovery Monitor

显示：

- UNKNOWN 状态。
- 最后可靠 Checkpoint。
- 未完成 Model Request。
- 未完成 Tool Execution。
- 需要用户处理的恢复问题。

## UI 安全

- UI 不直接修改数据库。
- UI 不直接调用 Tool。
- UI 所有操作通过 Backend API。
- UI 不展示隐藏推理。
- UI 显示的是审计计划、行动、结果和摘要。

# 23. E6-T19 Built-in Generic Agent

**优先级：P1**  
**依赖：E6-T01 至 E6-T18**

## 目标

实现第一个能够执行真实任务的通用 Agent。

它是验证 Agent Runtime 的基础 Agent，不是最终专业 Agent。

## Generic Agent 能力

- 接收任务。
- 理解任务目标。
- 获取项目 Context。
- 进行任务分析。
- 创建结构化 Plan。
- 使用允许的工具。
- 检查工具执行结果。
- 发现问题。
- 调整 Plan。
- 请求 Approval。
- 请求用户输入。
- 汇报进度。
- 提交执行摘要。

## 第一阶段工具范围

只开放经过授权的基础工具，例如：

- project_read
- file_read
- project_structure_inspect
- scene_inspect
- resource_inspect
- file_write（受权限和审批约束）

实际 Tool ID 必须以 E5 Tool Registry 中已注册的工具为准。

## Generic Agent 的验收任务

至少完成以下测试任务：

### 测试任务 A：只读分析

要求 Agent：

1. 获取项目结构。
2. 读取项目配置。
3. 分析主要 Scene。
4. 总结项目结构。
5. 输出结构化结果。

### 测试任务 B：简单文件修改

要求 Agent：

1. 分析用户提出的修改要求。
2. 读取相关文件。
3. 制定修改 Plan。
4. 检查写入权限。
5. 根据 ChangeSet 和 Approval 规则执行。
6. 读取修改结果。
7. 验证结果。
8. 提交执行摘要。

### 测试任务 C：暂停和恢复

要求 Agent：

1. 开始任务。
2. 执行部分 Step。
3. 收到 Task System Pause Request。
4. 创建 Checkpoint。
5. 进入 PAUSED。
6. 收到 Resume Request。
7. 验证状态。
8. 从正确 Step 恢复。
9. 完成任务。

### 测试任务 D：未知工具状态

要求 Agent：

1. 启动一个工具操作。
2. 模拟连接中断。
3. Tool Execution 返回 UNKNOWN。
4. Agent 停止后续执行。
5. Recovery Coordinator 查询原执行状态。
6. 确认结果后决定继续或等待用户。

## 本阶段不要求

- 38 个专业 Agent 全部实现。
- 自动分配设计师和程序员。
- 多 Agent 并行执行。
- Agent 之间互相委派。
- 专业 Agent 自动协作。

这些属于 E7。

## 数据库规则

- Event 表采用追加式设计。
- Event Sequence 必须唯一。
- Instance、Execution、Step 状态更新必须具备并发控制。
- 不保存 API Key。
- 不保存模型隐藏推理。
- 大型 Prompt 和 Context 内容优先存储为受控引用或独立快照，不应无限制复制进事件表。
- Checkpoint 必须保留恢复所需的最小完整信息。
- 所有跨模块数据通过公开 Contract 获取。

# 27. 事务与一致性要求

## 27.1 Instance 创建

以下内容应当具有一致性：

- Config Snapshot。
- Agent Instance。
- Initial Event。

如果其中一项失败，不得留下无法恢复的半成品 Instance。

## 27.2 Execution 启动

必须避免：

- Execution 已启动但 Instance 仍为 READY。
- Instance 已进入 RUNNING 但没有 Execution。
- 一个 Attempt 同时绑定多个活动执行者。

## 27.3 Tool Execution

Tool System 拥有 Tool Execution 的真实状态。

Agent Runtime 只能引用和消费执行结果。

## 27.4 Event 与 Checkpoint

优先采用事务内写入或可靠 Outbox 模式，避免事件与状态不一致。

## 27.5 并发控制

至少对以下对象实施版本控制：

- Agent Instance。
- Agent Execution。
- Agent Plan。
- Agent Step。
- Agent Checkpoint。

# 28. 配置管理

建议配置：

```yaml
agent_runtime:
  enabled: true

  scheduler:
    max_global_concurrency: 4
    max_project_concurrency: 2
    max_definition_concurrency: 2
    queue_poll_interval_ms: 500

  execution:
    default_timeout_seconds: 1800
    max_iterations: 30
    max_retries: 3

  checkpoint:
    enabled: true
    interval_steps: 1

  recovery:
    enabled: true
    scan_interval_seconds: 30
    unknown_requires_review: true

  observability:
    event_persistence: true
    execution_tracing: true
```

所有生产参数必须通过 Configuration Service 管理。

禁止在代码中硬编码 Provider API Key、Session Token 或其他 Secrets。

# 32. 主要风险与处理策略

| 风险 | 后果 | 处理 |
|---|---|---|
| Agent 与 Task 状态混淆 | 状态不一致 | 严格分离状态所有权 |
| Definition 更新影响 Instance | 执行行为漂移 | 创建时冻结版本 |
| 模型返回非结构化操作 | 不安全执行 | Action Schema Validation |
| 模型调用超时 | 重复请求和费用 | Request Tracking |
| Tool 状态 UNKNOWN | 重复修改项目 | 先查询原 Execution |
| Checkpoint 不完整 | 无法恢复 | Checkpoint 完整性验证 |
| Budget 并发超限 | 费用失控 | 预留与结算机制 |
| Context 过长 | 模型调用失败 | 固定 Context 保护与预算控制 |
| 权限叠加错误 | 越权操作 | 权限交集与默认拒绝 |
| Pause 中断原子操作 | 项目数据损坏 | 安全暂停边界 |
| Attempt 替换后旧 Agent 继续运行 | 重复修改 | Attempt Lease 与 Supersession Check |
| UI 直接操作后端数据 | 绕过安全层 | 所有操作通过 API |

# 35. 最终阶段目标

E6 的真正完成标志不是“模型能够回复消息”，也不是“模型能够调用一个工具”。

而是：

**一个由 Task System 正式授权的 Agent，能够在权限、预算、上下文和项目边界受到严格控制的前提下，独立完成任务分析、计划制定、模型调用、工具执行、结果验证、状态持久化、暂停恢复和结果提交，并且在异常情况下不会重复执行不确定的项目操作。**

当这条闭环经过真实 Godot 项目验证后，系统才具备进入 E7 多 Agent 协作阶段的基础。
