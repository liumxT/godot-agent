# E12-DEV-001《Productization 产品化、正式交付与长期运维阶段详细开发实施文档》

**文档编号：** E12-DEV-001  
**版本：** V1.0 DRAFT  
**所属路线：** E0–E12 Godot AI Agent Platform  
**阶段名称：** E12 Productization  
**阶段性质：** 平台产品化、正式交付、发布治理与长期运维  
**前置阶段：** E0–E11  
**阶段定位：** 将已经通过 E11 系统级集成验收的 Godot AI Agent 平台转化为可正式交付和持续维护的软件产品。

---

# 1. 阶段概述

## 1.1 阶段目标

E12 的核心目标是让整套系统从一个能够在开发环境中运行的工程项目，转化为用户可以独立安装和使用的正式产品。

最终用户应当能够：

1. 下载并安装 Godot AI Agent 平台。
2. 安装或启用 Godot Editor Plugin。
3. 启动和管理 Local Backend。
4. 完成首次运行配置。
5. 连接自己的 Godot 项目。
6. 配置 AI Model Provider。
7. 配置 Tool、Agent、Budget 和 Permission。
8. 使用 Development Assistant 模式。
9. 使用 Autonomous Game Development 模式。
10. 创建和管理 Task、Workflow、Agent Team。
11. 使用 Asset Pipeline。
12. 使用 Verification & QA。
13. 使用 Build & Release。
14. 查看系统状态、日志和诊断报告。
15. 安全升级系统。
16. 在升级失败或系统异常时恢复。
17. 导出诊断信息并获取技术支持。
18. 卸载软件而不意外删除用户的项目数据。

E12 必须完成产品本身的安装、配置、兼容性、安全、隐私、更新、恢复、文档、支持和正式发布流程。

## 1.2 E12 与 E10 的区别

必须严格区分两类发布。

| 项目 | E10 Build & Release | E12 Productization |
|---|---|---|
| 发布对象 | 用户开发的 Godot 游戏 | Godot AI Agent 平台本身 |
| 核心对象 | Game Artifact | Product Package |
| 构建系统 | Godot Export | 平台产品构建 |
| 交付对象 | 游戏可执行文件和资源 | Backend、Plugin、安装包及依赖 |
| 版本 | 游戏版本 | 平台版本 |
| 签名 | 游戏制品签名 | 平台安装包及更新包签名 |
| 升级 | 游戏版本升级 | 平台组件和数据库升级 |
| 发布渠道 | 游戏分发渠道 | 产品 Stable/Beta/Dev |
| 回滚 | 游戏版本回退 | 平台版本、Plugin、配置和数据库恢复 |

E10 的 Build & Release Engine 是平台内部的游戏交付能力。

E12 的 Product Release Pipeline 是平台产品自己的构建和发布能力。

两者不能共用同一个 Release 状态机，也不能混用产品版本和游戏 Artifact 版本。

## 1.4 产品运行模式

产品必须继续支持两种主要使用模式。

**Development Assistant**

用户主导开发，AI 提供分析、建议、代码辅助、Editor 操作、调试、资产处理和测试支持。

**Autonomous Game Development**

用户定义目标和授权边界，由 Workflow Engine、Multi-Agent Orchestrator 和 Agent Runtime 协作执行开发任务。

两种模式共享：

- Project Intelligence
- Context System
- Task System
- Workflow Engine
- Agent Runtime
- Tool System
- ChangeSet
- Approval
- Verification
- Asset Pipeline
- Build & Release

不得为产品化而重新实现一套独立业务逻辑。

# 4. 产品化总体架构

## 4.1 产品分层

产品化阶段继续使用已经冻结的八层架构。

| 层 | 职责 | 产品化重点 |
|---|---|---|
| L1 Presentation | Godot Plugin UI | 安装、配置、错误提示、用户体验 |
| L2 Application | Application Services | 产品操作入口、流程编排 |
| L3 Domain | 业务领域 | License、Update、Installation 等 |
| L4 Agent | Agent Runtime | 运行稳定性和资源治理 |
| L5 AI & Tool | 模型和工具 | Provider、权限和密钥保护 |
| L6 Integration | Godot/External Adapters | 兼容性、协议稳定性 |
| L7 Infrastructure | DB、Logging、Recovery | 升级、备份、恢复、监控 |
| L8 Security & Governance | 权限、审计、策略 | 安全、隐私、合规 |

产品化服务不能绕过业务模块直接访问其他模块的 Repository。

## 4.2 产品级核心原则

- 产品组件全部有明确版本。
- Plugin 和 Backend 版本必须具备兼容性声明。
- DB Schema 和 Migration 必须有版本。
- Agent Definition 和 Tool Schema 必须版本化。
- 更新必须验证签名和内容完整性。
- 安装与升级不得静默修改用户项目。
- 不得在卸载时默认删除用户项目和数据。
- 用户拥有数据导出和备份能力。
- 本地 Backend 默认只监听 Loopback。
- Secrets 不进入普通配置文件、日志、模型 Context 或 Support Bundle。
- Telemetry 默认关闭。
- 用户项目源代码和资产不得默认上传。
- 所有不确定的外部操作必须支持 UNKNOWN 状态和恢复检查。

# E12-T01 Productization Domain & Contract

**优先级：P0**

## 目标

建立平台产品化领域模型和统一契约，避免产品安装、更新、授权、迁移、支持等功能散落在各个业务模块中。

## 依赖

E1、E2、E4、E5、E9、E10。

## 任务内容

### 1. Product Domain

建立以下核心实体：

| Entity | 职责 |
|---|---|
| Product | 平台产品定义 |
| Product Edition | 产品版本或能力集合 |
| Product Release | 平台产品发布版本 |
| Product Component | 产品组件 |
| Installation | 用户安装实例 |
| Installation Profile | 安装配置 |
| Product Configuration | 产品配置 |
| Product Environment | 运行环境 |
| Compatibility Matrix | 兼容性矩阵 |
| Update Channel | 更新通道 |
| Update Package | 更新包 |
| Migration Plan | 迁移计划 |
| Recovery Point | 恢复点 |
| License | 授权记录 |
| Entitlement | 功能使用权 |
| Feature Flag | 功能开关 |
| Support Bundle | 支持诊断包 |
| Telemetry Consent | 数据采集同意记录 |
| Crash Report | 崩溃报告 |
| Product Policy | 产品策略 |
| Documentation Version | 文档版本 |

### 2. 产品版本与游戏版本隔离

必须定义两个完全独立的版本域：

- Product Version：AI Agent 平台版本。
- Game Artifact Version：用户游戏制品版本。

禁止使用同一个版本号或同一 Release Repository 管理两者。

### 3. 版本规则

建议平台版本采用：

`MAJOR.MINOR.PATCH`

例如：

`1.2.3`

版本规则：

- MAJOR：不兼容的 API、协议或数据结构变化。
- MINOR：向后兼容的功能增加。
- PATCH：向后兼容的缺陷修复。

同时为以下组件记录独立版本：

- Godot Plugin。
- Backend。
- API Protocol。
- Database Schema。
- Agent Definition Schema。
- Tool Schema。
- Provider Adapter Contract。
- Installer。
- Product Package。

### 4. 契约设计

统一记录：

- contract_id
- contract_version
- owner_module
- compatibility_policy
- deprecated_since
- removed_since
- migration_strategy
- schema_hash

## 目录建议

<escape>```text

  modules/
    product/
      domain/
      application/
      infrastructure/
      contracts/
      repositories/
      services/
      policies/
      events/
      tests/
```</escape>

## API

- `GET /api/v1/product/info`
- `GET /api/v1/product/version`
- `GET /api/v1/product/components`
- `GET /api/v1/product/compatibility`
- `GET /api/v1/product/capabilities`
- `GET /api/v1/product/health`

## 测试

- Product Version Contract Test。
- Component Compatibility Test。
- Product/Game Version Isolation Test。
- Schema Compatibility Test。
- Contract Deprecation Test。

## 验收标准

- 所有产品组件可查询版本。
- Product Version 与 Game Artifact Version 完全隔离。
- 所有公开契约有版本。
- 兼容性检查可由系统自动执行。
- 不允许未声明版本的组件进入正式发布包。

# E12-T02 Product Architecture & Packaging

**优先级：P0**

## 目标

建立可独立安装和部署的正式产品组件结构。

## 依赖

E12-T01。

## 任务内容

### 1. 产品组件布局

建议正式安装结构：

<escape>```text
GodotAIAgent/
│
├── app/
│   ├── backend/
│   ├── launcher/
│   ├── migrations/
│   └── resources/
│
├── godot_plugin/
│   └── addons/
│       └── godot_ai_agent/
│
├── tools/
│   ├── diagnostics/
│   └── maintenance/
│
├── config/
│   └── defaults/
│
├── docs/
│
└── metadata/
    ├── product_manifest.json
    └── component_manifest.json
```</escape>

用户数据必须放在独立的数据目录，而不是安装目录。

建议采用操作系统标准用户数据路径：

- Windows：用户 LocalAppData。
- macOS：用户 Library/Application Support。
- Linux：用户 XDG 数据目录。

配置、日志、数据库和缓存应分别管理。

### 2. 组件安装策略

必须支持：

- Backend 独立运行。
- Plugin 独立安装。
- Plugin 连接指定 Backend。
- 本机多个 Godot Editor 实例。
- 多项目连接。
- 多个产品版本之间的隔离策略。

### 3. Godot Plugin 安装方式

首期提供：

1. 手动安装 ZIP。
2. 产品 Installer 安装。
3. 用户指定项目后执行 Plugin 安装。

安装时：

- 检查项目路径。
- 检查已有 Plugin。
- 检查 Plugin 版本。
- 生成安装变更清单。
- 允许用户确认。
- 不覆盖用户修改过的文件而不提示。
- 提供恢复原始 Plugin 文件的机制。

### 4. 操作系统支持

首期目标：

- Windows x64。
- macOS（根据 CI 和签名环境逐步支持）。
- Linux x86_64。

不得在没有真实测试的情况下宣称 ARM、特定发行版或特定 OS 版本完全兼容。

## 测试

- Clean Installation Test。
- Upgrade Installation Test。
- Plugin Installation Test。
- Multiple Editor Test。
- Multiple Project Test。
- User Data Separation Test。

## 验收标准

- 产品可以独立安装。
- Backend 和 Plugin 组件可独立识别。
- 用户数据与安装文件隔离。
- 多项目之间不存在数据串扰。
- 不会静默覆盖用户 Plugin 修改。

# E12-T03 Installer & First-Run Setup

**优先级：P0**

## 目标

实现完整的安装、初始化和首次运行流程。

## 依赖

E12-T02。

## 任务内容

### 1. Installer

提供：

- 安装目录选择。
- 用户数据目录检查。
- 组件选择。
- 系统依赖检查。
- 文件权限检查。
- 磁盘空间检查。
- Backend 安装。
- Plugin 安装。
- 快捷启动入口。
- 安装完成验证。

### 2. Installation State Machine

<escape>```text
CREATED
  ↓
PRECHECK
  ↓
INSTALLING
  ↓
VERIFYING
  ↓
COMPLETED
```

异常状态：

- FAILED
- PARTIAL
- RECOVERY_REQUIRED
- ROLLED_BACK

### 3. First-run Wizard

首次启动包含：

1. 欢迎页。
2. 产品运行模式介绍。
3. Backend 状态检查。
4. 数据目录选择。
5. 安全设置。
6. 模型 Provider 配置。
7. 默认 Model Policy。
8. Budget 设置。
9. Godot Editor 检测。
10. Plugin 连接。
11. Demo Project 或用户项目选择。
12. 完整性诊断。

### 4. 安装后检查

系统必须验证：

- Backend 可启动。
- API Server 可访问。
- Database 可读写。
- Migration 已完成。
- Plugin 文件完整。
- Plugin 与 Backend Protocol 兼容。
- WebSocket 可以建立。
- Session Lease 正常。
- 日志目录可写。
- Secrets Store 可用或明确报告限制。

### 5. 可恢复安装

安装中断时：

- 记录 Installation Step。
- 记录已创建文件。
- 记录组件版本。
- 记录配置变化。
- 支持继续安装或安全回滚。
- 不删除用户原有项目内容。

## 验收标准

- 新机器可以从零完成安装。
- 安装中断后能够恢复。
- First-run Wizard 能识别常见环境问题。
- 安装完成后可启动 Godot Plugin 并连接 Backend。
- 不存在安装成功但核心组件不可运行的假成功状态。

# E12-T04 Configuration & Secrets UX

**优先级：P0**

## 目标

让用户能够安全地管理模型、工具、项目、预算和连接配置。

## 依赖

E5、E12-T01、E12-T03。

## 任务内容

### 1. Configuration Center

建立统一设置中心：

- General。
- Backend。
- Godot Integration。
- Model Providers。
- Model Routing。
- Agent Policies。
- Tool Permissions。
- Budget。
- Asset Providers。
- Network & Proxy。
- Project Defaults。
- Logging。
- Privacy。
- Updates。
- Diagnostics。

### 2. Configuration Profile

支持：

- Default Profile。
- Development Profile。
- Restricted Profile。
- Custom Profile。

配置应具有：

- profile_id
- profile_version
- scope
- created_at
- updated_at
- configuration_hash

### 3. 配置优先级

建议采用：

`System Default < User Global < Project Override < Explicit Session Override`

但是任何覆盖都必须明确展示来源。

安全策略和权限策略不能因为低优先级配置而被覆盖。

### 4. Secrets 管理

优先使用：

- Windows Credential Manager。
- macOS Keychain。
- Linux Secret Service 或可用的系统凭证存储。

如果 OS Credential Store 不可用：

- 明确提示风险。
- 提供受控替代方式。
- 不得将 API Key 明文写入 SQLite。
- 不得把密钥放入普通 JSON 配置。
- 不得在日志中记录密钥。
- 不得把密钥放入模型 Context。

### 5. Model Policy

用户指定的模型必须优先。

如果用户配置的模型不可用：

- 明确显示错误。
- 解释失败原因。
- 提供用户主动选择替代模型的入口。
- 不得静默切换到其他 Provider。

### 6. 配置导出

配置导出默认排除：

- API Key。
- Access Token。
- Refresh Token。
- Credential Material。
- 私密路径。
- 用户项目内容。

## 测试

- Secret Persistence Test。
- Log Redaction Test。
- Config Import/Export Test。
- Profile Priority Test。
- Provider Configuration Test。
- Model Fallback Policy Test。

## 验收标准

- 用户能在 UI 中管理主要配置。
- Secrets 不出现在普通配置文件和日志中。
- 配置备份不会包含明文密钥。
- 模型选择行为符合用户指定策略。

## 设计原则

商业化策略尚未确定时，不得臆造价格、订阅等级、强制云服务或收费规则。

首期实现：

- License Interface。
- Entitlement Interface。
- Development Mode。
- Local Evaluation Mode（仅在产品策略明确后启用）。
- Feature Access Policy。

### 1. 核心模型

- License。
- License Validation。
- Device Binding。
- Entitlement。
- Feature Access。
- License Event。
- Offline Grace Policy。

### 2. 授权模式

预留：

- Local License。
- Online License。
- Enterprise License。

不要求首期全部实现。

### 3. 设备绑定

- 使用最小必要设备信息。
- 支持解绑。
- 支持设备更换。
- 不收集不必要的硬件标识。

### 4. 离线行为

- 系统时间回退。
- 时间跳变。
- 离线验证。
- License 过期。
- 验证服务不可用。

不能只依赖客户端系统时间作安全判断。

## 验收标准

- License 与 Entitlement 接口独立于核心业务。
- 开发模式不依赖商业授权服务。
- 授权失败不会破坏用户数据。

- Max Tool Execution。

- Per-Project Budget。

### 4. 磁盘管理

# E12-T16 Reliability & Long-Running Operations

**优先级：P0**

## 目标

确保平台长时间运行和异常情况下可恢复。

### 1. 必须覆盖的场景

- Godot Editor 关闭。
- Godot Editor 重启。
- Backend 崩溃。
- Backend 重启。
- OS 休眠。
- OS 唤醒。
- 网络断开。
- Provider 超时。
- WebSocket 断开。
- 数据库锁竞争。
- 数据库异常。
- Agent 执行中断。
- Tool 执行中断。
- Build 执行中断。
- 更新中断。
- Migration 中断。

### 2. 长时间任务管理

每个 Task、Attempt、Agent Execution、Tool Execution 必须有独立执行记录。

恢复时先检查：

- 当前状态。
- 最后一个持久化事件。
- Checkpoint。
- 外部 Operation ID。
- Resource Lock。
- Fencing Token。
- 实际文件状态。
- 实际 Provider 状态。

### 3. UNKNOWN 处理

所有不确定结果必须先进入状态检查。

禁止：

- 未检查文件就重复写入。
- 未检查 Provider 就重复生成。
- 未检查发布状态就重复发布。
- 未检查数据库就重复 Migration。
- 未检查签名状态就重复签名。

### 4. 故障注入

模拟：

- 随机进程终止。
- 网络丢包。
- API 超时。
- 数据库连接中断。
- 磁盘写入失败。
- 文件权限变更。
- 更新包损坏。
- Migration 中断。
- 系统休眠唤醒。

## 验收标准

- 主要长时间任务具有恢复路径。
- Outbox/Inbox 幂等有效。
- 恢复过程不会产生重复不可逆操作。
- UNKNOWN 状态不会被错误转换为成功或失败。

# 13. 风险管理

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 安装覆盖用户 Plugin | 项目异常 | 变更清单、备份和确认 |
| Migration 失败 | 用户数据损坏 | 备份、校验、恢复演练 |
| 自动更新被篡改 | 供应链攻击 | 签名、Hash、版本防降级 |
| Secrets 泄露 | 用户凭证风险 | OS Credential Store、脱敏 |
| Context 过度发送 | 隐私风险 | Context Preview、排除规则 |
| Godot 版本不兼容 | Plugin 无法使用 | Compatibility Matrix |
| Backend 长时间运行泄漏资源 | 性能下降 | 监控、压力测试、资源治理 |
| Support Bundle 泄露项目内容 | 隐私风险 | 最小化收集、脱敏、用户确认 |
| 过早宣布 GA | 用户信任受损 | 严格 GA Gate |
| 授权策略未定 | 商业架构返工 | 只实现抽象接口和开发模式 |
| 回滚不完整 | 产品无法恢复 | 恢复点和故障演练 |
| API 演进破坏扩展 | 插件生态受损 | 版本化契约和弃用策略 |

# 14. 不可妥协的产品化规则

1. E12 负责平台产品化，不负责重新开发 Demo 游戏。
2. E10 游戏 Release 和 E12 产品 Release 必须完全分离。
3. 产品组件、Plugin、Backend、Agent Definition、Tool Schema 和 DB Migration 全部必须版本化。
4. 安装、升级和卸载不得静默修改用户 Godot 项目。
5. 用户数据备份必须经过真实恢复演练。
6. 不可逆 Migration 必须提前说明。
7. 自动更新必须验证签名和 Hash。
8. 不允许静默强制升级。
9. 不允许默认上传项目源码、资产或诊断数据。
10. Telemetry 默认关闭。
11. Model Context 必须可见并受用户控制。
12. Secrets 不入库、不进日志、不进模型 Context、不进 Support Bundle。
13. Local Backend 默认仅监听 Loopback。
14. 远程访问必须明确授权并具备认证保护。
15. 不支持的 OS、Godot 版本和 Provider 不得宣称兼容。
16. UNKNOWN 不得直接当作成功。
17. 长时间任务必须具有恢复路径。
18. 产品 Release 必须经过独立审批。
19. E11 Demo 通过不等于产品达到 GA。
20. 正式产品必须具有维护周期、漏洞处理和 EOL 策略。
