# 1. 阶段概述

## 1.1 阶段目标

E11 的目标是使用前面 E0–E10 已建立的系统，完成一款真实、可运行、可测试、可构建、可交付的 Godot 2D Platformer Demo 游戏。

本阶段不是单纯开发一款游戏，而是使用这款游戏验证整个 AI Agent 系统的实际工作能力。

系统必须能够：

1. 接收用户的游戏开发需求。
2. 分析需求并形成游戏设计文档。
3. 将需求拆分为可执行 Task。
4. 建立 Workflow 和 Phase。
5. 通过 Orchestrator 分配专业 Agent。
6. 完成项目架构和技术方案。
7. 创建 Godot 项目、Scene、Node 和资源。
8. 生成、处理、导入和管理游戏资产。
9. 编写游戏逻辑和 UI。
10. 操作 Godot Editor 并验证真实编辑器状态。
11. 使用多 Agent 完成分工协作。
12. 通过 ChangeSet 管理项目修改。
13. 通过 Approval 控制高风险操作。
14. 通过 E9 执行自动化测试、Runtime 测试和视觉验证。
15. 修复缺陷并执行回归测试。
16. 通过 E10 完成真实桌面平台导出。
17. 对导出产物执行 Smoke Test。
18. 生成 Release Candidate。
19. 经过用户批准后完成本地交付。
20. 保存完整的开发过程、证据、资产来源和构建来源。

最终必须证明：

**用户提出需求 → AI 设计 → 多 Agent 开发 → Godot Editor 集成 → 资产生产 → 游戏运行 → QA 验证 → 缺陷修复 → Build → Artifact → Release Candidate → 用户批准 → 本地交付**

整个链路能够真实运行，而不是依靠人工手动补齐核心步骤。

## 1.2 本阶段的产品定位

Platformer Demo 是系统级集成验收项目。

它同时承担三个角色：

- 游戏产品：一款真正可以玩的 2D 平台跳跃游戏。
- Agent 实战项目：验证专业 Agent 的开发协作能力。
- 系统验收项目：验证 E0–E10 的架构和功能能否形成完整闭环。

## 1.3 成功标准

不能以以下指标单独判断 E11 成功：

- Agent 能生成代码。
- Agent 能创建 Scene 文件。
- 游戏能在 Editor 中启动。
- 游戏画面看起来完整。
- 单元测试通过。
- 能够生成一个可执行文件。

必须以真实游戏功能、真实 Godot Editor 状态、自动化验证、真实导出产物和可追溯交付证据综合判断。

# 2. 项目范围与游戏规格

## 2.1 游戏类型

第一阶段采用：

- 2D Platformer。
- 单人游戏。
- 横向卷轴。
- 单关卡或短关卡组合。
- 键盘控制。
- 桌面平台运行。

## 2.2 游戏基本规格

建议项目名称：

`Project Platformer Demo`

建议内部代号：

`PF-DEMO-001`

建议采用：

- Godot 4.x 中经 E10 验证的具体稳定版本。
- GDScript。
- 2D Renderer。
- TileMapLayer。
- 2D Animation。
- 2D Physics。
- 本地单机游戏架构。

具体 Godot 次版本必须在项目启动时确定并冻结，不能在项目中途随意升级。

## 2.3 游戏核心玩法

玩家需要在关卡中：

1. 移动。
2. 跳跃。
3. 攻击敌人。
4. 避开陷阱。
5. 收集物品。
6. 获得分数。
7. 完成关卡。

玩家具有生命值。

受到伤害后可以进入短暂无敌状态。

生命归零后进入死亡流程，并根据游戏设计决定是否重生或结束游戏。

## 2.4 必须实现的游戏系统

| 系统 | 必须功能 | 优先级 |
|---|---|---|
| Player | 移动、跳跃、攻击、受伤、死亡 | P0 |
| Physics | 重力、碰撞、平台检测 | P0 |
| Level | TileMapLayer、平台、陷阱 | P0 |
| Enemy | 巡逻、攻击、受伤、死亡 | P0 |
| Combat | 攻击判定、伤害、无敌帧 | P0 |
| Health | 玩家和敌人生命 | P0 |
| Collectible | 收集物、分数 | P0 |
| UI | HUD、生命、分数 | P0 |
| Menu | 主菜单、开始游戏、退出 | P0 |
| Pause | 暂停、恢复 | P0 |
| Game Flow | 开始、失败、胜利、结算 | P0 |
| Animation | 玩家、敌人、UI 动画 | P1 |
| VFX | 跳跃、受伤、死亡、收集效果 | P1 |
| Audio | 背景音乐、动作音效 | P1 |
| Save | 最佳分数或基础进度保存 | P1 |
| Polish | 转场、反馈、视觉优化 | P1 |

P0 是系统级 Demo 验收必须具备的能力。

P1 应在 P0 完成后实施，不得因为视觉包装而影响核心玩法和验收。

## 2.5 游戏不在本阶段实现的内容

以下功能不属于 E11 的强制范围：

- 在线多人。
- 云存档。
- 复杂 RPG 装备系统。
- 复杂技能树。
- 大型开放世界。
- 复杂经济系统。
- 多平台账号系统。
- 复杂剧情分支。
- 大规模 3D 内容。

后续可通过新项目验证。

# 4. E11-T01：需求分析与游戏规格建立

**优先级：P0**

## 4.1 目标

验证系统能否把自然语言需求转换为可追踪的游戏需求。

## 4.2 输入

用户初始需求可以是：

> 创建一款 2D 平台跳跃游戏，玩家可以移动、跳跃和攻击敌人，能够收集物品、避开陷阱，最终完成关卡。

## 4.3 需求分析输出

至少生成：

- Game Concept。
- Core Gameplay Loop。
- Game Mechanics。
- Player Requirements。
- Enemy Requirements。
- Level Requirements。
- UI Requirements。
- Asset Requirements。
- Technical Constraints。
- Acceptance Criteria。
- Out-of-Scope List。

## 4.4 需求追踪

每个需求必须有唯一 ID。

示例：

```text
REQ-PLAYER-001
玩家必须能够向左和向右移动。

REQ-PLAYER-002
玩家必须能够跳跃。

REQ-PLAYER-003
玩家必须能够攻击敌人。

REQ-ENEMY-001
敌人必须能够在指定范围内巡逻。

REQ-LEVEL-001
关卡必须包含可碰撞的平台。

REQ-UI-001
HUD 必须显示玩家生命值。

REQ-FLOW-001
玩家完成关卡后必须进入胜利结算。
```

## 4.5 Acceptance Criteria

每条需求必须具有可验证的验收条件。

例如：

REQ-PLAYER-002：

- 玩家在地面时按下跳跃键，能够向上移动。
- 玩家在空中重复按跳跃键时，不能触发未经设计的额外跳跃。
- 玩家落地后可以再次跳跃。
- 玩家不能穿过平台。

验收条件必须能够转化为 E9 测试用例。

## 4.6 交付物

- Game Requirement Document。
- Requirement Registry。
- Acceptance Criteria Registry。
- Requirement Traceability Matrix。
- Scope Baseline。

7. 避免过度耦合。
8. 关卡逻辑和玩家控制逻辑分离。
9. 资产路径必须稳定。
10. Scene 和 Resource 的引用关系必须可验证。

# 9. E11-T06：Combat System 战斗系统

**优先级：P0**

## 9.1 目标

建立玩家、敌人、攻击判定和伤害接收之间的统一系统。

## 9.2 参与 Agent

- `gameplay_programmer`
- `game_systems_programmer`
- `signal_interaction_specialist`
- `scene_developer`

## 9.3 核心模块

- Hitbox。
- Hurtbox。
- Damage Data。
- Damage Receiver。
- Attack Controller。
- Knockback Handler。
- Invulnerability Handler。

## 9.4 Damage Data

建议字段：

```text
damage
knockback_force
damage_type
source_id
attack_id
hit_position
timestamp
```

## 9.5 战斗规则

1. Hitbox 与 Hurtbox 通过明确 Layer/Mask 过滤。
2. 一次攻击不能无限重复造成伤害。
3. 同一个攻击对同一个目标的命中次数必须受规则限制。
4. 无敌状态不能重复扣血。
5. 死亡状态不能继续接受普通攻击。
6. 伤害事件必须有来源。
7. 战斗数值必须可配置。

## 9.6 验收

- [ ] 攻击可以命中敌人。
- [ ] 伤害正确。
- [ ] 无效碰撞不会造成伤害。
- [ ] 重复命中受到控制。
- [ ] 无敌状态有效。
- [ ] 死亡目标不会继续正常战斗。
- [ ] Combat 事件可以追踪。

# 10. E11-T07：Enemy System 敌人系统

**优先级：P0**

## 10.1 目标

建立可配置的敌人基础结构。

## 10.2 参与 Agent

- `gameplay_programmer`
- `game_systems_programmer`
- `scene_developer`
- `animation_specialist`

## 10.3 Enemy Base

建议结构：

```text
Enemy (CharacterBody2D)
├── Sprite2D / AnimatedSprite2D
├── CollisionShape2D
├── AnimationPlayer
├── DetectionArea (Area2D)
├── AttackArea (Area2D)
├── Hurtbox (Area2D)
└── HealthComponent
```

## 10.4 巡逻行为

必须实现：

- 左右巡逻。
- 移动范围。
- 边缘检测。
- 转向。
- 碰撞处理。
- 玩家检测。

## 10.5 攻击行为

可以采用简单攻击机制：

# 22. E11-T19：系统稳定性与故障恢复验收

**优先级：P0**

## 22.1 目标

验证整套系统在异常情况下是否能够保持数据安全和状态一致。

## 22.2 故障场景

必须模拟：

- Godot Editor 关闭。
- Godot Editor 崩溃。
- Backend 重启。
- Runtime Bridge 断开。
- Agent 执行超时。
- Model Provider 超时。
- Tool 执行失败。
- ChangeSet 应用中断。
- 资产导入中断。
- Verification 中断。
- Build Executor 断线。
- 数据库写入失败。
- Release 请求响应丢失。

## 22.3 恢复原则

1. 不得丢失已提交的 ChangeSet。
2. 不得把未完成 Task 自动标记为成功。
3. 不得将 UNKNOWN 验证结果标记为通过。
4. 不得丢失 Artifact Hash 和来源信息。
5. 不得重复执行未知结果的外部操作。
6. 不得在恢复时静默覆盖用户文件。
7. 不得自动绕过审批。
8. 必须记录恢复动作。

## 22.4 一致性验收

验证：

- Task 状态一致。
- Workflow 状态一致。
- Agent Instance 状态一致。
- Approval 状态一致。
- ChangeSet 状态一致。
- Verification 状态一致。
- Build 状态一致。
- Release 状态一致。

各模块只能通过公开接口协调状态，不能由某个模块直接修改其他模块的数据。

1. 创建缺陷 Task。

4. 生成 ChangeSet。
5. 执行审批。
6. 应用变更。
7. 执行回归测试。

## 27.4 自动化测试边界

测试脚本不得依赖固定运行时延迟来猜测游戏状态。

优先使用：

- 明确的状态事件。
- 可观察的节点状态。
- 受控输入。
- Runtime Probe。
- Test Instrumentation。

视觉测试可以使用截图，但不能只凭截图认定碰撞、伤害或游戏逻辑正确。

# 29. E11 风险管理

| 风险 | 影响 | 应对 |
|---|---|---|
| 需求范围过大 | 项目无法按期完成 | P0/P1 分级 |
| Agent 生成错误代码 | 游戏无法运行 | Editor 检查和自动测试 |
| 多 Agent 冲突 | 文件覆盖 | Resource Lock、ChangeSet |
| Scene 结构错误 | 运行时错误 | Editor Bridge 验证 |
| 资源引用错误 | 资产丢失 | Import Evidence、UID 检查 |
| 玩法设计不完整 | 无法通关 | Acceptance Criteria |
| UI 和逻辑耦合 | 难以维护 | Game Flow 独立 |
| 测试不真实 | 假通过 | Runtime Evidence |
| 视觉验证误判 | 质量缺陷 | 结合结构和功能测试 |
| 模型调用不稳定 | 工作中断 | Checkpoint、Retry Policy |
| Token 或成本超限 | 项目预算失控 | Agent Budget Manager |
| Editor 状态冲突 | 用户修改丢失 | 未保存状态检测 |
| 构建环境不一致 | 导出失败 | Environment Fingerprint |
| Release 证据缺失 | 无法交付 | Release Gate |
| 系统恢复失败 | 状态不一致 | Fault Injection |
