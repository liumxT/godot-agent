# 1. 阶段概述

## 1.1 阶段定位

E2 是 Backend 从内部基础服务转向对外提供服务的阶段。

E1 已经建立了：

- Backend 生命周期。
- 配置服务。
- SQLite 数据库服务。
- Migration。
- Repository。
- 事务管理。
- 日志和异常处理。
- 事件基础设施。
- Outbox/Inbox。
- 数据备份和恢复。
- Health Check。

E2 在这些能力之上，建立统一的 Backend API Server、身份认证、会话管理、权限检查和客户端访问体系。

完成 E2 后，Godot Plugin 应能够通过受保护的本地接口与 Backend 通信，并获得稳定、统一的服务响应。

## 1.2 阶段目标

| 编号 | 目标 | 完成标准 |
|---|---|---|
| E2-G01 | API Server | Backend 能提供统一服务接口 |
| E2-G02 | API 路由体系 | 路由、版本和接口注册统一 |
| E2-G03 | 身份认证 | 未授权客户端不能访问受保护接口 |
| E2-G04 | Session 管理 | 支持客户端会话创建、验证和撤销 |
| E2-G05 | 客户端管理 | 能够识别不同 Editor 客户端 |
| E2-G06 | 项目隔离基础 | 不同项目的数据访问边界明确 |
| E2-G07 | 权限检查 | 请求执行前能够验证权限 |
| E2-G08 | 请求处理机制 | 支持验证、限流、超时和错误转换 |
| E2-G09 | 审计日志 | 关键操作可追踪 |
| E2-G10 | API 文档 | 提供完整接口定义和调用说明 |
| E2-G11 | 服务安全 | 本地通信具有基本安全保护 |
| E2-G12 | 服务测试 | API、认证、权限和异常通过测试 |

## 1.3 本阶段范围

本阶段实现 Backend 的通用服务能力。

不实现以下完整业务：

- Project Intelligence。
- Task System。
- Workflow Engine。
- Agent Runtime。
- Model Gateway。
- Tool Execution。
- Multi-Agent Orchestration。
- Asset Pipeline。
- Verification。
- Godot Editor Bridge。

这些业务会在后续阶段通过 E2 的 API、Session 和权限体系接入。

# 2. 整体架构设计

## 2.1 Backend Services 架构

```text
              Local Client
             Godot Plugin
                  |
                  v
             API Server
                  |
        Request Middleware
                  |
       Authentication Layer
                  |
          Session Resolver
                  |
          Authorization
                  |
            API Router
                  |
          Application Services
                  |
             Core Layer
                  |
       Database / Event / Log
```

## 2.2 模块划分

| 模块 | 职责 |
|---|---|
| API Server | HTTP 服务启动和监听 |
| Router | API 路由注册和分发 |
| Middleware | 请求预处理和后处理 |
| Authentication | 客户端身份验证 |
| Session Service | 会话创建、验证和撤销 |
| Client Registry | 客户端身份与状态管理 |
| Project Access | 项目访问边界 |
| Authorization | 权限检查 |
| Rate Limiter | 请求频率限制 |
| Request Validator | 请求格式验证 |
| Response Formatter | 统一响应格式 |
| Audit Service | 关键操作审计 |
| API Documentation | 接口文档生成 |

## 2.3 技术架构原则

1. 所有外部请求统一经过 API Server。
2. API 层不直接操作数据库。
3. API 层不绕过业务模块调用 Repository。
4. 认证和权限必须分离。
5. Session 不能等同于用户身份。
6. 项目访问权限不能仅依靠客户端传入 Project ID。
7. 所有敏感操作必须经过服务端授权。
8. 不信任来自客户端的权限声明。
9. 错误响应必须统一。
10. 本地运行不代表不需要认证和访问控制。

# 3. API Server 设计

## 3.1 E2-T01：API Server 基础实现

**优先级：** P0  
**依赖：** E1-T01、E1-T02、E1-T08

### 开发目标

```text

├── api/
│   ├── server/
│   │   ├── server.py
│   │   ├── lifecycle.py
│   │   └── listener.py
│   │
│   ├── routers/
│   ├── middleware/
│   ├── schemas/
│   ├── responses/
│   └── documentation/

```

### 实施步骤

1. 创建 API Server 入口。
2. 创建 Listener。
3. 实现服务启动和关闭。
4. 绑定配置中的本地监听地址。
5. 实现统一路由注册。
6. 实现请求解析。
7. 实现响应输出。
8. 实现异常转换。
9. 实现服务健康检查接口。
10. 实现请求日志。

### 网络监听规则

默认仅允许绑定本机回环地址。

例如：

```text
127.0.0.1
::1
```

不得默认绑定：

```text
0.0.0.0
```

如果未来需要远程连接，必须通过单独的远程访问配置和安全评审启用。

### 验收标准

- API Server 能正常启动和关闭。
- 未授权请求不能访问受保护接口。
- 端口占用能够明确报告。
- 请求失败能够返回统一错误格式。

# 4. 身份认证系统

## 4.1 E2-T03：本地客户端身份认证

**优先级：** P0  
**依赖：** E2-T01、E2-T02

### 开发目标

建立 Backend 与本地客户端之间的身份认证机制。

Godot Plugin 不是可信任的认证来源。客户端必须通过 Backend 认可的方式证明自身持有有效凭证。

### 认证对象

- Godot Editor Plugin。
- 本地管理工具。
- 未来其他授权客户端。

### 认证流程

```text
客户端启动
    |
    v
请求认证挑战
    |
    v
Backend 返回 Challenge
    |
    v
客户端证明持有有效凭证
    |
    v
Backend 验证
    |
    v
认证成功？
  ├─ 否：拒绝
  └─ 是：创建认证结果
```

### 实施步骤

1. 定义 Client Identity。
2. 定义认证挑战结构。
3. 定义挑战有效期。
4. 定义认证凭证存储接口。
5. 实现 Challenge 生成。
6. 实现 Challenge 验证。
7. 实现重放攻击防护。
8. 实现认证失败计数。
9. 实现认证失败日志。
10. 实现凭证撤销。

### 安全要求

- 使用安全随机数。
- Challenge 必须短期有效。
- Challenge 必须一次性使用。
- 不允许在普通日志中输出凭证。
- 不允许在普通配置文件中保存明文认证 Secret。
- 认证失败应进行适当的速率限制。

### 测试

- E2-T03-UT-001：正常认证。
- E2-T03-UT-002：无效凭证。
- E2-T03-UT-003：Challenge 过期。
- E2-T03-UT-004：重复 Challenge。
- E2-T03-UT-005：重放攻击。
- E2-T03-UT-006：凭证撤销。

## 4.2 E2-T04：认证 Token 管理

**优先级：** P0  
**依赖：** E2-T03

### 开发目标

建立认证成功后的请求凭证机制。

### Token 要求

- 具有唯一标识。
- 具有有效期。
- 可以撤销。
- 不能从客户端提供的普通字段中推断权限。
- 不应在日志中暴露。
- 应支持安全轮换。

### Token 分类

| 类型 | 用途 |
|---|---|
| Access Token | 短期访问 Backend |
| Refresh Credential | 在满足条件时更新访问凭证 |
| Session Token | 关联具体会话 |
| One-time Challenge | 一次性认证证明 |

具体是否使用独立 Refresh Credential，应在技术评审中结合本地运行场景决定。

### 实施步骤

1. 定义 Token 数据模型。
2. 定义 Token 生成规则。
3. 实现有效期检查。
4. 实现撤销机制。
5. 实现 Token 轮换。
6. 实现 Token 安全存储。
7. 实现 Token 与 Client Identity 绑定。
8. 实现过期清理。

### 验收标准

Token 无效、过期或撤销后，受保护接口必须拒绝访问。

## 6.2 E2-T08：Authorization 权限检查服务

**优先级：** P0  
**依赖：** E2-T03、E2-T05、E2-T07

### 开发目标

建立统一权限决策服务。

### 权限模型

采用 RBAC + ABAC + Capability 的组合方式。

- RBAC：角色权限。
- ABAC：基于资源、项目和上下文的属性判断。
- Capability：限定某次操作能够执行的具体能力。

### 权限检查输入

```text
principal
action
resource
project_scope
session
context
```

### 权限检查结果

```text
decision
reason
policy_id
checked_at
```

decision：

```text
ALLOW
DENY
```

### 权限判断流程

```text
收到请求
   |
   v
验证认证
   |
   v
验证 Session
   |
   v
验证 Project Access
   |
   v
检查 Role
   |
   v
检查 Attributes
   |
   v
检查 Capability
   |
   v
最终决策
```

### 核心安全原则

**UNKNOWN 默认 DENY。**

以下情况必须拒绝：

- 身份未知。
- Session 无效。
- 项目访问关系未知。
- 权限规则缺失。
- Capability 未授权。
- 资源归属不明确。

### 实施步骤

1. 创建 Principal 模型。
2. 创建 Action 定义。
3. 创建 Resource 定义。
4. 创建 Permission Policy 接口。
5. 创建 Authorization Service。
6. 实现 RBAC 检查。
7. 实现 ABAC 检查。
8. 实现 Capability 检查。
9. 实现权限决策记录。
10. 实现权限测试工具。

### 测试

- Session 创建。

- Project Access 授予。
- Project Access 撤销。

action

decision

### 审计要求

## 11.4 安全测试

必须验证：

1. 未认证请求无法访问受保护接口。
2. 过期 Token 无法访问。
3. 已撤销 Token 无法访问。
4. Session 不能跨 Client 使用。
5. Project ID 篡改不能越权。
6. 未知权限默认拒绝。
7. 不可信客户端不能自行授予权限。
8. Challenge 不能重复使用。
9. Token 不进入日志。
10. 非法大请求不会耗尽 Backend 资源。
11. API 默认不监听公网接口。
12. 诊断接口不能泄露敏感数据。

## 11.5 故障注入

- API Server 端口被占用。
- 数据库临时不可用。
- 认证凭证存储不可用。
- Session 数据异常。
- 请求处理中断。
- 审计写入失败。
- 限流器异常。
- 客户端断开连接。
- Backend 关闭期间收到请求。

# 14. E2 风险管理

| 风险编号 | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| E2-R01 | 认证设计不完整 | 未授权访问 | 先完成威胁分析 |
| E2-R02 | Session 和 Client 混淆 | 身份错乱 | 独立模型和状态管理 |
| E2-R03 | Project ID 越权 | 跨项目数据泄露 | 服务端 Project Access 校验 |
| E2-R04 | 权限判断分散 | 安全漏洞 | 统一 Authorization Service |
| E2-R05 | 本地服务被其他程序访问 | 未授权操作 | 回环监听、认证、挑战验证 |
| E2-R06 | API 版本变化 | 插件兼容问题 | 契约测试和版本管理 |
| E2-R07 | 审计信息泄露 | 安全风险 | 日志脱敏和权限保护 |
| E2-R08 | 限流策略不合理 | 正常请求被拒绝 | 通过实际测试调整参数 |

# 15. E2 阶段结束后的下一阶段准入条件

E2 验收通过后，进入 E3 Godot Integration。

E3 将实现：

- Godot Editor Plugin 生命周期完善。

- 本机 WebSocket 通信。
- Challenge-Response。
- Session Token。
- Heartbeat。
- Session Lease。

- Godot Editor 状态同步。
- Runtime Bridge 基础连接。
- Editor 和 Runtime 状态边界管理。

**E2 的最终目标是让 Backend 具备安全、统一、可追踪的服务能力，为 Godot 编辑器接入和后续 AI Agent 业务提供稳定入口。**
