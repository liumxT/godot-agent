# 1. 阶段概述

## 1.1 阶段目标

E8 的目标是建立一套完整、可追溯、可恢复、可审计的游戏资产生产与管理管线。

系统需要支持：

1. 资产需求定义。
2. 资产规格管理。
3. AI 图片生成。
4. AI 音频生成。
5. 3D 资产适配器基础。
6. 资产版本管理。
7. 资产处理与转换。
8. Sprite Sheet 和 Tileset 处理。
9. 资产技术质量检测。
10. 人工美术审核。
11. 资产来源追踪。
12. License 与使用权管理。
13. Godot Editor 真实导入。
14. Godot UID 和引用关系验证。
15. 资产依赖图管理。
16. 资产交付与 ChangeSet 管理。
17. 失败任务恢复。
18. Agent 与资产生产系统集成。

E8 不只是一个 AI 图片生成接口，也不是一个文件上传管理器。

它是连接游戏设计、专业 Agent、AI Provider、资产处理工具、Godot Editor 和项目文件系统的完整生产系统。

## 1.2 E8 完成后的能力

用户可以提出：

“为 Platformer Demo 制作一组统一风格的像素美术资产。”

系统能够完成：

- 读取游戏设计和美术方向。
- 生成 Asset Brief。
- 确定角色、敌人、地图、UI、特效和音效所需资产。
- 分配给对应专业 Agent。
- 生成资产。
- 记录生成来源。
- 检查生成结果。
- 处理透明背景、尺寸、格式和动画帧。
- 生成 Sprite Sheet。
- 检查帧间一致性。
- 进行人工审核。
- 检查 License。
- 创建资产版本。
- 经 Tool System 写入项目。
- 通过 Godot Editor 导入。
- 获取真实 UID。
- 检查资源引用。
- 更新资产依赖关系。
- 将合格资产交付给 Workflow。
- 由用户进行最终验收。

## 1.3 资产生命周期

系统必须区分以下阶段：

**Generation → Processing → Quality Review → License Review → Approval → Project Write → Godot Import → Verification → Delivery**

以下概念不能混为一谈：

- 生成成功不等于质量通过。
- 质量通过不等于 License 合格。
- License 合格不等于项目写入成功。
- 项目写入成功不等于 Godot Import 成功。
- Godot Import 成功不等于资源引用完整。
- 资源引用完整不等于资产可以正式交付。

资产只有通过所有适用门禁后，才能成为正式可交付资产。

## 3.2 架构原则

1. Asset Pipeline 不直接调用 AI 厂商 API。
2. Asset Pipeline 不绕过 Model Gateway。
3. Agent 不直接写项目文件。
4. Asset Pipeline 不自行授予文件写入权限。
5. 所有项目写入必须经 Tool System。
6. 所有项目写入必须关联 ChangeSet。
7. 需要审批的操作必须经 Approval System。
8. 文件写入必须使用 Resource Lock。
9. Godot UID 必须来自真实 Godot Import 或 Editor 扫描。
10. 资产版本不可变。
11. 所有生成和处理任务必须可审计。
12. 所有重要操作必须支持恢复。
13. License 未知不能作为正式交付资产。
14. 技术质量与授权状态分别管理。
15. 所有模块通过公开 Contract 通信。

# 5. 详细开发任务

# E8-T01 Asset Domain & Contract

**优先级：P0**

## 5.1 目标

建立资产领域模型和统一 Contract。

资产不能只用一个文件路径表示。

一个逻辑资产可能包含：

- 多个不可变版本。
- 多个分辨率。
- 多种格式。
- 多个生成结果。
- 多个处理任务。
- 多次导入记录。
- 多个来源。
- 多种授权凭证。
- 多轮质量审核。
- 多个项目引用。

## 5.2 核心实体

## 5.3 状态模型

资产、生成、处理、导入、授权、审核必须独立拥有状态。

Asset 生命周期：

```text
DRAFT
  |
  v
ACTIVE
  |
  v
DEPRECATED
  |
  v
ARCHIVED
```

Generation：

```text
CREATED
  |
  v
SUBMITTED
  |
  v
RUNNING
  |
  +----> SUCCEEDED
  |
  +----> FAILED
  |
  +----> UNKNOWN
  |
  +----> CANCELLED
```

Processing：

```text
QUEUED
  |
  v
RUNNING
  |
  +----> SUCCEEDED
  |
  +----> FAILED
  |
  +----> UNKNOWN
```

Import：

```text
NOT_IMPORTED
  |
  v
IMPORT_REQUESTED
  |
  v
IMPORTING
  |
  +----> IMPORTED
  |
  +----> FAILED
  |
  +----> UNKNOWN
```

Quality：

```text
NOT_REVIEWED
  |
  v
MACHINE_REVIEWED
  |
  +----> HUMAN_REVIEW_REQUIRED
  |
  +----> REJECTED
  |
  +----> APPROVED
```

License：

```text
UNKNOWN
  |
  v
PENDING_REVIEW
  |
  +----> VERIFIED
  |
  +----> REJECTED
  |
  +----> EXPIRED
```

## 5.4 关键实现要求

- 每个状态有明确的所有者。
- 禁止跨模块直接更新状态。
- 版本创建后禁止修改内容。
- 内容变化必须创建新版本。
- 版本必须保存 Content Hash。
- 所有异步操作都需要 Job ID。
- 状态变化必须产生 Domain Event。

## 5.5 验收标准

- 所有实体具有独立 Contract。
- Asset 和 AssetVersion 分离。
- Generation、Processing、Import 分离。
- Provenance 和 License 分离。
- Quality Review 与 License Review 分离。
- 状态转换有合法性检查。
- 不合法转换返回统一错误。

## 6.2 功能

- 创建 Asset。
- 查询 Asset。
- 按类别过滤。
- 按标签过滤。
- 按文件类型过滤。
- 按版本查询。
- 按状态查询。
- 按来源查询。
- 按 License 状态查询。
- 查询项目资产。
- 查询资产引用。
- 查询重复资产。
- 查询孤儿资产。

## 6.3 分类体系

```text
ASSET
├── IMAGE
│   ├── CHARACTER
│   ├── ENEMY
│   ├── TILESET
│   ├── BACKGROUND
│   ├── UI
│   ├── ICON
│   ├── VFX

├── AUDIO
│   ├── SFX
```

## 6.4 目录管理

建议项目目录：

```text
res://
├── assets/
│   ├── characters/
│   ├── enemies/
│   ├── tilesets/
│   ├── backgrounds/
│   ├── ui/
│   ├── vfx/
│   ├── audio/
│   ├── textures/
│   └── models/
```

资产管理系统内部存储：

```text

└── assets/

        └── {project_id}/
```

## 6.5 测试

# E8-T03 Asset Versioning

**优先级：P0**

## 7.1 目标

建立不可变版本体系。

## 7.2 版本规则

例如：

```text
player_character
├── v001
│   ├── source.png
│   └── metadata.json
├── v002
│   ├── source.png
│   └── metadata.json
└── v003
    ├── source.png
    └── metadata.json
```

版本之间使用：

- parent_version_id。
- content_hash。
- change_reason。
- provenance_id。

## 7.3 变体管理

```text
player_character
├── idle
├── run
├── jump
├── attack
├── hurt
└── death
```

同一角色的不同动画可以通过 Variant 关联。

不同分辨率、格式和导入配置也可以建立 Variant。

## 7.4 回滚规则

回滚不是修改旧版本，而是将当前引用切换到已存在版本。

回滚操作必须：

1. 生成变更计划。
2. 计算引用影响。
3. 检查 Resource Lock。
4. 创建 ChangeSet。
5. 获取审批。
6. 执行引用更新。
7. 验证 Godot Import。
8. 保存回滚记录。

## 7.5 验收标准

- 版本不可变。
- 每个版本具有 Hash。
- 版本之间存在关系。
- 支持版本比较。
- 支持回滚。
- 回滚可审计。
- 不允许静默覆盖正式版本。

# E8-T04 Asset Brief & Specification

**优先级：P0**

## 8.1 目标

将游戏需求转化为可执行的资产规格。

不能只让 Agent 输出一句：

“生成一个像素风格角色。”

必须产生结构化 Asset Brief。

## 8.2 Asset Brief

```text
AssetBrief
- id
- project_id
- task_id
- asset_category
- visual_direction
- style_reference
- technical_constraints
- animation_requirements
- delivery_requirements
- license_requirements
- acceptance_criteria
```

## 8.3 图像规格

包括：

- 宽度。
- 高度。
- 宽高比。
- 透明背景。
- Alpha 要求。
- 色彩空间。
- 文件格式。
- 位深。
- 是否允许抗锯齿。
- 像素风格约束。
- 角色主体位置。
- Sprite Sheet 网格。
- 帧数量。
- 每帧尺寸。
- 动画 FPS。
- 循环规则。
- 图集 Padding。
- Texture Filtering。

## 8.4 音频规格

包括：

- 格式。
- 采样率。
- 声道。
- 时长。
- 峰值。
- 音量范围。
- 循环点。
- 是否需要无缝循环。
- 是否需要淡入淡出。
- 是否需要语音字幕。
- 目标播放用途。

## 8.5 Godot 资源规格

必须支持：

- Sprite2D。
- AnimatedSprite2D。
- Texture2D。
- AtlasTexture。
- TileSet。
- TileMapLayer。
- AudioStream。
- AudioStreamPlayer2D。
- AudioStreamPlayer。
- StandardMaterial3D。
- MeshInstance3D。

## 8.6 验收标准

- 每个生成任务关联 Asset Brief。
- 每个 Brief 具有技术规格。
- 规格可以由 Agent 提出。
- 用户可以确认或修改规格。
- 生成结果可以自动与规格比较。
- 规格变更创建新版本或新 Generation Request。

# E8-T05 Generation Orchestrator

**优先级：P0**

## 9.1 目标

统一管理所有资产生成任务。

## 9.2 模块职责

Generation Orchestrator 负责：

1. 接收 Generation Request。
2. 校验 Asset Brief。
3. 检查权限。
4. 检查预算。
5. 检查 Provider 能力。
6. 选择适配器。
7. 创建 Generation Job。
8. 调用 Model Gateway。
9. 跟踪外部任务。
10. 获取生成结果。
11. 保存原始产物。
12. 创建 AssetVersion。
13. 写入 Provenance。
14. 发布事件。

## 9.3 Provider 选择

优先级：

1. 用户指定 Provider。
2. 用户指定 Model。
3. 项目配置的 Provider Policy。
4. 满足规格的可用 Provider。
5. 用户批准的默认策略。

禁止在用户指定模型不可用时静默切换到其他模型。

Provider 能力未知时，必须视为不满足能力要求，除非经过明确验证。

## 9.4 Job 管理

每个外部生成请求必须保存：

- internal_job_id。
- provider_job_id。
- request_hash。
- provider。
- model。
- budget reservation。
- submitted_at。
- last_checked_at。
- result_reference。
- status。

## 9.5 幂等要求

使用：

```text
generation_idempotency_key
```

同一个逻辑请求不能因为网络超时而重复收费。

外部请求已提交但响应丢失时：

1. 查询 Provider Job。
2. 检查 request ID。
3. 检查结果状态。
4. 只有确认未提交，才允许重新提交。

无法确认时保持 UNKNOWN。

## 9.6 验收标准

- 所有生成任务统一管理。
- Provider 调用经过 Model Gateway。
- 支持异步任务。
- 支持状态查询。
- 支持预算限制。
- 支持幂等。
- 支持 UNKNOWN。
- 支持审计。

## 10.1 目标

# E8-T16 Asset Pipeline Recovery

**优先级：P0**

## 20.1 目标

建立跨 Provider、Processing、File System、Godot Editor 的恢复机制。

## 20.2 典型故障

- Provider 请求提交成功但响应超时。
- Provider 生成完成但 Backend 断线。
- 文件下载完成但数据库事务失败。
- Processing 完成但结果登记失败。
- 项目文件写入完成但 Editor 断线。
- Import 完成但回执丢失。
- UID 获取成功但数据库写入失败。
- 用户审批完成后资产内容变化。
- 资产写入中 Resource Lock 过期。

## 20.3 UNKNOWN 处理原则

UNKNOWN 不是 FAILED。

遇到 UNKNOWN：

1. 查询外部 Provider。
2. 查询外部 Job ID。
3. 检查已有产物。
4. 校验 Hash。
5. 检查 Processing Job。
6. 检查项目文件。
7. 查询 Godot Editor Session。
8. 查询真实 Import 状态。
9. 根据证据恢复状态。

不能确认时保持 UNKNOWN，并交给 Recovery Coordinator。

## 20.4 幂等机制

为每个操作建立幂等键：

```text
generation:{generation_id}
processing:{processing_job_id}
project_write:{changeset_id}
import:{import_job_id}
delivery:{delivery_id}
```

不能仅依靠任务名称判断重复。

## 20.5 补偿操作

可能的补偿：

- 删除未交付的临时文件。
- 保留原始版本。
- 恢复旧引用。
- 重新生成 ChangeSet。
- 释放过期资源锁。
- 重新获取 Import Evidence。
- 将异常资产标记为 QUARANTINED。

补偿不等于数据库回滚。

对于已发生的外部 Provider 收费、项目文件写入和 Editor Import，必须记录实际结果。

## 20.6 验收标准

- 所有重要 Job 支持恢复。
- UNKNOWN 不会盲目重试。
- 不会重复收费或重复写入。
- 断线后能检查真实状态。
- 恢复操作有审计日志。
