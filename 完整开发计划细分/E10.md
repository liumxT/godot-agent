# 1. 阶段概述

## 1.1 阶段目标

E10 的目标是建立完整、可审计、可恢复、具有安全门禁的 Godot 游戏构建与发布系统。

系统需要能够：

1. 检查 Godot 项目的构建条件。
2. 管理 Godot Export Presets。
3. 检查 Godot Engine、Export Templates、平台 SDK 和签名工具。
4. 通过受控执行器启动 Godot Headless Build。
5. 支持不同桌面平台的构建与导出。
6. 管理构建任务、执行尝试、构建日志和构建环境。
7. 注册和管理不可变构建制品。
8. 生成带有 Manifest 的交付包。
9. 管理签名配置和签名验证。
10. 生成 Release Candidate。
11. 将 E9 验证结果与最终导出制品关联。
12. 执行制品完整性检查和 Smoke Test。
13. 管理 Release Approval。
14. 支持本地交付、用户下载和未来的外部分发渠道。
15. 支持构建、签名、打包和发布过程的故障恢复。
16. 通过专业 Agent 协助完成构建和发布工作。

最终形成以下闭环：

**Project Revision → Build Configuration → Environment Check → Build → Export → Artifact Registration → Package → Artifact Verification → Release Candidate → Approval → Release → Distribution → Post-release Verification**

## 1.2 阶段边界

E10 负责构建与发布，不负责重新实现前面阶段的核心系统。

| 系统 | 所有权 |
|---|---|
| Project System | 项目身份、项目版本及项目访问权限 |
| ChangeSet Manager | 项目变更及变更审批 |
| Workflow Engine | Workflow 和 Phase 状态 |
| Task System | Task 状态 |
| Agent Runtime | Agent Instance 状态 |
| Tool System | 受控工具执行 |
| Asset Pipeline | 资产版本、来源、许可和导入证据 |
| Verification System | 验证计划、结果和证据 |
| Approval System | 审批状态 |
| Build & Release | Build、Artifact、Package、Release 生命周期 |

E10 不得直接修改其他模块拥有的状态。

## 1.3 核心设计原则

### P01：构建流程必须分阶段

以下操作是不同的业务行为：

- Build：执行构建任务。
- Export：生成目标平台可运行产物。
- Package：组织和封装交付文件。
- Sign：对制品执行数字签名。
- Release：创建并执行正式发布。
- Distribution：将制品交付到具体渠道。

不能将其中一个步骤的成功当作整个流程成功。

### P02：所有构建命令必须经过受控执行器

Agent 不得直接执行任意 Shell 命令。

所有构建操作必须经过 Build Executor，并执行：

- 命令白名单。
- 参数校验。
- 工作目录限制。
- 环境变量白名单。
- 超时限制。
- CPU、内存、磁盘预算。
- 日志脱敏。
- 执行记录。
- 取消和恢复管理。

### P03：Artifact 必须不可变

已经注册的 Artifact 不允许原地修改。

如果内容发生变化，必须生成新的 Artifact Version 和新的 Hash。

### P04：发布审批必须绑定制品内容

Release Approval 必须绑定：

- Artifact Hash。
- Package Manifest Hash。
- Release Candidate Manifest Hash。
- 目标平台。
- 发布渠道。
- 版本号。
- 审批策略版本。

任意关键内容变化，都必须重新审批。

### P05：构建结果必须有真实证据

以下情况不能视为构建成功：

- 只成功启动 Godot 进程。
- 只生成了部分文件。
- 只完成 Editor 中的运行测试。
- 只获得命令退出码为 0，但未检查实际导出产物。
- 只生成了 Package，但未检查其内容。

### P06：UNKNOWN 不能直接重试

当构建、签名或发布操作状态不明确时，必须先检查实际执行状态、输出文件、Hash、外部操作 ID 和渠道状态。

不能因为客户端超时就立即重新构建或重复发布。

### P07：首期以桌面平台为主

优先支持：

- Windows
- macOS
- Linux

移动端、Web、主机平台按工具链、平台权限和适配器能力逐步扩展。

不支持的平台不得显示为已具备可用导出能力。

# 4. E10-T01：Build & Release Domain & Contract

**优先级：P0**

## 4.1 目标

建立构建与发布领域模型、统一状态定义、事件结构和跨模块 Contract。

## 4.2 核心实体

### Build

表示一次逻辑构建任务。

建议字段：

- build_id
- project_id
- build_config_id
- source_revision
- changeset_id
- status
- created_by
- created_at
- updated_at

### Build Attempt

表示一次实际执行尝试。

字段：

- attempt_id
- build_id
- attempt_number
- executor_id
- started_at
- finished_at
- exit_code
- status
- log_reference
- environment_fingerprint
- error_code

同一个 Build 可以有多个 Attempt。

重试必须创建新的 Attempt，不得覆盖旧记录。

### Artifact

## 4.4 统一状态定义

### Build 状态

```text
QUEUED
  → PREPARING
  → RUNNING
  → EXPORTING
  → COLLECTING
  → SUCCEEDED
  → FAILED
  → CANCELLED
  → UNKNOWN
```

`UNKNOWN` 表示执行结果尚未确认，不是失败，也不是成功。

### Artifact 状态

```text
REGISTERED
  → VERIFYING
  → VERIFIED
  → REJECTED
  → QUARANTINED
```

Artifact 的内容一旦注册不可修改。验证状态变化不改变制品内容。

### Release Candidate 状态

```text
DRAFT
  → VALIDATING
  → READY_FOR_APPROVAL
  → APPROVED
  → REJECTED
  → SUPERSEDED
```

### Release 状态

```text
PENDING
  → AUTHORIZED
  → DISTRIBUTING
  → PUBLISHED
  → POST_VERIFYING
  → COMPLETED
```

异常状态：

```text
FAILED
UNKNOWN
WITHDRAWN
ROLLED_BACK
```

不得将 `ROLLED_BACK` 解释为历史发布记录不存在。

- release.approval.completed

所有事件必须包含：

- schema_version

# 5. E10-T02：Build Configuration Registry

**优先级：P0**

## 5.1 目标

建立版本化构建配置管理系统。

## 5.2 构建配置内容

每个 Build Configuration 至少包含：

- configuration_id
- project_id
- name
- version
- Godot version constraint
- target platform
- architecture
- renderer
- export preset reference
- debug/release mode
- feature tags
- output format
- environment variable allowlist
- build timeout
- resource budget
- packaging policy
- verification policy

## 5.3 配置版本管理

规则：

1. 已经用于构建的配置必须保留历史快照。
2. 修改配置产生新版本。
3. Build Attempt 必须记录使用的配置版本。
4. Release Candidate 必须绑定对应配置快照。
5. Agent 不能静默修改用户配置。
6. 配置中不得保存明文 Secret。

## 5.4 配置校验

检查：

- Godot 版本是否支持目标平台。
- 架构是否受支持。
- Export Preset 是否存在。
- Export Template 是否可用。
- 输出路径是否合法。
- 是否存在不允许的环境变量。
- 是否超出项目预算。
- 是否与用户指定的构建模式冲突。

## 5.5 交付物

- Build Configuration Registry。
- Configuration Versioning。
- Configuration Validator。
- API。
- Unit Tests。

# 6. E10-T03：Export Preset Management

**优先级：P0**

## 6.1 目标

管理 Godot 项目的 Export Presets。

## 6.2 核心功能

读取并解析 Godot 的 Export Presets 配置。

需要支持：

- Preset 列表。
- Preset 名称。
- 导出平台。
- 导出模式。
- 导出路径。
- 功能配置。
- 资源过滤规则。
- 依赖模板检查。
- 配置错误提示。

## 6.3 安全规则

1. 默认只读用户现有 Export Presets。
2. 不得静默修改用户配置。
3. 自动修改前必须生成 ChangeSet。
4. 配置变更必须由用户批准。
5. 密码、证书和密钥不进入普通日志。
6. Secret 不得写入普通项目配置。
7. 对无法识别的字段保持原样，不得擅自删除。

## 6.4 导出模板管理

检查当前 Godot 版本对应的 Export Templates 是否已安装。

缺失时：

- 明确报告缺失模板。
- 提供安装指引。
- 不得假装模板已经安装。
- 不得自动下载并执行未经确认的文件。

## 6.5 交付物

- Export Preset Parser。
- Preset Registry。
- Preset Validator。
- Preset ChangeSet Integration。
- Secret Redaction。

# 7. E10-T04：Build Environment Manager

**优先级：P0**

## 7.1 目标

建立可检查、可记录、可复现的构建环境管理系统。

## 7.2 环境检查范围

### Godot 环境

- Godot 可执行文件路径。
- Godot Engine 版本。
- Godot Engine 构建类型。
- Headless 能力。
- Export Templates 版本。
- 项目要求的 Godot 版本。

### 操作系统

- 操作系统名称。
- 系统版本。
- CPU 架构。
- 可用内存。
- 磁盘空间。
- 文件权限。

### 平台工具链

根据平台检查：

- 编译器。
- 平台 SDK。
- 签名工具。
- 打包工具。
- 目标架构支持。
- 必需的运行时依赖。

不能把某个平台的 SDK 存在误认为所有平台均可构建。

## 7.3 Environment Fingerprint

建议字段：

```text
environment_id
os_name
os_version
cpu_architecture
godot_version
godot_executable_hash
export_template_version
toolchain_versions
sdk_versions
renderer
build_executor_version
environment_fingerprint
created_at
```

环境指纹用于判断历史构建是否具有可比性。

## 7.4 环境分类

- READY：所有必要依赖满足。
- READY_WITH_WARNINGS：可以构建，但存在警告。
- BLOCKED：缺少必要条件。
- UNKNOWN：无法确认环境状态。

只有符合策略的环境才能启动构建。

## 7.5 交付物

- Environment Detector。
- Godot Environment Probe。
- Toolchain Registry。
- Environment Fingerprint。
- Environment Diagnostics UI。

# 8. E10-T05：Build Orchestrator

**优先级：P0**

## 8.1 目标

负责构建任务的创建、调度、执行和生命周期管理。

## 8.2 核心功能

- 创建 Build。
- 排队。
- 调度。
- 并发限制。
- 资源锁。
- 构建超时。
- 取消。
- 重试。
- 失败处理。
- UNKNOWN 恢复。
- Attempt 记录。

## 8.3 构建执行流程

```text
Create Build
    ↓
Validate Project
    ↓
Validate Configuration
    ↓
Check Approval / Permissions
    ↓
Check Environment
    ↓
Acquire Resource Lock
    ↓
Create Build Attempt
    ↓
Start Build Executor
    ↓
Monitor Process
    ↓
Collect Logs
    ↓
Collect Export Outputs
    ↓
Validate Outputs
    ↓
Register Artifact
    ↓
Release Resource Lock
    ↓
Finalize Build
```

## 8.4 并发控制

同一项目默认不允许两个可能互相影响的构建操作同时修改项目状态。

允许并行的前提：

- 输入版本已冻结。
- 构建工作目录隔离。
- 输出目录隔离。
- 不共享可变临时文件。
- 环境资源预算允许。

## 8.5 资源锁

使用 E4 Resource Lock。

锁必须具有：

- resource_id
- owner_id
- lease_expiration
- fencing_token

过期锁不能直接假定执行已终止，必须先检查实际执行进程。

## 8.6 取消机制

取消操作必须区分：

- QUEUED：取消排队任务。
- PREPARING：终止尚未启动的准备操作。
- RUNNING：向执行器发出取消请求。
- EXPORTING：安全终止导出过程。
- COLLECTING：原则上完成安全收集或进入恢复流程。

取消不能自动删除已经生成的文件。

## 8.7 交付物

- Build Orchestrator。
- Build Scheduler。
- Attempt Manager。
- Build Queue。
- Resource Lock Integration。
- Build Lifecycle Tests。

# 9. E10-T06：Godot Headless Build Adapter

**优先级：P0**

## 9.1 目标

通过明确版本的 Godot Engine 执行真实项目检查、导入和导出。

## 9.2 执行器要求

所有操作通过受控 Build Executor 执行。

Executor 负责：

- 命令模板管理。
- 参数验证。
- 路径限制。
- 环境变量隔离。
- 进程启动。
- 进程监控。
- 超时控制。
- 进程终止。
- 日志采集。
- 退出码采集。
- 产物收集。

## 9.3 Godot 命令适配

根据实际安装版本和官方 CLI 参数构建命令。

典型操作包括：

- 项目解析。
- Headless 项目启动。
- 资源导入。
- Export Preset 导出。
- Headless 测试。
- 日志采集。

命令参数必须由对应 Godot 版本的能力描述生成，不能假设不同版本的 CLI 行为完全一致。

## 9.4 输出证据

每次执行至少记录：

- Godot 版本。
- 执行器版本。
- 命令模板 ID。
- 已脱敏的参数。
- 工作目录。
- 开始时间。
- 结束时间。
- 退出码。
- stdout。
- stderr。
- 日志文件。
- 输入文件 Hash。
- 输出文件 Hash。
- 环境指纹。

## 9.5 成功判定

不能只依赖退出码。

至少需要：

1. 进程正常结束。

6. 目标平台格式符合要求。
7. 无阻断级构建错误。

## 9.6 故障处理

- 查询 Executor 的进程状态。
- 查询 Attempt 状态。
- 检查日志是否继续写入。
- 检查输出文件是否稳定。
- 检查是否存在完整产物。
- 无法确定时设置 UNKNOWN。

不得直接启动第二个相同构建进程。

# 11. E10-T08：Artifact Registry

**优先级：P0**

## 11.1 目标

建立不可变制品注册与存储系统。

## 11.2 Artifact 注册规则

每个 Artifact 必须记录：

- Artifact ID。
- Project ID。
- Build ID。
- Attempt ID。
- Artifact Version。
- 平台。
- 架构。
- 格式。
- 文件大小。
- Content Hash。
- 存储位置。
- Godot 版本。
- 创建时间。
- 验证状态。

## 11.3 Hash 策略

首期使用 SHA-256。

必须支持：

- 单文件 Hash。
- Package Hash。
- Manifest Hash。
- 目录内容 Manifest Hash。

目录 Hash 必须基于规范化 Manifest 计算，不能直接依赖文件系统枚举顺序。

Manifest 应记录：

- 相对路径。
- 文件大小。
- 文件 Hash。
- 文件类型。
- 文件权限信息（适用时）。

## 11.4 不可变策略

- Artifact 注册后不允许覆盖。
- 不允许相同 Artifact ID 指向不同内容。
- 文件丢失时标记 QUARANTINED。
- Hash 不匹配时禁止交付。
- 新内容必须注册为新版本。
- 删除必须遵循保留策略和审计要求。

## 11.5 存储架构

建议：

```text
artifact-storage/
    projects/
        {project_id}/
            artifacts/
                {artifact_id}/
                    manifest.json
                    files/
            packages/
                {package_id}/
                    manifest.json
                    package.zip
```

实际路径必须由 Storage Service 管理，不允许 Agent 自行拼接和访问存储路径。

- 检查资源加载失败。
- 检查崩溃。
- 验证正常退出。

- 主菜单可以打开。
- 游戏场景可以加载。

- 玩家可以跳跃。

- 敌人可以运行。
- HUD 可以显示。
- 暂停可以使用。
- 游戏结束流程正常。

### 第六层：性能和兼容性

按照发布策略检查：

- 启动时间。
- 内存占用。
- 基础帧率。
- 崩溃情况。
- 目标平台兼容性。

## 20.2 UNKNOWN 场景

- Godot 进程仍在运行。

```text

    ↓

    ↓
Query Executor Status
    ↓
Check Process Status
    ↓
Inspect Output Files
    ↓
Verify Hash
    ↓
Check Artifact Registry
    ↓
Query External Operation
    ↓
Reconcile Actual State
    ↓
Resume / Finalize / Fail / Manual Review
```

每个操作需要：

- operation_id
- idempotency_key
- correlation_id
- external_operation_id
- operation_status
- started_at
- completed_at

重复请求必须返回既有操作状态，而不是盲目创建新操作。

## 20.5 恢复规则

### Build

检查进程、输出文件、日志和 Artifact Registry。

### Export

检查目标文件是否完整，以及是否由当前 Attempt 产生。

### Package

检查 Package Hash 和 Manifest Hash。

### Signing

查询签名工具结果并验证最终制品。

### Release

查询外部渠道状态，禁止仅根据客户端超时再次发布。

# 27. 安全与权限设计

## 27.1 权限类别

建议新增：

```text
build.config.read
build.config.write
build.environment.inspect

build.cancel

artifact.verify

signing.profile.read
signing.execute
release_candidate.create
release.approval.request
release.approval.decide
release.execute
release.withdraw
release.rollback
distribution.execute
```

## 27.2 权限原则

- RBAC + ABAC + Capability。
- 项目级权限隔离。
- UNKNOWN 默认拒绝。
- Agent 权限不能超出 Definition。
- 工具调用必须经过 Permission Check。
- 签名操作需要额外授权。
- 正式发布需要独立审批。
- 审批主体与执行主体应按策略分离。

## 27.3 构建隔离

构建过程应具备：

- 独立工作目录。
- 路径白名单。
- 进程限制。
- 资源预算。
- 网络访问策略。
- 环境变量白名单。
- Secret 隔离。
- 文件权限隔离。

如果当前系统不具备真正的操作系统级沙箱能力，必须明确报告限制，不得将普通工作目录隔离描述为完整安全沙箱。

## 27.4 日志脱敏

必须脱敏：

- Token。
- 密码。
- API Key。
- 证书路径中的敏感信息。
- 签名凭证。
- 用户个人路径中不必要暴露的部分。

# 30. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Godot 版本差异 | 导出行为不同 | 版本化 CLI Capability |
| Export Templates 缺失 | 无法导出 | 环境诊断和明确阻断 |
| SDK 不完整 | 平台构建失败 | 平台环境预检 |
| Executor 失联 | 状态不明确 | Operation Recovery |
| 构建输出不完整 | 错误制品 | Manifest 和 Hash 验证 |
| Artifact 被覆盖 | 发布完整性受损 | 不可变存储 |
| License 未知 | 法律风险 | Release Gate 阻断 |
| Secret 泄露 | 严重安全风险 | Secret Reference、脱敏 |
| 重复发布 | 外部渠道产生重复版本 | Idempotency Key、Operation ID |
| 旧审批复用 | 未授权内容发布 | Manifest Hash 绑定 |
| 只测 Editor 不测导出 | 发布后崩溃 | 对真实 Artifact 执行 Smoke Test |
| 平台能力误报 | 用户无法交付 | Capability Registry |
| 构建资源耗尽 | Backend 或系统不稳定 | Budget 和并发限制 |
| 回滚能力不一致 | 发布事故扩大 | 渠道级回滚策略 |

5. 从 Verification 到 Quality Gate。
6. 从 Build 到 Artifact。
7. 从 Release Candidate 到用户批准。
8. 从本地交付到最终运行验证。

E11 的重点不是继续堆积功能，而是检验 E0–E10 是否已经形成一套真正可工作的 Godot AI 游戏开发系统。

E10 的 Release Manager 不代表产品化已经完成。E12 仍负责产品安装、升级、迁移、授权、兼容性、用户体验、运维和正式产品发布。

# 35. E10 不可妥协的架构规则

1. Build ≠ Export ≠ Package ≠ Sign ≠ Release ≠ Distribution。
2. Build Job 与 Build Attempt 必须分离。
3. 重试必须产生新的 Attempt。
4. Artifact 必须不可变。
5. Artifact Hash 必须可验证。
6. 所有构建命令必须通过受控 Build Executor。
7. Agent 不得任意执行 Shell。
8. Secret 不得进入数据库明文、普通日志或 Agent Context。
9. Release Approval 必须绑定不可变 Artifact Hash 和 Manifest Hash。
10. 内容变化必须重新审批。
11. License UNKNOWN/UNVERIFIED 不允许正式 Release。
12. Godot Editor 运行成功不能替代导出产物 Smoke Test。
13. UNKNOWN 不允许盲目重试、重复签名或重复发布。
14. Release 必须经过授权主体批准。
15. 本地交付不等于线上发布。
16. Release Manager 不拥有 Task、Workflow 或 Verification 状态。
17. 外部分发渠道必须有明确 Provider Adapter 和能力登记。
18. 未验证的平台不得宣称支持。
19. 所有构建、签名、打包、发布操作必须有审计记录。
20. E10 完成不代表 E12 产品化完成。
