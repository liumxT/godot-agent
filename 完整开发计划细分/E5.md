# 1. 阶段概述

## 1.1 阶段定位

E5 是 AI 能力与项目操作能力的基础设施阶段。

在 E4 完成后，系统已经具备：

- Project System。
- Task System。
- Attempt System。
- Workflow Engine。
- Phase Management。
- ChangeSet Manager。
- Approval System。
- User Acceptance。
- 项目级权限体系。
- Godot Editor Bridge。

但是，系统还没有正式的 AI 模型调用框架，也没有完整的工具执行框架。

E5 需要建立两个相互独立、通过统一协议协作的基础系统：

**A. Model Gateway：AI 模型调用基础设施**

负责统一管理不同 AI Provider、模型能力、请求、响应、Token、Cost、超时、重试和调用审计。

**B. Tool System：工具注册与安全执行基础设施**

负责统一管理所有工具，包括 Godot Editor 操作、文件操作、代码操作、场景操作、资源操作、调试操作和外部服务调用。

两个系统之间不能直接耦合。

Model Gateway 不负责执行 Godot 操作。

Tool System 不负责选择 AI 模型。

Agent Runtime 在 E6 中通过统一接口调用这两个系统。

# 2. 总体架构

## 2.1 AI 与 Tool 总体结构

```text
                    E4 Task System
                          |
                          v
                    E6 Agent Runtime
                          |
               ┌──────────┴──────────┐
               |                     |
               v                     v
        Model Gateway             Tool System
               |                     |
       ┌───────┼───────┐      ┌──────┼─────────┐
       |       |       |      |      |         |
       v       v       v      v      v         v
    OpenAI  Anthropic  Local  Godot  File    External
    Adapter Adapter   Models Editor System  Services
                                  |
                                  v
                         Execution Result
                                  |
                                  v
```

## 2.2 Model Gateway 职责

- 接收模型调用请求。
- 验证模型权限。
- 解析用户模型偏好。
- 解析模型能力要求。
- 选择 Provider Adapter。
- 构建标准请求。
- 处理模型响应。
- 统一错误。
- 记录 Token。
- 记录 Cost。
- 处理超时和重试。
- 保存调用元数据。
- 输出标准化响应。

Agent 不允许直接调用厂商 SDK。

- 工具注册。
- 工具发现。
- 工具 Schema 验证。
- 权限检查。
- 风险分级。

- 后置验证。
- 失败恢复。
- UNKNOWN 状态管理。

所有项目操作必须经过 Tool System。

包括：

- Godot Scene 操作。
- Node 操作。
- Inspector 属性修改。
- Signal 操作。
- Group 操作。
- Animation 操作。
- TileMap 操作。
- 资源导入。
- 游戏运行。
- 游戏停止。
- Debugger 操作。

# 4. Model Gateway

## E5-T01：Model Gateway Domain

**优先级：** P0  
**依赖：** E1 Backend Core

### 4.1.1 开发目标

建立统一模型调用领域模型。

Model Gateway 必须独立于具体 AI Provider。

不能让业务模块直接依赖某家模型厂商的 SDK 或数据结构。

### 4.1.2 核心模型

```text
ModelProvider
- id
- name
- provider_type
- status
- configuration_ref
- created_at
- updated_at
```

```text
Model
- id
- provider_id
- model_key
- display_name
- context_window
- input_price
- output_price
- status
```

```text
ModelCapability
- model_id
- capability
- support_status
- max_input
- max_output
- evidence_source
- verified_at
```

```text
ModelRequest
- id
- project_id
- task_id
- attempt_id
- agent_instance_id
- provider_id
- model_id
- status
- request_metadata
- created_at
```

```text
ModelResponse
- id
- request_id
- status
- response_metadata
- usage
- finish_reason
- created_at
```

### 4.1.3 状态模型

Model Request：

```text
CREATED
   |
   v
VALIDATING
   |
   v
QUEUED
   |
   v
SENDING
   |
   ├──> STREAMING
   |
   ├──> SUCCEEDED
   |
   ├──> FAILED
   |
   ├──> TIMEOUT
   |
   └──> UNKNOWN
```

UNKNOWN 表示请求可能已经被 Provider 接收，但本地未能确认最终结果。

不能直接把 UNKNOWN 当作 FAILED 并重复发送非幂等请求。

### 4.1.4 验收标准

- 模型调用请求有统一模型。
- Provider 和 Model 分离。
- 模型调用状态完整。
- 所有调用都可以关联 Project、Task、Attempt 和 Agent Instance。

## E5-T02：Provider Interface

**优先级：** P0  
**依赖：** E5-T01

### 开发目标

定义所有 Provider Adapter 必须实现的统一接口。

建议接口：

```text
ModelProviderAdapter
- get_provider_info()
- list_models()
- get_model_capabilities()
- validate_configuration()
- generate()
- generate_stream()
- cancel()
- normalize_error()
- normalize_usage()
```

### 设计原则

1. Provider SDK 只存在于 Adapter 内部。
2. Agent 不直接接触 Provider SDK。
3. 不同 Provider 的错误必须标准化。
4. 不同 Provider 的 Token Usage 必须标准化。
5. 不支持的能力必须明确报告。
6. Adapter 不得自行修改用户指定模型。

### 验收标准

增加新 Provider 时，不需要修改 Task System 或 Agent Runtime 的调用接口。

## E5-T06：Model Capability Registry

**优先级：** P0  
**依赖：** E5-T05

### 开发目标

记录模型实际具备的能力。

### Capability 分类

| 能力 | 说明 |
|---|---|
| TEXT_INPUT | 文本输入 |
| TEXT_OUTPUT | 文本输出 |
| IMAGE_INPUT | 图片理解 |
| AUDIO_INPUT | 音频输入 |
| AUDIO_OUTPUT | 音频生成 |
| VIDEO_INPUT | 视频理解 |
| TOOL_CALLING | 工具调用 |
| STRUCTURED_OUTPUT | 结构化输出 |
| JSON_SCHEMA | JSON Schema 约束 |
| STREAMING | 流式输出 |
| LONG_CONTEXT | 长上下文 |
| REASONING_MODE | 特定推理模式支持 |

### 能力状态

```text
SUPPORTED
UNSUPPORTED
UNKNOWN
```

### 核心规则

UNKNOWN 不能视为 SUPPORTED。

如果模型没有经过验证，系统不得默认其支持某项能力。

### 能力证据

能力记录应包含：

- 官方文档来源。
- Provider 返回的模型信息。
- 实际能力测试结果。
- 测试日期。
- 适用 API 版本。

### 验收标准

Model Router 能够基于能力约束排除不满足要求的模型。

## E5-T07：Model Routing

**优先级：** P0  
**依赖：** E5-T06

### 开发目标

建立统一模型选择和路由机制。

### 路由输入

```text
ModelRoutingRequest
- requested_model
- required_capabilities
- task_type
- context_size
- output_limit
- latency_preference
- cost_preference
- project_policy
- user_preferences
```

### 路由规则优先级

1. 用户明确指定的模型。
2. 用户授权的模型范围。
3. 模型实际能力。
4. 上下文长度要求。
5. 项目模型策略。
6. 预算限制。
7. 用户成本偏好。
8. 延迟偏好。

### 不允许静默降级

如果用户指定的模型不可用：

- 明确返回不可用原因。
- 提供可选替代模型。
- 等待用户确认是否替换。

不能在用户不知情的情况下自动换成能力较弱的模型。

### 路由结果

```text
ModelRoutingResult
- selected_provider_id
- selected_model_id
- capability_check
- budget_check
- fallback_options
- routing_reason
```

## E5-T12：Cost Tracking

**优先级：** P0  
**依赖：** E5-T11

```text
ModelCost
- request_id

- output_cost
- cached_input_cost
- additional_cost
- currency
- pricing_version
- calculation_status
```

### 计费原则

- 价格来源必须可追踪。

- Task Budget。
- Attempt Budget。
- Agent Budget。
- 单次调用 Budget。

超过预算后，根据策略阻止新请求或请求用户授权。

## E5-T14：Retry & Timeout

**优先级：** P0  
**依赖：** E5-T08

### 开发目标

建立统一超时、取消和重试策略。

### 错误分类

```text
AUTH_ERROR
RATE_LIMIT
PROVIDER_UNAVAILABLE
NETWORK_ERROR
TIMEOUT
INVALID_REQUEST
CAPABILITY_UNSUPPORTED
CONTENT_REJECTED
UNKNOWN_RESULT
```

### 重试策略

可以重试：

- 明确未发送的请求。
- Provider 明确返回可重试错误且请求语义允许重试的请求。
- 有明确幂等保障的请求。

不能盲目重试：

- 请求已发送但响应未知。
- 可能产生重复计费的请求。

# 9. Tool Risk Classification

## E5-T20：Tool Risk Classification

**优先级：** P0  
**依赖：** E5-T17

### 风险等级

| 等级 | 名称 | 示例 | 默认处理 |
|---|---|---|---|
| R0 | READ_ONLY | 查询项目状态 | 权限检查后执行 |

# 12. Tool Idempotency

## E5-T23：Tool Idempotency

**优先级：** P0  
**依赖：** E5-T22

### 开发目标

避免断线、重试或重复请求导致重复修改项目。

### Idempotency Key

建议由以下信息组合生成：

```text
project_id
task_id
attempt_id
tool_id
logical_operation_id
```

### 执行前检查

1. 查询 Idempotency Key。
2. 判断是否存在历史执行。
3. 如果已成功，返回已有结果。
4. 如果正在执行，返回当前状态。
5. 如果失败，按策略判断是否允许重试。
6. 如果 UNKNOWN，先执行结果核验。

### 关键原则

UNKNOWN 不能直接重新执行。

例如：

Godot Editor 已经创建了一个 Node，但 WebSocket 在返回结果前断开。

此时再次创建 Node 可能造成重复节点。

必须先查询实际 Editor 状态，判断操作是否已经发生。

- 幂等记录必须具有唯一约束。
- 不允许跨模块直接访问 Repository。
- 重要业务状态变化使用 Outbox。

# 21. 安全设计

## 21.1 Model Gateway 安全

- Provider API Key 不写入数据库明文。
- 模型调用必须关联授权 Project。
- 不允许 Agent 修改 Provider 凭证。
- 模型路由不能绕过用户指定模型策略。
- 外部模型请求需要遵循 External Data Authorization。
- 敏感 Context 必须经过数据发送策略检查。
- 模型输出视为不可信输入。

## 21.2 Tool System 安全

- 所有工具都必须注册。
- 所有参数都必须验证。
- 所有执行都必须经过权限检查。
- 高风险工具必须经过审批。
- 写操作必须关联 ChangeSet。
- 重要操作必须进行后置验证。
- 未知状态不能自动重试。
- 文件路径必须受到项目范围限制。
- Editor 操作必须验证 Session 和 Lease。
- 资源锁必须验证 Fencing Token。

## 21.3 Prompt Injection 防护

必须将以下内容视为不可信数据：

- 用户输入。
- Godot 项目文件。
- 脚本注释。
- 场景名称。
- 资源名称。
- 外部网页。
- 第三方文档。
- Tool 返回结果。

不可信数据中的指令不能改变系统权限、审批要求和工具安全策略。

# 25. E5 性能和可靠性要求

1. Provider Adapter 不能阻塞 Backend 主事件循环。
2. 模型请求必须支持超时控制。
3. Tool 执行必须具有执行期限。
4. 大型模型响应不能无边界缓存。
5. Tool 输出必须限制大小。
6. Token 和 Cost 记录不能阻塞主要执行流程。
7. 高风险 Tool 必须执行完整审批流程。
8. Tool Execution 必须可追踪。
9. 所有重要操作必须具有幂等机制。
10. UNKNOWN 必须具有专门恢复流程。
11. Resource Lock 必须支持过期和 Fencing。
12. Tool Execution 结果必须能够进行后置验证。

# 28. E6 阶段准入条件

E5 验收通过后，进入：

**E6：Agent Runtime（AI Agent 运行时系统阶段）。**

E6 将建立：

1. Agent Definition。
2. Agent Instance。
3. Agent Lifecycle。
4. Agent Runtime Scheduler。
5. Agent Execution Loop。
6. Agent Planning。
7. Agent Step Manager。
8. Agent Context Binding。
9. Agent Model Binding。
10. Agent Tool Binding。
11. Agent Permission Binding。
12. Agent Budget Manager。
13. Agent Checkpoint。
14. Agent Event Log。
15. Agent Recovery。
16. Agent Stop/Pause/Resume。
17. Agent Execution Result。
18. Agent Runtime Monitoring。

E6 的核心任务是让一个 Agent 能够接收 Task、读取 Context、调用 Model Gateway、调用 Tool System、检查执行结果并持续推进任务。

但 E6 仍然以单 Agent Runtime 为重点。

多 Agent 的 Orchestrator、专业角色协作和 Handoff 会在 E7 中实现。

**E5 的最终目标：建立一个统一、可扩展、可审计、可控成本且具有严格安全边界的 AI 模型与工具执行基础设施，让未来所有 Agent 都通过同一套模型调用和工具执行体系工作。**
