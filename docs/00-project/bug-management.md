# Bug 管理规范（E0-T10）

## 1. 严重级别

| 级别 | 定义 | 响应 |
| --- | --- | --- |
| P0 | 数据损坏、凭证泄露、服务不可用、无法启动 | 立即修复，暂停其他工作 |
| P1 | 核心功能不可用且无绕过方式 | 当日内定位，优先修复 |
| P2 | 功能异常但有绕过方式 | 当前迭代内修复 |
| P3 | 体验/文案/低频问题 | 排期处理 |

## 2. 生命周期

```text
New → Confirmed → Fixing → Fixed → Verified → Closed
```

| 状态 | 进入条件 | 负责人 |
| --- | --- | --- |
| New | 提交 Bug 报告 | 报告人 |
| Confirmed | 可复现并确认级别 | 值班/技术负责人 |
| Fixing | 已分配并开始修复 | 开发者 |
| Fixed | 修复提交已合并 | 开发者 |
| Verified | 回归用例通过 | 测试/评审人 |
| Closed | 确认无遗留 | 技术负责人 |

无法复现时标记 `Need Info`，超过 5 个工作日无回应则 `Closed`（附说明）。

## 3. 报告要求

使用 [bug-report 模板](../templates/bug-report.md)，必须包含：

1. 环境（OS、Godot 版本、Backend commit）。
2. 最小复现步骤与复现概率。
3. 期望结果与实际结果。
4. 证据：结构化日志行（含 `event` / `correlation_id`）、截图、CI 报告。

缺少复现步骤的报告不进入 `Confirmed`。

## 4. 定位手段

| 手段 | 用途 |
| --- | --- |
| `correlation_id` | 串联一次请求在日志与错误响应中的记录 |
| `event` 字段 | 按事件名过滤（如 `migration_failed`） |
| `artifacts/ci-report.md` | 判断是否为环境/检查问题 |
| 迁移备份 `backups/` | 数据异常时对比升级前状态 |

## 5. 修复要求

1. 必须先补回归测试，再修复（或同一 PR 内完成）。
2. P0/P1 修复必须包含根因说明与影响范围评估。
3. 涉及契约的修复需同步 `packages/contracts/`。
4. 修复提交信息使用 `fix(<scope>): ...`，并在 Bug 报告中填写 commit。

## 6. 回归验证

- 新增测试必须能在修复前复现失败、修复后通过。
- 验证人独立执行 `check_all.py`，结果附在报告中。
- 验证通过后由报告人或测试人员关闭。

## 7. 统计与复盘

- 每阶段验收时统计 P0/P1 数量与平均关闭时间。
- P0 必须产出复盘记录，说明预防措施（测试、检查项、文档）。
