# Code Review 规范（E0-T10）

## 1. 基本要求

1. 任何进入 `main` / `develop` 的代码必须经过至少 1 人评审。
2. 作者不能评审自己的变更。
3. 评审必须在 CI 通过后进行；CI 失败时先修复再评审。
4. 单次 PR 尽量控制在 400 行以内（不含迁移与生成文件）。

## 2. 评审重点

按优先级从高到低：

| 优先级 | 关注点 |
| --- | --- |
| P0 | 正确性、数据一致性、安全（凭证、路径、权限） |
| P1 | 模块边界、跨模块访问、契约一致性 |
| P2 | 错误处理、日志事件、测试覆盖 |
| P3 | 命名、可读性、注释 |

架构级变更（新增层、跨模块依赖、协议版本）必须先有 ADR。

## 3. 评审流程

1. 作者按 [code-review 模板](../templates/code-review.md) 填写 PR 描述，
   包含变更目的、关联任务、验证证据。
2. 评审人逐项核对检查清单，问题标注级别：
   - `Must`：必须修改，阻塞合并。
   - `Should`：建议修改，可在本 PR 或后续任务处理。
   - `Nit`：风格问题，不阻塞。
3. 所有 `Must` 解决后，评审人给出 `Approve`。
4. 作者合并；合并后删除功能分支。

## 4. 必须阻塞的情况

- 存在明文凭证或敏感文件。
- 未通过 `check_all.py` 且无合理说明。
- 缺少对应测试，或测试被跳过/弱化。
- 破坏契约但未更新 `packages/contracts/`。
- 跨模块直接访问其他模块 Repository。
- 静默吞掉异常或使用空实现掩盖失败。

## 5. 评审证据

评审记录中必须包含：

1. 执行的检查命令与结果摘要。
2. 关键测试名称。
3. 如涉及 UI，附截图或录屏说明。

## 6. 响应时限

| 变更规模 | 首次评审响应 |
| --- | --- |
| < 100 行 | 1 个工作日 |
| 100–400 行 | 2 个工作日 |
| > 400 行 | 拆分后评审 |
